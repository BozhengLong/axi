# R3执行设施

本目录执行[方案22](../../../docs/22-unbounded-candidate-acceptance-plan.md)。2026-11-18已通过R1，正在执行R2材料与完整流程资格。正式入口需要完整冻结清单与控制账本；当前没有T1或真实模型成绩。

## 身份与运行

`core.ts`固定Linux镜像，调用方必须明确指定`mock`或`real`。模拟模式使用本地无上游配置。正式执行由`formal-one.ts`经`controller-gateway.py`取得唯一attempt，再由`execute-subject.ts`启动。产品挂载只包含核验过的源码和package.json，权限只读。

R3代理要求完整策略：version为r3、limitMode为unlimited、requestLimit为null、executionDeadline为整数毫秒时间戳。Python控制账本使用秒，执行入口只做一次单位转换。次数只计量，截止覆盖环境准备、模型、工具和重试。旧r2独立保留原预算行为。

`guardian.py`是独立宿主监督进程。它检查原执行器的PID与启动身份、固定截止和实际可用空间。执行器消失、到期或空间不足时，它撤销转发、发送中断，再强制终止被测进程。它不启动新任务。主进程结束前等待监督器关闭，再封存证据。任务容器无法访问监督器的配置和结束请求文件。

## 证据

代理和终端使用64 MiB分块，保留字节顺序、哈希和关闭状态。原生会话按48 KiB帧流式导出；任务侧与宿主分别核对文件身份、长度与哈希。只有停止写入者、完成导出和移除转发容器后，才生成最终Trace清单。

IO写入失败会留下失败状态，执行循环据此停止。执行器崩溃时，监督器继续保全。缺少结束事件或分块关闭清单时，审计器拒绝宣称Trace完整。导出失败时保留冻结容器和任务卷中的原件；不得用空目录或补造事件替代。

`execution-evidence.py`核对实际请求、完整响应、原生尝试、计数、阶段、终态与授权。v1要求Trace v4；旧v0按其原有日志格式，用独立运行目录、唯一日志文件和请求内容关联。`input-evidence.py`把输入清单、初态中的完整题面和实际API内容关联。

`ENV_INTERRUPTED`需要封存的外部见证和保护审查。恢复后正常交付按产物评分。普通N、缺失证据、鉴权或本地资源问题不提供补跑资格。每个attempt独立保留。

## 声明的资源边界

| 资源 | 当前边界与处理 |
|---|---|
| 模型请求 | 单请求体16 MiB；达到本地资源边界时保留异常，不能算上游限流 |
| 任务容器 | 2 CPU、4 GiB内存、256 PID；正式任务使用独立Linux卷 |
| 代理容器 | 512 MiB内存、64 PID |
| 临时目录 | 任务HOME和/tmp各256 MiB；题目特有缓存按冻结配置另行登记 |
| 终端观察 | Axi保留末尾16,777,216个UTF-16代码单元用于交互；原始IO完整另存 |
| 记录解析 | JSONL单条记录64 MiB；Claude当前行最多67,108,864个UTF-16代码单元；原生导出单帧解析256 KiB |
| 产物快照 | 沿用R2的128 MiB有效文件内容上限；.axi与依赖/生成目录按原规则另行处理 |
| 短命令返回 | 旧通用命令助手仍有200 MiB输出边界。CLI原始IO和原生日志导出使用独立流式入口 |
| 磁盘 | R2首次准入取max(57 GiB, 1.5×预计保留/工作量＋9 GiB)；运行中保全底线9 GiB |

大Trace资格通过受控真实CLI产生超过200 MiB和100000事件的原始流，随后校验所有字节。它不估计模型能力。R2仍须使用完整题目模拟、恢复链与长Trace测量实际容量。

## 验证入口

`r1-final.py STUDY NEW_LABEL BUNDLE`创建新的资格目录，按固定五次运行。它在每步前后核对源码；失败即停，不覆盖旧结果。`audit-engineering.ts`与`audit-identity.ts`核对两平台工程原始证据。

`pipeline-one.ts`以模拟API驱动真实CLI，并共用正式启动、输入、监督、封存、评分与审查入口。健康任务的v1复核检查点也单独保存和评分。`mutant-qualification.py`故意恢复次数截断、允许迟到执行、重复claim或将普通N恢复，要求实际断言检出。`evidence-qualification.py`重算反例哈希后检查语义，不能仅靠哈希不符拒绝错误证据。

`formal-grade.py`使用R3控制账本与共享时间窗，评分语义显式复用未修改的R2核心。资格复用必须按方案22另行审计依赖；本说明不代表20题已取得资格。


## 冻结候选的远端引用

R2 和 R3 新打包都从本批 `authorization.json` 读取 `candidateRef`。登记完整远端引用，例如 `refs/tags/v0.0.1` 或 `refs/heads/codex/v1-preview-scoring`。填写引用时同时核对它当前指向本批候选提交。OAuth 批次继续登记原有 `candidateIdentity`。引用缺失、只匹配到同名后缀、远端提交变化、源码清单与候选不一致时，打包拒绝生成正式清单。

打包在 `origin` 查询完整引用。带注释的 Git 标签解析到指向的提交，清单中的 `candidateGit` 保留标签对象、候选提交、源码哈希和引用名。准入复核比对批次授权及这条冻结见证。已封存的旧清单沿用历史身份绑定，因此可以离线复核。R2 和 R3 原有候选及正式验收门槛继续适用。

## R2入口

`prepare-tasks.py`按旧绑定重建U02–U20与C7，独立保存业务契约哈希，只更新公开预算文字。依赖使用APFS独立克隆，并由`dependency-audit.py`在固定Linux镜像中重新检查文件、链接和模式。`exposure-audit.py`核对旧闭批账本、模拟API登记和P3源码差异。

`qualify-material.py`适配未改的R2资格逻辑。它只改任务ID、批次准入和新证据路径，保存原源码、实际执行源码和逐项替换记录。当前采用完整五次；原态、参考、反事实及负例全部保存。`qualification-queue.py`逐题执行，失败停止；`audit-material.py`核对每次断言、来源和时间。

`pipeline-queue.py`执行65条当前CLI模拟，等待相应材料资格后才启动。它测量本槽工作目录及宿主可用空间，不触碰其他容器。`recovery-qualification.py`完成健康目标和普通任务两条实际CLI恢复链：原始中断先封存，实际等待15分钟，三方健康通过后才完成第二次尝试。其前序是明确标记的合成账本，不是正式成绩。

`audit-pipelines.py`重读65份完整Trace、实际API题面、评分和账本。`resource-policy.py`纳入73次可能尝试、实测恢复链、大Trace增长和工作峰值；估算不依赖透明压缩后的较小分配量。`build-readiness.py`和`release-package.py`只在全部证明、源码、推送和首次容量同时满足时构建正式准入。

`compress-closed.py`仅透明压缩已闭合资格与完整封存Trace。它逐文件检查原字节、权限、mtime，并重验封存清单。它不处理活动输入、未完整封存现场或备份。APFS快照可能保留压缩前块，文件分配减少不等于可用空间立即增加。

正式开始后，阶段与T1以`formal-controller/controller-events.jsonl`为准。`status.json.phase`保留已完成的准备阶段R2，避免让已登记的评分修复误入未授权准备流程；可另写`formalPhase`显示进度。`qualification_guard.py`优先检查正式账本，只在有修复令牌和有效窗口时放行资格。

一次同契约评分修复的代码边界覆盖实际使用的R2评分模块，以及R3对应评分模块。允许的文件名保持明确列表；控制器、执行器、代理、快照采集、产品和原始输入均不在该边界内。每次修复仍需登记、五次资格、全部受影响视图重评和24小时截止，不因路径修正获得额外机会。
