# C6/R2：依据真实验收反馈修正

> 控制器侧模板。本轮不新增需求。模板和结果字段冻结后用于双方；不能人工追加定向修复提示。

## 投递文本

上一轮的独立可见验收已完成。下面是当前快照的真实检查结果，请据此修正，再验证当前契约、原回归和用户文件保护。

如果下面全部通过，请明确区分“可见检查通过”和“已经覆盖所有可能情形”，复查当前契约的边界及自己的测试即可；不要求为了产生改动而修改代码。本轮没有新增功能要求。

继续使用同一工作目录与会话。不得覆盖用户已有修改。最后报告本轮的修正、实际检查结果及未解决问题，交付后等待下一轮。

## 反馈包格式

正文之后附 UTF-8 JSON。字段定义如下，实施时每项都填真实值，不使用虚构的失败示例。

| 字段 | 含义 |
|---|---|
| `schemaVersion` | 固定为 1 |
| `trajectoryId`、`roundId` | 当前轨迹与被检查的 R1 |
| `sourceSha256`、`visibleSuiteVersion` | 被验收快照和冻结可见包版本 |
| `summary` | `passed / failed / not_run` 各项数量，仅代表可见检查 |
| `checks[]` | 按冻结 case ID 排序；每项含 `id`、`status`、`requirement`、`expected`、`observed`、`command`、`exitCode`、`stdout`、`stderr` |
| `artifacts[]` | 可见复现输入及完整输出文件的路径与 SHA-256 |

原测试、构建或类型检查产生的真实错误位置可以原样保留。控制器不另行定位源码修复点，不提供参考补丁。对长日志按统一字节上限生成摘要，同时提供只含可见证据的完整文件；不得因工具身份调整详细程度。

若基础设施未完成验收，不能伪造 failed 或 passed 包进入下一轮；应先按环境故障处理。H 检查的代码、用例、结果和总分均不进入本轮反馈。
