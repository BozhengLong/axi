# 同键删除的等待与错误归属

本文件R1–R6及公开时序是本研究已确认的行为定义。它明确替代旧资料中未定义的“适用删除/正在等待”含义。

## 3. 术语与推荐规则

本节的`del1`、`del2`表示删除操作，不是设计决策D编号。以下讨论同一个缓存对象、同一个键。

- **删除生效**：参数和能力检查成功后，安装失效状态；发生在该删除API返回Promise之前。沿用既有重入契约。
- **未完成删除**：已生效，但对应删除操作尚未完成成功或失败处理。仅后端回调返回，不等于库已完成该操作。
- **新工作W**：完成键求值后，没有加入可合法复用的已有工作，因而启动的新一份计算。复用已有Promise的调用共享那份工作的结果；不重新选择错误归属。
- **等待目标**：W当前直接等待的一次删除操作。它是描述公开行为的逻辑关系，不要求实现某个字段、集合或Promise链。

### R1：删除操作依次执行，各自报告自己的结果

同键删除按生效顺序执行。后一次必须等待前一次完成，成功或失败都算完成，然后调用自己的后端delete一次。前一次失败不得省略后一次。

`del1`返回的Promise只报告`del1`的后端结果；`del2`返回的Promise只报告`del2`的后端结果。为了让队列继续而观察前次拒绝，不能把公开返回的错误吞掉。不同键、不同缓存仍独立。

### R2：W开始时选择最新未完成删除

W在身份形成后、首次缓存读取或业务计算之前，同步选择此刻生效顺序最后的一次未完成同键删除。没有未完成删除时，W不承担历史删除的失败。

如果`del1`和`del2`都已生效且未完成，W选择`del2`。`del2`的串行执行已经保证W不会越过`del1`提前开始读取。W不因此继承`del1`的失败。

选择与等待登记之间不能额外执行用户回调，或插入一个异步让步来任意改变选择结果。cacheKey内发生的删除先于W身份形成，按既有条款纳入选择。若调用合法复用了已有工作，则依该工作已选择的目标继续，不能借复用重置其失败。

### R3：选定目标失败，W按该目标的原错误拒绝

W一旦选择某次删除，该删除失败时，W按原错误拒绝。之后排队或成功的删除不能把这次拒绝改成成功，不能把错误替换成更新删除的错误。

因此，`del1 → W选择del1 → del2 → del1失败 → del2成功`时，W仍失败。错误保留身份和值，涵盖对象、Symbol、`undefined`、`null`、`0`等，不能用真假判断是否存在错误。

W拒绝后不必等后续删除全部完成；后续删除本身仍须执行。内部队列或清理Promise不能产生无人处理的额外拒绝。

### R4：选定目标成功，W恢复时再次检查

等待目标成功后，W在开始缓存读取或业务计算之前，再检查此刻是否还有未完成同键删除。有则选择其中最新一次，并重复R3/R4；没有才可继续。

W仍在等待`del1`时加入的`del2`，不能让W越过尚未完成的`del2`提前读取。但`del2`若在W恢复检查之前已经完成，且W从未选择它，W不追溯承担它的失败。这一规则不回放已经结束的全部删除历史。

每次检查基于实际发生的先后关系。要求唯一结果的测试必须固定恢复检查前后的位置；无法固定的竞争使用预先声明的允许集合。不能凭墙钟延迟猜测，也不能把“后来出现过删除”直接等同于“曾经选为等待目标”。

### R5：等待成功不恢复旧写资格

等待目标、读取资格和写回资格分别判断。等待删除成功，只解决何时可以继续读取；不使在后续失效之前形成的旧工作重新取得写资格。

既有共享写失效、仅移除目标函数去重登记、clear不等待已开始set、W01等待调用不得重新写回，以及原生Promise观察语义均保持。clear不能取消已经排队的delete，也不能消除已选删除的失败。同步重入开始的工作仍须遵守原登记边界，不能因本次澄清移除157条既有检查。

### R6：失败释放后可以新建工作重试

一次失败的等待工作清理完成，且没有未完成同键删除时，后来的新工作可以重新读取或计算。不能永久复用失败工作，也不能将已结束删除的错误永久保存成新调用的失败。

没有承诺后端删除失败时缓存必定为空。后端可能已部分修改；W成功继续后仍按实际缓存读取结果和业务结果执行，后续业务本身也可能失败。
