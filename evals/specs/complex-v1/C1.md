# C1：修复重复下单与库存竞争

> 任务设计已实施。实际题面与初始项目见 [seed](../../complex-v1/C1/seed/)，验收历史与结果见 [报告](../../../docs/verification/2026-11-11-complex-comparison.md)。冻结批次使用各自源码快照。

## 场景

你接手一个已有的订单服务。客户端因超时重试时，偶尔生成重复订单；并发提交时，库存可能小于 0。请定位原因并修复，不重写整个项目，也不改变现有读取接口。

实施时将提供：路由、订单服务、SQLite 存储、旧客户端、公开测试、启动说明，以及复现用例。原项目可启动并通过严格类型检查。

## 业务契约

- `POST /orders` 接收 `sku`、正整数 `quantity` 和 `Idempotency-Key`。
- 首次成功返回 201。相同键和相同业务参数重放，返回同一个订单 ID、状态码和业务响应体。
- JSON 对象的键顺序不影响业务参数是否相同。
- 相同键但不同商品或数量返回 409，不修改状态。
- 缺少键或参数无效返回 400。库存不足返回约定的 409。失败请求不消耗幂等键，不产生订单或扣减残留。
- 库存、订单和成功幂等记录应一起提交。成功提交后即使响应丢失，重试也不能再次扣减。
- 重启后仍可识别成功重放。
- 保留原有读取 API 和旧客户端契约。具体响应字段以提供的接口文档为准，实施前冻结。
