# v1 发布候选修复与验收方案

2026-11-14。状态：D1–D5已由用户确认，正在实施。原方案依据是用户询问“接下来应该怎么做，才能让v1达到发布门槛”。实施与实际验证见[当日日报](devlog/2026-11-14.md)。

目标：修复已确认的协议兼容缺口，验证通用交付流程的改进，再用冻结版本完成原定发布验收。保持[v1设计](07-v1-design.md#94-评测适配与指标)的要求：确定性场景通过，新Axi两次C7已知回归及六次新任务完整交付，没有未解决的保护或协议回退。无需胜过Claude Code，也不以更少token或更快速度代替正确交付。

## 1. 当前证据与判断

截至本次检查，本地产品仍为`0bde765`，分支为`codex/v1-tools`，上次收尾提交为`435e551`。本轮建议不改变[上轮报告](verification/2026-11-12-v1-stable-comparison.md)或其原始证据。

| 已观察的事实 | 判断 | 下一步 |
|---|---|---|
| 固定Node22的320次重复检查通过，14份真实交付的评分正常结束 | 已有可用的环境基础；不能宣称故障率为零 | 保留固定工具版本与隔离设施，对新候选重新做相关门槛 |
| HTTP200的SSE错误把`error`写成字符串；产品丢失具体错误说明，控制器不能归类 | 可定位的产品与评测协议兼容缺口 | 先用脱敏事件复现，再修复错误规范化和独立归因 |
| 新Axi一份Emittery实现读取被丢弃对象的`then`属性，破坏事件隔离 | agent交付代码存在真实缺陷；未证明文件工具本身有错 | 验证通用边界自检能否改善交付，不把修补这份答案当作修好了Axi |
| 旧Axi另有报告未复验、README示例语法错误 | 暴露交付审查与验收覆盖的薄弱处，不都是新Axi的缺陷 | 加入下一版校准，分别核对代码、文档和报告 |
| 新Axi已有“不要声称未执行操作已完成”的系统指令 | 单纯重复提醒不足以证明质量改善 | 将自检动作具体化，并通过实际CLI行为检查效果 |

假设：简短、通用的交付自检要求可能改善代码边界、文档和报告质量。它尚未被验证，不能保证模型之后六次都成功。六次通过也是限定任务集的发布条件，不是任意任务都正确的保证。

## 3. 第一阶段：修协议，先用离线证据验证

修改范围首先限于错误解析、重试信息和评测归因。现有位置为`src/api/stream.ts`、`src/api/client.ts`、转发器及`scripts/eval/c7/outcome.ts`。实际实现可以提取小型模块，不引入SDK、agent框架或新依赖。

- 标准结构化错误继续支持。对上次观察到的字符串限流事件，使用明确、可审查的匹配规则；不以包含某个词作为任意错误都可重试的依据。
- 只对真实API错误事件做规范化。普通模型正文、工具输出或用户文本不能触发限流恢复。
- 未识别错误保留脱敏后的说明和原始结构，停止并明确标记未知；鉴权错误不得误判为可重试限流。
- 沿用现有最多三次请求重试。重试次数、等待和实际请求均留证，受原任务预算与截止约束；等待时Ctrl+C必须有效。持续限流在上限后仍可能无法完成任务，不能承诺靠兼容修复消除上游限额。
- 只重试当前未完成的模型请求，保持请求快照；不重做已执行的工具，不把部分工具参数作为完整调用执行，不重复追加失败响应到历史。
- 产品与评测器采用相同错误字段规范。验收使用固定输入及独立预期结果，不能只让评分器调用产品自己的分类函数来证明其正确。
- 转发器只补充旁路记录和归因，不改写候选实际收到的HTTP/SSE。新版在自己的客户端兼容错误格式；旧Axi和Claude保留各自产品行为。

离线用本次脱敏事件和反例验证：标准限流、已知字符串限流、未知字符串、鉴权、畸形事件、部分流后错误、重试成功、连续失败到上限、退避期间取消，以及已执行工具后的下一请求失败。核对实际调用次数、历史配对、工具副作用和原始/规范化日志。

随后回归现有文件、权限、中断和日志场景；通过后再做真实接入探针。上轮已关闭且截止已过的研究不使用`--live`或`--resume`重新打开。

## 4. 第二阶段：改进交付习惯并检查验收器

优先在现有系统指令中加入可执行的通用流程，不增加隐藏自动批准或额外agent：

1. 实现前读取现有接口、测试和约束，明确兼容要求。
2. 对改动涉及的状态转换、异常传播、取消与清理补充真实行为测试；根据任务选择边界，不机械套模板。
3. 检查新增文档示例；最后一次相关修改之后重新执行受影响的检查。保留真实退出码，不把管道中`tail`等命令的成功当成测试成功。
4. 最终说明区分实际执行且通过、执行但失败、未执行；依据工具证据说明剩余风险。用户拒绝检查时如实记录，不能绕过拒绝。

上述属于模型工作要求，不是运行时能自动证明所有代码正确的保证。不得写入Emittery专用补丁、`then`边界答案、隐藏测试内容或特定测试名。

将上轮p-limit和Emittery归为已知开发回归题。验证候选时，各进行一次真实模型开发试跑，共两次，保留成功和失败；不计入正式新题成绩。若未满足交付要求，先分析，不反复抽样到成功，也不直接进入正式轮。

两次开发试跑使用同一产品和系统指令快照，开始前记录哈希，中途不改。若根据结果继续修改，原通过不能移作修改后版本的证据；本方案的试跑额度不重置，须重新明确后续验证范围。

同时校准验收器：

- 让已知错误产物失败，参考修复通过；包含异常属性访问、溢出隔离、监听清理和相邻状态等契约导出的边界。
- 对新增或修改的完整JavaScript示例做语法检查；伪代码与完整示例的区分事先写清。只做语法检查时不声称验证了运行行为。
- 将最后修改时间、检查命令及真实结果与报告相互核对；不以报告中的“通过”字样作为证据。
- 对基线、参考、故意错误实现和恒真测试做正反校准。正式保留检查只能覆盖公开契约。

每次修改产品或系统指令，保存新的版本及开发记录。所有既有正式成绩保留，不把改过的历史产物回填为成功。

## 5. 第三阶段：冻结发布候选，执行一次正式验收

开发验证通过后，冻结产品和系统指令，提交并推送。此后再选择两道新仓库任务，固定提交、依赖、题面、参考和验收；要求涉及多个文件、兼容性、异常/状态边界、类型或文档及新增回归，不能用简单任务替换既定复杂度。

同题比较仍为旧Axi`963704b`、新候选Axi和Claude Code，使用同一固定执行环境与模型设置。新题不得用于继续修改候选；如需修改，新题转为开发题，正式计划必须重新设计。没有独立盲审时不得称盲测。

复用Node22.23.5及现有隔离、封存和版本化评分设施。镜像因新产品而派生新digest，新任务依赖和相关检查也需重新验证；不能把旧完整源码下的门槛结果冒充新候选已通过。具体任务冻结时列明每项门槛的版本与执行证据。

已确认预算如下：

| 用途 | 计划与上限 |
|---|---|
| 已知开发题试跑 | p-limit、Emittery各一次，共2次；不计正式成绩 |
| 当前候选的C7回归 | 两题各一次，共2次真实执行；历史离线产物单列 |
| 新题三方正式对照 | 两题×三方×三次，共18次 |
| 上游整组恢复 | 至多一次完整三方补跑；正式合计最多23次，普通失败不补跑 |
| 真实接入探针 | 初始三方各一次；合法上游恢复前至多再各一次，总计最多6次 |
| 真实CLI启动总上限 | 开发2 + 正式最多23 + 探针最多6 = 31次；不是成功样本配额 |
| 单次任务 | 30分钟、最多50次实际转发生成请求（含重试）；独立评分15分钟 |
| 单次探针 | 2分钟、最多12次生成请求 |
| 绝对截止 | 确认后开始实施时固定18小时，含实现、准备、试跑、正式与恢复；最后30分钟留报告 |

沿用预先轮换的三方顺序，模型任务串行执行。每次和每组启动前检查能否容纳最坏执行/评分窗口；不足则停止，不延长截止。每个阶段只有前置检查通过才进入下一阶段。

已知且经过验证的上游限流在产品有界重试耗尽后，可按冻结规则进入一次整组三方恢复。鉴权失败、未知协议、证据损坏、隔离或权限异常直接停止。C7或开发题环境中断不单独重抽。仅评分设施故障仍允许一次批次级离线修复与统一重评，原执行profile、断言和评分语义必须保持。

正式期间新发现的边界单列为补充诊断，统一检查可比产物，保留冻结机判；不得静默改验收或忽略已确认的契约缺陷。

## 6. 发布判定与交付

以下全部满足才建议将当前候选标记为v1验收通过：

- 当前版本的文件、权限、中断、日志与协议确定性检查通过。
- 当前版本两次C7已知回归和六次新题均完整交付。
- 代码、有效新增回归、文档和实际验证报告均通过复核；无未解决的保护、协议回退或已确认契约缺陷。
- 完整可观察Trace、文件/Git快照、评分版本和校验清单齐全；正式比较仅采用完整三方组。

时间、token和确认次数用于解释行为，不要求超过Claude Code。新版本不能借旧版本的成功样本凑足门槛。一次有上限的正式轮仍可能失败；失败后交付原因和证据，不自动追加新轮。

最终交付包括产品修复commit、确定性验证、开发试跑记录、正式报告、完整私有Trace和发布建议。每个阶段继续commit、push并核对远端。满足门槛后再按明确范围办理合并或版本发布，不将本方案的讨论视为已发布。
