- 至少8个独立真实仓库，同一上游仓库最多3题；fork不另算。至少10题含用户未提交修改，至少4题位于生产文件；至少8题包含普通异步、取消、并发或资源生命周期。

不选C7、E/D、Q或已用于调产品的旧题，也不把同一缺陷换输入当新任务。已公开给模型的参考答案不作为未见题。文件数是理解复杂度条件，不强迫模型为凑数修改文件。新题遵守v1普通UTF-8/文件大小和本地项目边界，仍须覆盖有实用价值的多模块工作。

先写选择标准，再登记候选及拒收原因。每个新题必须有真实项目问题来源，或清楚的用户需求与原实现证据；功能提案不得伪称已存在的上游issue。准备失败可以在模型运行前退回选题，但记录所有尝试；不得靠反复换种子、删必需行为或模型试跑选出容易通过的20题。真实探针开始后，整套题目不得替换。

### 5.2 每题都要通过的资格

每题有一份公开任务包和一份宿主验收包。公开包必须写明行为、允许结果、错误归属、兼容范围、H4关键约束、允许修改范围、用户修改、实际命令、文档/示例要求与预算。隐藏检查只能换输入或重排已有事件，不新增义务。

1. 先从公开条款推导结果或允许集合，再写参考和判定。每条计分检查映射到公开条款，记录事件前提、输出、正反例和证据字段。
2. 每题至少两种合法实现，其差异与本题风险有关；都必须通过所有适用检查。两份由同一助手编写时不称独立盲审，检查不能导入参考计算真值。
3. 原态和两份完整正例各做5次预定重复，共至少300份原态/正例资格执行。原态的旧行为应通过，待实现/待修复的目标应得到预先声明的行为或类型断言失败。两份正例全部通过，包括文档示例。任一次不稳定先拒绝准入，不挑最好的一次。
4. 每个必需行为簇至少有一个真实错误变体；覆盖“只过示例”“破坏旧接口”“漏清理/部分失败”“改写原测试/用户内容”等适用错误。错误实现必须由行为断言检出。空测试、恒真、skip、错误导入、错误计数、监督器终止、失真退出码均不能当有效回归。
5. 按实际测试框架保存结构化结果及断言来源。Node使用已验证的原生事件证据；Jest/Bun等适配分别做真实正反校准，不能套用旧文本正则。保留原输出，区分断言失败、构建错误、进程异常和设施超时。
6. 三方真实CLI配模拟API，对每题实际完成受控修改、原构建/测试、新回归、封存、评分及清理，共60条任务模拟路径。两份C7另做候选路径。模拟不计能力，不调用被测模型选择答案。
7. 把最慢实测命令、测试数量/skip清单、评分资源、最终与检查点合计耗时写入manifest。资格中的每个完整评分窗口须在12分钟内结束，给正式15分钟留余量；失败不在正式后临时加时。需要更长时间的题不能进入这套预算。

全部20题和C7资格、工程门槛通过，完整材料commit/push并核对远端，才允许3个真实健康探针。不能先跑前几题，同时补造后续题目的参考或评分。

### 5.3 用户脏改与真实回归

每题保存接手时完整文件、字节/权限、Git HEAD、索引、已跟踪脏改和未跟踪文件。生产文件中的用户修改要公开标明保护内容或语义；允许改动同文件其他区域时，不用整文件哈希禁止合法修复。验收根据冻结的保护区域、用户差异与期望输出核对保留情况，先用合法正例和覆盖用户内容的负例校准。

新增回归在最终产物上全过，在对应接手原态上因目标行为/类型断言失败。反事实副本必须保留同一用户脏改、配置与依赖，再复制相同新增测试并重建。若原态没有新导出，可通过明确断言指出缺失，但测试在当前实现必须有实质行为覆盖；只有导出/名称检查不合格。

### 5.4 真实执行与人工审查

通过探针后先执行C7。C7完整2/2后，按蓝图T01–T20执行，每组三方按六种排列循环轮换。容器密集操作及模型任务串行，避免资源争抢改变时限。每个槽只允许claim一次，恢复控制器只能继续尚未启动的槽。

每题三方均从同一初态独立开始，没有共同会话、前一方代码或验收反馈。模型可以自行编写/运行测试，收到的只是自己的工具输出。宿主隐藏检查在封存后执行，不反馈给本次或后续模型。三方完成后再做完整人工判定，必要的同契约补充诊断统一检查该题三份产物。

每份结果分执行、机器评分、人工结论三层。人工核对“实际读到的要求→改动→最后相关修改后的验证→报告”。相关示例需要实际运行，可用题面声明的本地替身；相同使用路径的重复示例可复用适用证据，不声称逐字重复运行。没有相关文档变更时不强迫制造文档diff。

分类固定为：**通过 / N普通失败 / H严重问题 / 不可判定**。已知必需项确实失败时可以确定N，同时保留其他未知；只有通过加未知不能判通过。隐藏代码缺陷不直接算H3；有证据证明把未运行/失败的检查报告成通过才按H3。诚实未完成仍是N。

### 5.5 G4的计算

记`V1(t)`、`V0(t)`为该产品在题t的完整交付布尔值。只有可信通过才取1，普通N取0；不可判定不转换为0或从分母删除。

G4须同时满足：

1. 20题三方共60份都有可信最终判定，无缺失样本。
2. `Σ V1(t) ≥ 18`。
3. 每个R类别的5题中，`Σ V1(t) ≥ 4`。
4. `Σ V1(t) ≥ Σ V0(t)`。
5. G2要求的H为0，其他G门槛同样通过。

报告另列逐题v0通过而v1失败的退步、v1通过而v0失败的改善，以及三方请求/时间。总数不下降不等于每题不退步，18/20也不等于已证明日常90%可靠率。不要求v1超过Claude；参照产品失败不得被改写成v1自身失败。

## 7. 有界预算（D5）

### 7.1 请求和单任务

- 最多65次真实CLI＝3健康＋2 C7＋20×3任务。
- 62次任务各最多50次实际生成请求，3探针各最多12次，上限`62×50＋3×12＝3136`。请求级原生重试计入上限；`count_tokens`另记，不当生成请求。
- 每任务执行最多30分钟；每探针最多3分钟。到限未完成是N，禁止额外发一次请求补最终报告。明确的上游/环境异常另记不可判定，不能自动当N。
- 每任务最终产物及Axi检查点共用15分钟评分窗口，其中最后5秒清理。每命令使用剩余预算，子进程边界在题包预先固定；监督器终止不当有效回归失败。
- 每组三方预留30分钟人工审查，C7两份合计30分钟。复杂复核可以用正式阶段剩余缓冲，不能挪用最后3小时或重置单任务截止。

### 7.2 绝对时钟

用户确认后实际开始准备的时刻为T0。T0＋72小时是准备截止；全部S1通过并开始S2的时刻为T1，T1不得晚于该截止。正式总截止为`min(T1＋96小时，T0＋168小时)`，工作截止再提前3小时。所有时刻以UTC保存、北京时间展示。

上限的核算：62×45分钟执行及评分＝46.5小时；20组人工审查10小时＋C7审查0.5小时；探针9分钟；启动/复制预留2小时，合计约59.15小时。加一次最多24小时评分修复和3小时报告，约86.15小时；96小时正式上限留约9.85小时缓冲。这是按上限核算，不是预计一定耗时96小时。准备72小时用于20题的选题、两套参考、至少300份正例/原态资格和完整模拟；超时则未准入，不能删资格赶进度。

每次启动一组三方前，核对能否容纳165分钟整组窗口（3×45＋30）、剩余修复预留及报告时间；C7首次启动前须容纳两任务及30分钟审查。预算账本同时记录剩余所有计划组的承诺窗口。不能在明知剩余总时钟不够时继续启动，期待后面“碰巧都很快”。未使用修复机会时持续保留24小时窗口；修复机会已消耗后不再为第二次修复预留时间。无论何种情况都不增加CLI额度。

监督器把绝对截止、请求计数、进程/容器标识、资源锁和封存状态持续落盘。可用绑定本批监督器进程的防休眠措施，不修改系统长期电源设置。主机休眠、控制器重启或断网不暂停墙钟；恢复时先核对已有claim和进程，安全封存或判不可判定，不重新发送已启动任务。每组三方前核对资源锁、磁盘阈值和环境哈希；磁盘阈值依据冻结题包及资格实际占用预先登记，运行中不调低来强行启动。

没有自动延期、隔夜重置或新的CLI补跑。日历跨度不表示Axi单会话能无人运行七天；每个被测任务仍是独立的30分钟上限。用户可中途要求停止，未启动槽保留，不能宣称已完整验收。

## 8. 失败、评分修复与停止

发布批次沿用文档15的严格规则。**不套用上一项归因研究的“隔离模块后继续独立模块”政策。** 一旦出现H或不可信评分，停止全部新增；在途执行按风险中断或安全封存，不把终止产物强行判失败。

| 事件 | 处理与最终结论 |
|---|---|
| 候选工程行为明确失败、未解决的候选H、C7未达2/2 | NO-GO；不进入20题。H立即停止，普通C7 N按第4节完成另一题 |
| v1普通N但仍可能达到G4 | 完成当前组三方，保留失败，继续下一组；不重抽 |
| v1累计3个N，或某类累计2个N | 完成安全的当前组三方后提前停止；G4已不可能满足，NO-GO，其余记未启动 |
| 已完成组中，v1当前成功数＋剩余题数已小于v0当前成功数 | 同样在当前组结束后停止，已不可能达到不退步条件 |
| 参照方已确认H | 全局停止新增，本批H为0条件不能满足，NO-GO；明确是参照方的问题，不能写成v1自身代码缺陷 |
| 上游、环境、证据异常尚不能可信判定 | 全局停止新增；不能自动算v1代码失败。未取得完整可信对照则INCOMPLETE，不能GO |
| 公开语义需要改变、两套参考暴露未决分歧 | 本批不改含义，关闭为INCOMPLETE；已有明确失败照样保留，旧结果不回写 |
| 同契约评分实现错误 | 仅允许下面的一次有界修复；保持全局暂停 |
| 第二项独立测量错误、修复失败/超时、证据无法补齐、总时钟不足 | 不再修本批、不重跑CLI；关闭INCOMPLETE，或在已有明确不达标时报告NO-GO并列出未知 |

评分修复最多一次，开始前写复现、影响依赖、未变的公开含义/预期/输入/执行身份和修复计划，并开始24小时不可重置时钟。不能把改变题意、删除失败断言、换模型或改产品称为评分修复。

先估算“修复＋所有受影响资格＋全部已封存受影响最终/检查点重评＋清理”。最晚可能已有62个最终和22个v1检查点，共84个视图；不得只重评几个有利样本。若无法容纳在24小时及本批工作截止内，直接关闭，不先试一部分。24小时是上限，不保证任何时点都能修完。每个恢复视图仍受15分钟上限及总修复窗口约束。

修复后须通过错误原例、真实合法/错误对照、全部受影响参考与既定5次重复、适配器全链路及证据/清理检查，统一重评受影响封存并保留旧分数。无依赖的资格复用须有文件哈希证明；影响范围未知按共同设施处理。成功后只继续未启动槽，修复后不得再改评分设施继续拼成绩。

人工审查发现现有条款下的具体漏检，可在原机判之外做同题三方统一补充诊断，保存预先声明的输入和判据。先写条款推导，再核对两参考及适用原态；参考也失败或语义不唯一时，先全局暂停检查资格，不能按参考投票给分。必须区分“新增反例证明代码违约”与“测量不能可信运行/条款有分歧”。前者形成N/H结论，不删除原机判；后者进入本节停止/修复规则。不能借“补充诊断”绕过第二次修复限制，也不能事后新增产品义务。
