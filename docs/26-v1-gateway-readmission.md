# 同一网关恢复与新批次准入

2026-11-19。用户已确认先排查同一网关到冻结模型的 OAuth 鉴权，以一次真实请求核验，再按原门槛启动新批。候选仍为 `280d1f3`。沿用[方案22](22-unbounded-candidate-acceptance-plan.md)与[方案25](25-v1-recovery-health-plan.md)。

1. 比较客户端实际使用的完整请求地址、API key 指纹和模型与 R5 冻结记录。检查已登记的网关管理方式。本机客户端用 API key 调用网关。该 key 和上游报告的 OAuth 访问令牌属于不同的凭据位置。
2. 用同一 Messages 入口、冻结模型和 medium 档发出一个带随机校验文本的流式生成请求。记录原始响应及脱敏回执。仅当 HTTP 成功、实际模型一致、文本匹配、内容块闭合、正常结束且收到 `message_stop` 时通过。真实探测单列，不计入三方能力分数。
3. 探测通过后，以新批次号、授权时钟、独立账本和全新任务工作区开始。逐项核对冻结包、证据来源、题面、评分器和实测容量。健康 3/3 后运行当前 v1 的 C7-L、C7-O。C7 2/2 后按预定题序运行 20 组三方任务。发布要求与停止条件沿用原契约。
4. 若仍收到鉴权错误，保存原始事件，用已授权的网关运维入口定位和修复。需要服务方重新授权时记录具体依赖。网关身份、模型、产品评分和旧批次结论保持冻结。
5. 同时盘点实际的评测根目录。按已冻结的文件引用、Trace 索引及跨批依赖区分运行输入、复核证据和可重建副本。此次盘点只读。

本批的准入复用由用户于 2026-11-19 单独确认：“沿用经复核的 R5 冻结包，直接跑正式健康”。R5 的 308 项材料和 65 条模拟属于 R5。R6 复核来源和哈希，重新检查执行所用的依赖、空间与环境。正式槽只采用 R6 的新运行。
