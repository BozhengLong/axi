# v1 验证报告准确性专项方案

2026-11-18。用户已确认先做专项、再做候选验收的流程。用户已确认 D1–D5 全部按推荐执行，原话为“你先完成专项验证，通过后冻结新候选，继续推进到正式验收结论”。专项已启动。目标是让用户从最终回答看清一项检查经历了什么，最后验证到了什么。

**起点。** C3 修好了 C7-L 的监听器问题，新增回归在原实现上触发了预期断言。交付报告却说只有复制失败。最后一次模型请求已经包含两条工具结果，首行都是外层脚本退出 0，正文分别记录了测试子命令退出 127。现有系统提示和收尾复核都已要求保留检查本身的退出码。本次要验证，在复核时明确关联同一检查的多次尝试，能否减少这类报告错误。依据见[C3 正式结果](verification/2026-11-18-c3-release-result.md)与[第 33 次请求核对](devlog/2026-11-18.md#19-核对-c7-l-最终回答前的模型输入)。

**D1｜交付标准。** 推荐允许按同一检查合并叙述。报告须覆盖影响验证结论的启动失败、预期断言失败、后续成功或仍未验证的部分。例如 C7-L 可写为：“首次复制因空间不足失败。两次 Jest 启动失败后，改用有效入口；新回归在原代码上触发两处预期断言，修复后通过。”无需逐条列出探查命令。声称“全部通过”“只有一次失败”等时，证据须支持该范围。无法判断子命令是否运行时，报告应指出缺少哪项证据。

**D2｜最小改动。** 推荐先在独立开发版本里只改默认自动复核的指令。让 Axi 逐项核对检查对象、实际执行的命令、有效结果和后续尝试，再写最终回答。命令与工具结果一起解读；日志正文里的数字可来自样例或普通文本。沿用一次复核、原工具与权限。若该改动不足，再依据失败样例决定是否需要在工具层采集更明确的状态。实现位置见[C3 复核入口](https://github.com/BozhengLong/axi/blob/e684620d1fa9109fcbcf442033ed97323cf76716/src/agent/review.ts)。

**D3｜配对实验。** 推荐先锁定 6 份输入、每份的事实答案及评分表。用 C3 原版和 D2 版本分别生成报告，每份各做两次，交错顺序，共 24 份。两版使用相同的历史、模型和档位，只替换来自对应产品版本的复核指令。输入截至最终回答前，原最终答案及评分不进入模型上下文。固定历史只检验报告生成，正常复核中的工具选择由 D4 的实际 CLI 检验。历史回放在私有副本执行，只生成报告，不重放历史工具副作用。1 份取自 C7-L，其余 5 份用与 Jest 无关的本地命令生成。

| 输入中的事实 | 合格报告必须说清楚 |
|---|---|
| C7-L 封存历史 | 启动错误、有效的原态对照和修复后的结果，三者均与 Trace 相符 |
| 首次检查成功，样例文字恰好含有 127 | 检查通过；样例数字没有被判成故障 |
| 检查未能启动，外层脚本返回 0；换入口后成功 | 首次未运行检查，后一次实际通过 |
| 新回归在原缺陷上按预期触发断言，修复后通过 | 两次运行针对的代码版本、预期行为与实测结果 |
| 最后一次相关修改后检查仍失败 | 最终失败及具体未通过项；此前成功只适用于此前版本 |
| 外层脚本结束，关键子命令结果缺失 | 哪一项仍未验证；不推测其退出码 |

**D4｜专项放行线。** 推荐逐份隐藏版本标签，按事实评阅，接受等义表述，保留全部回答和首次结果。实验版须达到 12/12。再用两道预先留出的非 Jest 小任务，经正常 Axi CLI 实际执行、复核并交付，分别覆盖“失败后恢复”和“最终仍失败”。两份报告均须与实际 Trace 一致，后者的正确报告应明确说任务未通过。合计 24 份回放、2 次真实 CLI，实验记录与正式成绩分开。若两版回放打平，只报告观察到的结果；若未达到专项线，先解释失败再决定修订范围。专项结果只决定是否值得冻结候选。

**D5｜通往发布的顺序。** 推荐专项通过后，从受测开发版本冻结一个新候选，建立独立账本。按[方案 22](22-unbounded-candidate-acceptance-plan.md)核对新身份、容量和环境，通过新候选工程准入与 65 条模拟。旧材料按依赖哈希和暴露记录审核，复用已证明相同的部分；候选相关及受影响的检查重新执行。先跑三方真实健康探针，再跑两道真实 C7。C7 完整交付 2/2 后才启动 20 题三方对照。发布仍要求 60 份可信结果、v1 至少 18/20、每类至少 4/5、总成功数不低于同批 v0、严重问题为 0，且 G0–G6 全部通过。[发布契约](15-v1-release-contract-v2.md)

确认 D1–D5 后，可连续执行专项、候选冻结、正式验收及闭批，沿用方案 22 的时限、恢复和停止规则。专项与正式尝试各自保留完整可观察 Trace，阶段结果提交并推送。正式通过后再申请发布。
