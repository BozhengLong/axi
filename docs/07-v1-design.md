## 1. 目标与依据

v1 的目标是让用户看清 Axi 正在读什么、准备改什么，并能停止当前工作。自动读取减少重复确认；文件修改保留明确的执行边界。成功标准是操作可控、结果可核查，以及已有任务能力没有回退。

[C7](verification/2026-11-11-c7-comparison.md)中双方各完成 6/6 修复与有效回归。它没有证明 Axi 缺少文件工具会导致任务失败。本方案依据[项目愿景](00-vision.md)中的日常使用目标，不把“增加工具会提高解题成功率”当作已证结论。

### 假设与边界

- 首版服务本机 macOS 开发目录，并在 Linux 隔离容器验证。使用 Bun 1.3.14 建立实现基线；实施前核对安装版本，不顺便升级运行时或模型。
- 用户在希望工作的目录启动 Axi。一个会话只有一个固定项目根目录，取启动 cwd 的真实路径，不自动扩大到 Git 顶层，也不由模型切换。
- 文件工具处理不超过 1 MiB 的普通 UTF-8 文本。支持已有未提交修改；不要求工作区干净，不自动 stash、暂存、提交或重置。
- 文件内容和工具输出都是数据。不会因文件中的文字自动改变授权规则或执行命令。读取的内容会发给模型，并按既有规则进入本地日志。
- 本阶段不提供操作系统沙箱。用户批准的 bash 仍有宿主用户权限；文件工具的路径规则不能约束 bash 的所有效果。
- 外部编辑器可能在确认期间改文件。v1 检测已观察到的版本冲突并拒绝旧修改；不承诺阻止不配合的程序在最终检查之后并发写入。具体保证见第 5 节。

## 3. 用户看到的流程

假设用户要求：“修改配置加载逻辑，保留我已有的修改，再补测试。”

1. Axi 展示当前根目录和权限模式。默认模式下，查找、搜索和读取普通项目文件会执行，并显示简短状态，不弹确认。
2. 模型提出 edit。Axi 校验读取版本和唯一匹配，计算真正要写入的内容，再展示文件路径和差异。
3. 用户输入 y 后，Axi 再校验文件与路径。文件未改变才提交。输入 n 或回车时不写文件，并沿用可选拒绝理由。
4. 模型要求执行测试时，完整 bash 命令照常逐次确认。文件工具自动读取不表示 shell 命令也自动获准。
5. 任务结束时，模型依据实际工具结果报告改动和验证。用户可继续追问。

预览示例（示意界面，不是已实现输出）：

```text
修改文件：src/config.ts
操作：精确替换 1 处
--- 当前文件
+++ 拟写入文件
@@ ...
- 原内容
+ 新内容
应用这次修改？[y/N]
```

预览须覆盖所有改动块，可省略未改变的大段上下文。路径中的换行和 Tab 也要转义成单行文本；正文保留正常换行，其他控制字符和双向文本控制符使用可见转义，不能覆盖确认提示。超过预览上限时不提供隐藏内容的确认；要求拆小修改。

首版提供 `/permissions` 查看模式，`/permissions project` 使用默认规则，`/permissions strict` 让原本自动的读取也逐次确认。只能在等待用户输入时切换，从下一轮生效；不保存到磁盘。模型不能通过工具参数、文件内容或自身消息修改模式。硬性路径拒绝在两种模式下都有效。

这是待确认的 v1 文件工具规则。v0/D3 已确认的 bash 逐次授权继续保留；当前运行中的 v0 不会因提交本文而改变默认行为。

用户拒绝某项操作后，拒绝理由继续进入工具结果。模型不得改用 bash 或换一种文件工具绕过拒绝。权限系统不宣称能理解任意命令与自然语言限制的全部等价关系；自动验收同时检查实际文件结果与报告。

## 4. 工具与路径契约

### 4.1 工具最小接口

名称和字段为拟定接口。所有输入严格校验类型、范围和额外字段；完整模型消息到达后才执行。所有工具继续按响应中的顺序执行。

| 工具 | 拟定输入 | 成功结果与约束 |
|---|---|---|
| read | path；offset=1；limit=200 | 原文 content、起止行号、完整文件版本、next_offset/truncated；limit 最大 2,000 行，原文最多 30,000 个 Unicode 码点 |
| glob | pattern；path="." | 在 path 下按相对路径匹配；排序后的文件列表、是否完整、排除规则与停止原因；最多 200 条 |
| grep | pattern；path="."；可选 glob | 对普通文本逐行做区分大小写的字面量搜索；返回路径、行号、匹配行；最多 200 条、30,000 码点；不能把正则表达式当作字面量以外的语法 |
| write | path；content | 只创建不存在的新文件；父目录须已存在；成功返回新版本和创建事实。目标存在即拒绝，不先清空文件 |
| edit | path；base_version；old_text；new_text | 已有文件必须有本会话的有效读取版本；old_text 非空，在当前文件恰好匹配一次；允许 new_text 为空；保持未匹配字节 |
| bash | 沿用 command、timeout_ms | 新 shell、固定 cwd、关闭 stdin、逐次确认、现有超时和输出截断规则保持 |

read 的终端展示带行号，但返回给模型的原文与行号元数据分开，不重复返回一份带行号的正文，避免模型把行号写回文件。版本基于完整文件，不因只读其中一页而仅校验该页。分页可能拿到不同版本；一旦版本变了，模型须重新取得所需上下文，不能假设多页属于同一快照。取消的读取不授予编辑版本。

edit 不自动 trim、换行归一化、模糊匹配或合并。LF/CRLF、UTF-8 BOM 与末尾换行按原始内容保留。相同旧文本出现零次或多次（包括重叠匹配）都返回错误；需要更多上下文后重新提出。无需单独新增 append 工具，可用包含唯一末尾上下文的 edit。空文件可读取，但首版 edit 不接受空 old_text；对已有空文件的填充使用经确认的 bash，不借 write 覆盖。

工具结果保留既有 tool_result 协议。新增文件工具的 content 承载可解析的结构化数据，字段至少包括 status、code、path、operation、modified、truncated。版本、行号等按工具补充；参数错误、拒绝、冲突和取消使用明确错误码，不把所有情况混成“失败”。bash 保留原有结果正文，统一元数据放在内部结果与日志中；无法确定的文件副作用标为 unknown，不能填 false。模型无须计算或理解版本摘要，只能引用工具返回的 base_version。

### 4.2 路径与搜索范围

| 情况 | 文件工具行为 | 理由 |
|---|---|---|
| 根目录内普通文件 | 按 D2 处理 | 工具路径相对固定根目录解释，不受之前 bash 中 cd 影响 |
| 绝对路径 | 仅在规范化后仍位于根目录内时接受 | 判断路径组件，不使用简单字符串前缀；拒绝 NUL、URL 和含 .. 组件的路径 |
| 符号链接、特殊文件 | 不读取、不遍历、不修改；父路径中的符号链接也拒绝 | 首版缩小边界；启动 cwd 只在建立根目录时解析一次，之后核对根身份 |
| 多硬链接文件 | 文件工具拒绝 | 防止读写范围被共享 inode 模糊化；新文件发布期间自身临时链接例外，仅内部使用 |
| 任意层级 .git、.axi，及 Axi 自有临时文件 | 文件工具硬拒绝 | 不把 Git/会话内部状态当作普通项目内容 |
| .env、.env.*、.envrc；.ssh/.aws/.gnupg 下文件；id_rsa、id_ed25519、credentials.json、*.pem、*.key | 不自动读取或展示内容，首版文件工具硬拒绝 | 包括示例文件；规则按路径名识别，不保证发现任意名称下的秘密。必要的特殊操作另用人工检查后的 bash |
| 扫描遇到 node_modules、dist、build、coverage、.next、target、.venv、__pycache__ | glob/grep 默认不进入；明确路径的 read 仍可访问其中普通文件 | 控制扫描成本；这是搜索排除，不是读取权限 |

全部路径规则同时约束 read、write、edit，以及 glob/grep 的候选文件。保留名称、凭据名称与后缀按不区分 ASCII 大小写检查，不能用 .GIT 或 .ENV 绕过。被拒绝路径不因 strict 模式确认而放行。根目录、父目录或目标的身份在等待确认期间变化时，放弃原提案；不跟随新的链接或新目标。

glob/grep 使用同一受控遍历器，并显示实际根目录和排除清单。首版不完整解释 .gitignore，不能声称“搜遍仓库”或“没有匹配所以代码不存在”。遇到排除、无权限、二进制、超限或取消时，返回跳过数量与原因。搜索零结果本身是成功，不等于执行失败。

### 4.3 首版资源上限

以下是建议的工程参数，不是已经量测的最佳值。实现时先按此校准；调整必须记录，不得在正式比较中只对某一方放宽。

- 文本读写单文件最多 1 MiB，使用严格 UTF-8 解码；遇到 NUL 或非法编码时不替换成乱码再写回。读取期间增长也受字节上限约束。
- read 最多返回 30,000 码点，按完整行分页。单行本身超过上限时返回“该行过长”，不把半行作为完整可编辑内容。
- glob/grep 每次最多检查 20,000 个目录项；grep 累计最多读 32 MiB；扫描预算 5 秒。到限即停，标记 incomplete 和具体原因，提示缩小路径或模式。
- 写入差异预览最多 30,000 码点；不能在被截断的差异上接受 y。较大的合法修改拆成多次明确确认。
- 读取版本记录只在本会话内有效，最多保留 1,000 个文件的最新版本。被淘汰或过期后必须重新 read。grep、glob 的结果不授予编辑版本。

## 5. 修改、冲突与提交

“提案”是一份不可变的拟修改记录，包含工具调用 ID、规范路径、旧版本、原字节/新字节摘要、实际差异及预期模式。确认只授权这一份提案。

流程为：参数及路径校验 → 读取当前状态 → 校验版本/匹配 → 生成完整差异 → 等待确认 → 重新校验 → 提交 → 读取确认结果并记录。校验失败不弹可执行确认，也不写目标文件。

### 已有文件 edit

1. base_version 必须来自本会话同一路径的 read 或已成功修改结果。Axi 保存内容摘要、文件身份和模式，不信任模型自报的哈希。
2. 提案产生时和用户确认后，核对内容、身份、模式与路径。用户已有未暂存修改就是读取基线，不能用 HEAD 替代它。
3. 内容匹配不唯一、读取后发生变化、确认期间发生变化，均返回 stale_version/ambiguous_match 等错误。旧 y 不复用；重新读取、重新计算差异、重新确认。
4. 在同目录创建独占临时文件，写完并校验新字节，保留原文件普通权限位与可执行位，再替换目标。失败不退回直接截断原文件的写法。普通写入不改变 Git 索引。
5. 同一 Axi 会话中的提交串行执行。首版承诺内容和普通权限位，不承诺保留 inode、所有 ACL 或扩展属性；有这些要求的文件不在 native edit 的支持范围。

### 新文件 write

只创建，不能覆盖。先准备同目录临时文件，再用“目标存在则失败”的发布操作放到目标路径。实现候选是同文件系统的独占链接发布后移除临时名；须在 macOS/Linux 验证，不得用先 exists 检查、再普通 rename 覆盖代替。新文件使用普通非可执行权限（0644 再受 umask 约束）。父目录不存在时返回错误，不隐式创建一串目录。

### 并发保证的准确范围

原子替换只保证读者不看到半份内容；它不等于“检查版本并有条件替换”的原子操作。外部程序可能在最终版本检查后、替换前再次写入。v1 没有跨所有编辑器的强制锁，因此不承诺无条件防止并发覆盖；同一文件同时由多个 agent/编辑器持续写入不属于支持场景。

这不会削弱确认期间冲突的拒绝规则。自动场景要在确定时点改文件，并验证旧提案确实被拒绝。若产品要求最后一个竞争窗口也必须消除，需要另行设计隔离工作副本或协作锁，不能把补一次 hash 检查当成问题已解决。

同样，路径检查与重新检查可以拒绝已观察到的链接替换，但不是抗恶意并发文件系统攻击的沙箱。Node 官方文档明确说明分离的存在性检查与打开操作存在竞争窗口，rename 又会覆盖已存在的目标；这些语义决定了上述限制。[文件系统检查与竞争条件](https://nodejs.org/api/fs.html#fsaccesspath-mode-callback)、[rename 行为](https://nodejs.org/api/fs.html#fsrenameoldpath-newpath-callback)。

## 6. Ctrl+C 与实际副作用

保留 v0 的 AbortSignal 传递、请求退避取消及同进程组清理。在新增工具的各个阶段检查取消；扫描须定期让出执行权，不能因同步扫描而一直收不到 Ctrl+C。

| 中断时点 | 工具与文件行为 | 用户看到的状态 |
|---|---|---|
| 输入、模型请求或重试等待 | 停止本轮；未完成 assistant 响应不入历史 | 已停止，等待下一次输入 |
| read/glob/grep 执行中 | 停止后续读/扫描；已有部分结果带 incomplete，不报告完整零匹配 | 已取消读取/搜索 |
| 提案或确认等待 | 不提交；不执行本条消息后续调用；清除残留输入 | 此次修改未应用 |
| 临时文件准备中，尚未发布 | 清理本调用拥有的临时文件，不动目标 | 此次修改未应用；清理失败单列 |
| 已进入最终提交步骤 | 完成这一次短提交及状态确认，再停止；不启动下一项 | 按实际结果说明已应用或未应用，不能统一写成“未执行” |
| 已完成若干次修改后 | 保留已完成修改，未开始调用补取消结果 | 显示已修改文件与剩余未执行数 |
| bash 执行中 | 沿用同进程组终止；保留部分输出和退出信息 | 已停止命令，已发生的文件修改未自动撤销 |

不新增双击 Ctrl+C 强退或自动回滚。普通 Ctrl+C 返回输入框，不自动再调用模型“总结取消”；本地根据工具结果显示状态。用户之后输入“继续”才启动下一轮。

完整 assistant 消息中的每个 tool_use 都必须有一个 tool_result。同一批次前面已成功的结果不能被后续取消改成失败；未开始项明确标记 cancelled_not_started。最终提交已成功但随后收到取消时，结果仍为 applied，另记取消请求。

进程崩溃、外部 SIGKILL、断电与正常 Ctrl+C 分开。首版不做崩溃恢复或跨进程会话恢复。提交后无法确定状态时停止本轮并报告 unknown；不得自动重放可能已经生效的写操作。

## 7. 实现结构与记录

保持 Bun + TypeScript、手写 HTTP/SSE、无官方 SDK、无 agent 框架、历史只追加。模型、effort、重试次数和 bash 默认超时不因 v1 顺便调整。

| 拟改位置 | 职责 |
|---|---|
| src/tools/registry.ts | schema、严格参数解析、效果类别与执行入口统一登记；拒绝未知工具 |
| src/tools/files.ts、paths.ts、search.ts | 文件版本、精确编辑、提交、路径约束与有界搜索；不处理终端输入 |
| src/ui/permission.ts、terminal.ts | 模式、只针对已准备提案的差异展示与确认；保留输入清理和可见转义 |
| src/agent/loop.ts | 通用工具分派、串行执行、结果补齐、取消与实际写入状态；不放文件匹配细节 |
| src/api/client.ts | 从注册表生成 tools；重试仍使用同一请求快照 |
| src/main.ts、log.ts | 用户模式命令与清晰状态；关联提案、权限、提交结果和日志失败 |

上述新路径尚未创建。实施时按行为切分提交，避免改变现有协议。差异计算只要求真实、完整和有界，不要求产生最短补丁；单处替换可展示完整变化区间。计算或展示超限时拒绝本次提案，不引入无上限的差异算法或省略后批准。

建议使用 Bun.Glob 的 match 做路径模式匹配，目录枚举由受控遍历器负责。官方文档列有匹配和符号链接选项，但当前网页不是固定 Bun 1.3.14 的版本证明；实施前用固定版本做兼容检查。[Bun Glob](https://bun.sh/docs/runtime/glob)。文件描述符、lstat、临时文件和发布操作可以使用 Bun 的 node:fs 兼容 API，不引入 Node 运行时或 Node 专属工具链。[Bun 文件 I/O](https://bun.sh/docs/runtime/file-io)。两份资料查阅日期为 2026-11-12。

在既有本地日志新增或补齐以下关联事件：tool_start/end、permission_request/decision、proposal、commit_result、cancel_requested。记录 session/turn/tool_use_id、工具类型、路径、授权来源（自动规则或本次输入）、预览摘要、前后版本、实际副作用、截断原因和耗时。字段随日志版本登记，不破坏旧 Trace 的解释方式。

自动放行也留记录，不能等同于用户输入过 y。已有原始请求/响应可能含文件内容；日志保持私有权限与忽略规则，不写认证头、不自动上传。记录 API 返回的摘要，不声称取得服务端未返回的内部推理。

提交前的必要日志写入失败时不提交。提交后的日志失败不能改写“文件已应用”的实际事实；停止后续模型调用并提示检查现场，不自动重做写入。日志与文件更新不是同一个事务，不能承诺崩溃时二者始终同时落盘。

### 9.3 运行范围与预算

|---|---|

### 9.4 评测适配与指标

旧 Axi 保留原适配器；新 Axi 使用能够关联文件提案、差异和权限的适配器。先用真实 CLI 配模拟 API 验证 read 自动执行、修改拒绝/批准、冲突和取消；不能为了方便评测给产品新增秘密的“全部允许”模式。

控制器只在核对完整工具参数、当前预览和调用身份后代替用户输入。仅在隔离容器内按冻结策略批准；真实使用的权限规则仍保留。需要确认的次数按**实际出现的确认界面**计数；自动规则放行单列。评测中的自动输入不冒充真实用户等待时间或主观体验。

| 指标 | 定义与判断 |
|---|---|
| 完整交付 | 原/新增测试、公开契约、保护项及报告真实性；沿用代码修复和完整交付分列 |
| 控制正确性 | 未授权写入、错文件、过期覆盖、取消后错误继续等确定性场景；任何违反均不得标记 v1 验收完成 |
| 确认次数 | 每个正式任务中需人工决定的调用数；同时报告 bash 比例与自动读取数，不把少执行任务造成的少确认算改善 |
| 机制效果 | 用同一固定读取/搜索流程证明 project 模式无需确认、strict 模式仍逐次确认；另列模型是否实际采用新工具 |
| 时间与用量 | 活动时间、墙钟、生成请求、API 返回 token/重试；只作本批观察，不由此给总体排名 |
| 证据完整性 | 输入、工具、权限、终端、原生日志、快照、验收及 SHA-256；缺失另列不可判定 |

建议 v1 交付门槛：全部确定性场景通过；新 Axi 的 2 次 C7 回归和 6 次新任务均完整交付；没有未解决的保护或协议回退。旧 Axi/Claude 结果如实保留，不要求新 Axi 必须超过 Claude 才能交付。普通候选失败可继续剩余原计划，但不能临场改实现；报告后再定位，不自动增加重复直到成功。需要新一轮时提交结果和后续计划。

同题比较评估的是整套 v1 行为，不能仅靠胜负将收益归因于 read、edit 或权限中的某一个变化。用户手动试用为可选反馈，不是自动验收的前置要求。
