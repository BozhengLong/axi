# C6：真实仓库中的连续任务对照

> 日期：2026-11-11。状态：C6/D1–D4 已确认并执行完成。结果见[对照报告](verification/2026-11-11-c6-comparison.md)；实施差异见第 11 节。本文的 D 编号使用前缀 `C6/`，不改变此前已经确认的 EVAL 和 COMPLEX 决策。正文保留设计交付时点的描述。

## 1. 目标与判断边界

本阶段要回答：Axi 和 Claude Code 能否在一个真实仓库中，连续完成新功能、验收反馈和需求变更，同时保留旧行为及用户已有修改？

“连续”指同一 CLI 进程、同一会话历史、同一工作目录。每轮交付后保存证据，再给下一轮输入。退出重启、重新给完整题面，不算本设计的连续任务。

此前 C1/C2/C4 的冻结验收双方各 9/9，事后补充边界复验双方各 7/9。它们不能证明陌生大型仓库或长时间连续工作的能力。依据见[复杂任务报告](verification/2026-11-11-complex-comparison.md)。本次增加真实依赖关系和跨轮约束，不靠故意含糊的题面、无意义代码量或要求双方出现不同分数来增加难度。

**假设：** 真实项目的新公开接口、原测试和后续调用者变化，能暴露单轮小任务没有覆盖的集成问题。这是假设，需由本次执行验证。只做一个项目、每方三次，仍不能给两个产品作总体排名。

用户本次“好的，去做吧”承接的是先提交 C6 设计及验收清单。本轮完成可审阅方案；具体目标项目、运行范围和预算列在第 10 节，尚未记录为确认。

## 3. 三轮任务

| 轮次 | Agent 获得的输入 | 要交付什么 | 独立记录什么 |
|---|---|---|---|
| R1 | 完整仓库、当前契约、原测试、明确的已有修改清单 | 新增公开 `jsonl` renderer、类型、文档、测试和可运行调用示例 | 首次交付是否正确；是否保留原行为与用户文件 |
| R2 | R1 的固定格式、真实可见验收结果 | 修复发现的问题，确认回归范围 | 有反馈时能否修复；是否引入新失败 |
| R3 | 新增输出过滤及文本转换要求；控制器模拟的用户策略修改 | 扩展接口，并让调用示例使用用户的新策略 | 新需求、所有旧契约、用户修改是否同时成立 |

JSONL 指每行一个完整 JSON 对象。R1 的详细公开契约见[接口契约](../evals/specs/c6-real-v1/contract-r1.md)。核心要求包括稳定字段、运行与任务身份、嵌套任务、实例隔离、结束清理，以及输出回调抛错时不改变业务结果。最后一项吸收了 C1 事后发现的错误分类教训，**从 R1 就公开**，不是后来追加的秘密要求。

投递文本分别见 [R1](../evals/specs/c6-real-v1/round-1.md)、[R2](../evals/specs/c6-real-v1/round-2.md)、[R3](../evals/specs/c6-real-v1/round-3.md)。本目录和本设计留在控制器侧。候选容器每轮只收到当时已公布的文件，Git 历史中也不能出现未来题面、用户补丁、参考实现和隐藏输入。

R2 不增加需求。冻结的可见检查失败时，提供预期、实际结果、复现命令和原始输出；全部通过时，明确写“可见检查通过”，请求确认回归范围。不能假造失败，也不能把隐藏检查通过与否混入反馈。双方反馈模板、检查集合、顺序和详细程度相同；实际结果自然可以不同。

R3 的新契约不追溯判定 R1/R2。没有修复反馈的样本，反馈修复率标为不适用，不算一次修复成功。

## 4. 如何检验保留用户修改

建立相同的 Git 起点：上游提交 → 评测所需公开材料和调用示例基线。随后叠加两份明确告知 agent 的用户修改：

- `examples/c6-consumer/policy.ts`：已跟踪但未提交的修改，导出 `formatText(text: string): string`。
- `examples/c6-consumer/notes.md`：用户新增、未跟踪的说明文件。

两份文件对候选都受保护，其初始字节、权限、Git diff 和未跟踪状态进入清单。调用示例 `run.ts` 可以修改；上游源码可以按任务修改。保护清单同时列出原测试、原快照、锁文件、构建和测试配置及许可证。允许新增测试，不允许削弱旧检查。

policy 的 Git 基线、v1/v2 内容与 notes 原文已列入[固定用户修改](../evals/specs/c6-real-v1/user-changes.md)。v1 包含现有团队标记替换规则，v2 在保留该规则的基础上增加 token 替换。准备时仅把对应轮次内容投递给候选。

在 R2 交付之后、R3 开始之前，控制器先检查 policy 与 notes 仍符合已知哈希。然后在 agent 暂停期间，对 policy 应用预先冻结、双方相同的 v1→v2 用户补丁，保存修改前后字节与哈希。v2 的示例规则为把 `token=demo-secret` 中的值替换为 `[REDACTED]`，只使用合成数据。具体规则由提供的函数负责，候选只负责接入，不自行复制规则。

R3 明确告知这次用户修改、文件路径和新保护基线。`run.ts` 需要通过新接口调用 `formatText`。独立验收在副本中替换为同签名的另一策略，检验调用者是否真正使用策略，而不是硬编码样例字符串。

控制器不重置候选代码。若受保护文件已被改坏，该项记失败；保留现场并结束该轨迹，不能把破坏后的文件当作新用户基线继续。此前轮次的结果仍保留。保护按每次交付快照检查，Trace 中可观察到的中间改写另外记录；不能声称快照证明运行期间从未写过该文件。

## 5. 环境与连续会话控制

### 5.1 隔离、版本与依赖

- 每条轨迹使用独立容器、HOME、工作卷和网络。双方获得相同 Git 起点、用户修改和预装依赖。不同重复之间不共享会话、自动记忆或候选文件。
- Axi 和控制器仍用 Bun。**仅目标仓库**保留 Node/pnpm/Jest 工具链。拟用上游 CI 已覆盖的 Node 24 系列；搭建时固定具体补丁版本、pnpm 版本、镜像 digest、锁文件及依赖清单。正式 manifest 不得出现可漂移的 `latest`。
- 依赖只在可信镜像准备阶段安装，使用冻结锁文件。候选运行不能安装包或访问公网；只允许现有模型转发通道。验收容器不访问模型或公网。真实 key 留在转发服务，不给候选。
- pnpm 依赖目录只读，保留其相对 workspace 链接。必须证明 `listr2` 导入的是候选修改后构建的 `/task/packages/listr2/dist`，而非镜像内未修改的种子。用路径检查和哨兵改动验证。
- 工作卷取代旧的 200 MB `/task` tmpfs。预检测量依赖、构建和证据空间，设置双方相同的磁盘限额。初始资源为 2 CPU、4 GiB 内存；基线不足则在试跑前整体修订，不能只给某一方放宽。
- 不挂载宿主 Axi 仓库、用户 HOME、Docker socket 或其他项目。公共报告不包含原始会话凭据。

### 5.2 每轮交付的稳定快照

现有[适配器](../scripts/eval/adapters.ts)接收静态 `prompts` 数组；`onTurn` 不能直接生成下一条反馈。现有[冻结函数](../scripts/eval/core.ts)终止任务进程，不能用于需要继续同一 CLI 的轮间交接。C6 需要新增以下流程：

1. 检测本轮实际结束，并确认模型请求、工具调用均已完成。不能把工具成功后模型请求失败误判为交付成功。
2. 暂停整台候选容器，停止本轮活动计时。保持 CLI 进程、标准输入连接和会话历史。
3. 可信辅助容器只读挂载该轨迹工作卷，导出稳定快照。独立验收在另一份副本运行，不向候选工作目录写测试或结果。
4. 生成固定格式反馈。进入 R3 时，可信辅助容器仅对指定用户文件应用冻结补丁，并核对修改前后哈希。
5. 恢复容器，投递下一轮输入，开始新轮计时。

正式运行前，用真实双方 CLI 和模拟模型验证“暂停—快照—反馈—恢复”三轮完整闭环。必须证明历史延续、PTY/流连接存活、暂停期间候选不能写文件，以及快照和补丁不丢候选修改。若当前 Docker 环境不支持这个闭环，暂停实施并修订方案；不能用重启新会话冒充连续运行。

快照保留二进制字节、可执行权限和合法仓库内符号链接。依赖链接单独按冻结清单验证；拒绝越界链接和特殊设备文件。不得继续用“全文件按 0644 恢复”的方式重建此真实仓库。归档不重复复制整个 node_modules，但记录依赖版本、镜像与挂载清单。

### 5.3 完成、失败与预算

普通断言失败后，只要 CLI 正常交付且保护基线有效，就继续 R2/R3，按轮保留失败。若会话崩溃、预算耗尽或不能产生合法交付，结束轨迹；后续轮次标记未到达，不能重新开会话补成成功。

每轮最多 30 分钟 agent 活动时间、50 次生成类 HTTP 请求；重试计入请求数。每条轨迹最多 90 分钟、150 次生成请求。计数请求单列并保留，不混入生成预算。验收与控制器暂停时间单列，不计 agent 活动时间；总墙钟耗时仍完整报告。

需要把旧的单次运行请求账本改为“逐轮 + 整条轨迹”两个上限。只有控制器确认进入下一轮才能开启新额度，候选不能自行重置。

## 6. 独立验收与校准

详细分组见[验收矩阵](../evals/specs/c6-real-v1/acceptance-matrix.md)。每轮同时执行：原项目构建/类型/回归、该轮新增契约、之前轮次契约、保护清单检查。检查真实构建包和外部消费者，不只通过源码路径导入新类。

验收分为可见包 V 和保留输入 H。V 的用例及命令随当前题面提供，用于生成 R2 反馈。H 使用不同的输入组合检查**同一份已公开契约**，不给秘密需求。H 代码和结果留在控制器侧，整个运行结束后才进入分析报告。

必须在真实模型试跑前通过这些门槛：

| 门槛 | 必须有的证据 |
|---|---|
| 上游可运行 | 原冻结提交在隔离环境完成构建、类型检查、原测试，连续两次通过；记录准确命令、退出码、时长 |
| 包消费者可运行 | 主包及受影响 workspace 包的入口和类型可用；示例没有导入镜像旧代码 |
| 题目可解 | R1/R2/R3 参考产物分别通过当轮全部 V/H 和原回归；R1 初始项目通过原回归，但新功能验收应失败 |
| 验收能抓错 | 错误变体分别触发嵌套重复事件、全局 seq 泄漏、回调异常改变业务结果、只补运行时漏类型、R3 破坏旧默认值、覆盖用户文件、硬编码策略等失败 |
| 控制器可信 | 两个真实 CLI 的三轮模拟闭环、计时暂停、请求额度、崩溃和中断分类、未来材料不可见、稳定快照全部通过 |
| 证据可用 | 原生 Trace、HTTP/SSE、工具输入输出、轮间反馈、源文件及哈希收齐；测试凭据扫描通过 |

准备阶段先把 Node/pnpm 的具体版本、完整命令、原测试发现数量和合理超时写入 manifest。初始基线失败属于环境/任务准备失败，不计作 agent 失败。不接受静默跳过、自动更新快照或删掉失败测试。

验收副本从干净依赖环境和候选源码重建，恢复受保护原测试及配置。若候选改过保护项，先单独记失败，再恢复验证；恢复不能抹掉违规事实。构建缓存不得带入评分副本。

先执行 2 条完整试跑轨迹，每方 1 条，共 6 次轮次交付。试跑不计正式成绩。若因此修改题面或验收，重新校准受影响部分，固定新版本后才开始正式运行。正式期间新发现的遗漏另设 revision，对双方保存产物统一离线复验，保留原冻结成绩。

## 7. 正式计划与评分

正式做 3 对重复，每对 Axi/Claude Code 各一条三轮轨迹。顺序预先固定为 Axi→Claude Code、Claude Code→Axi、Axi→Claude Code。顺序不完全平衡是三对样本的限制；记录时间和上游事件，不据此推断小幅速度差。

双方同模型 `claude-opus-5-5`、同网关、medium，采用各自原生工具循环。不是相同 system prompt 下的裸模型对比。冻结 Axi 源码与 Claude Code 容器版本；只冻结评测镜像，不更改用户本机的自动更新设置。不在正式评测中途修 Axi。

沿用已有工具边界：Claude Code 使用 Bash/Read/Write/Edit/Glob/Grep，Axi 使用原生 bash；不启用子 agent、外部搜索或额外插件。双方不继承宿主个人配置和跨轨迹记忆。控制器不手动压缩历史；Axi 保持追加历史，Claude Code 若发生原生上下文压缩，则记录事件及其实际用量。这属于产品机制差异，不伪装成完全相同的上下文实现。

主要结果按如下口径同时报告，不能用一个最终总分覆盖过程：

- R1 首次交付通过率：3 次/方，所有必要分组通过才算该轮通过。
- R2 反馈修复：只对 R1 存在可见失败的轨迹报告修复情况；另列隐藏检查结果与回归。无可见失败时标“不适用”。
- R3 最终交付通过率：新增功能、全部旧契约、保护项同时通过。
- 三轮全通过率：三轮均通过；与“R3 最终通过”分别报告。
- 回归：上一轮通过、下一轮失败的分组清单。各轮未到达、预算耗尽、产品失败与环境不可判定分开。
- 成本与过程：活动时间、墙钟时间、token、生成请求/重试、工具调用、自测行为、人工介入。工具调用多不代表质量高。

**样本单位是 6 条正式轨迹，不是 18 个独立样本。** 同一轨迹的三轮有关联；三次重复也只来自同一题。采用逐次数据和范围描述，不宣称统计显著或总体胜者。

预计计划总量为 2 条试跑 + 6 条正式轨迹，上限 24 次轮次交付。按预算上限，模型活动时间可达 12 小时，另加环境搭建和验收；不能保证一个晚上跑完。执行时设置明确截止时间和报告预留时间。剩余时间不足容纳一整对时，不启动新配对，不为了赶进度缩短某一方预算。

上游网络、认证或限流不能完成等环境问题保留原始记录，标不可判定。恢复后每个事故最多补跑一次**完整配对的三轮轨迹**，从全新初态开始，并明确标记补跑。普通产品失败不触发重跑。重试不计入上述 8 条基础计划，必须显示实际启动数；若达到截止时间，则报告未完成，不自动延长。
