# v0 首次试用

本指南供你主动手动试用。建议用 15 至 20 分钟完成一轮：你输入需求、确认命令并判断结果，Axi 负责写代码和运行。助手承担的自动测试与同题对照已获确认，方案见[评测设计](../02-evaluation-design.md)，运行方法见[自动评测指南](automated-evaluation.md)。

事实：v0 已完成自动化测试和助手执行的真实网关验收。尚未记录用户亲自试用的反馈。

本次要了解三个问题：命令确认是否容易理解，等待过程是否清楚，连续修改是否符合预期。练习结果用于选择下一步工作，不预先确认 v1 的功能。

## 启动

2026-11-10 已核对：本机 `.axi/first-use/` 只有练习需求和虚构任务数据，尚未生成 `stats.ts`。入口的 `--help` 可运行；本次没有验证真实网关连接。

在 macOS 终端逐行执行以下命令。它使用本机实际路径，复制时保留已有文件：

```sh
cd /Users/spidey0o0zheng/workspace/axi
mkdir -p .axi/first-use
cp -n examples/v0-first-use/brief.md examples/v0-first-use/tasks.md .axi/first-use/
cd .axi/first-use
bun run /Users/spidey0o0zheng/workspace/axi/src/main.ts
```

出现 `你 [medium] >` 后再输入任务。Bun 和项目依赖在本机已安装，不需要为这次试用重新安装。新电脑先在仓库根目录运行 `bun install --frozen-lockfile`。

如果从新的仓库副本开始，在仓库根目录执行以下准备命令。`cp -n` 保留目标目录中已有的同名文件。

```sh
mkdir -p .axi/first-use
cp -n examples/v0-first-use/brief.md examples/v0-first-use/tasks.md .axi/first-use/
```

从仓库根目录进入练习目录并启动：

```sh
cd .axi/first-use
bun run ../../src/main.ts
```

需要你启动 Axi 的那个终端已经配置 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_API_KEY`。本次助手进程能看到这两个变量，不代表每个新开的终端都能看到。可以先检查是否设置；下面的命令只显示状态，不显示值：

```sh
bun --no-env-file -e 'for (const key of ["ANTHROPIC_BASE_URL", "ANTHROPIC_API_KEY"]) console.log(key + ": " + (process.env[key]?.trim() ? "已设置" : "未设置"))'
```

如果提示未设置，在自己的终端中配置后再启动。Axi 不会自动读取 Claude Code 的个人设置；Claude Code 能用，不代表 Axi 已得到同样的环境变量。不需要把真实值发到聊天里。

另一种方式是在本地仓库 `.env` 中配置两个变量。2026-11-10 核对时该文件不存在。若你自行创建了它，从练习目录启动时应显式指定文件，避免依赖工作目录的自动加载：

```sh
bun --env-file=/Users/spidey0o0zheng/workspace/axi/.env run /Users/spidey0o0zheng/workspace/axi/src/main.ts
```

练习目录用于归拢文件，不是沙箱。确认前检查命令是否符合当前练习。命令含义不清楚时，可以拒绝，并在理由中要求 Axi 先解释它会读取或修改哪些文件。

[终端输入清理缺陷 R1](../verification/2026-11-10-repo-review.md)已修复，并通过真实伪终端回归：新提示会清除光标两侧的残留输入，中断后也不会复用旧的 `y`。使用时仍应等确认提示出现后再输入；输入 `n` 或直接回车均拒绝当前调用。

## 按顺序输入三条任务

每次等待上一轮结束，再输入下一条。v0 只支持单行输入，不要一次粘贴多条任务。

| 顺序 | 输入给 Axi 的任务 | 检查结果 |
|---|---|---|
| 1 | 阅读 brief.md 和 tasks.md，简述需要完成的功能。先不要修改文件。 | 能正确说明三种任务状态，并保持文件不变 |
| 2 | 按 brief.md 实现 stats.ts，并用 bun run stats.ts tasks.md 实际运行验证。 | 输出未开始 3、进行中 1、已完成 2 |
| 3 | 保留现有三项输出，再增加任务总数和完成率。完成率保留一位小数。实际运行验证。 | 原三项不变，新增总数 6、完成率 33.3% |

每次出现命令确认时，输入 `y` 只批准当前调用。需要暂停或拒绝时，输入 `n` 或直接回车。拒绝理由可以留空。

可以在第 3 步首次提出修改文件的命令时拒绝一次。理由填写“先解释本次会修改哪些内容，等我确认后再修改”。观察 Axi 是否停下来解释。后续命令仍需重新确认。

结束时输入 `/exit`。生成文件保留在练习目录，日志位于 `.axi/first-use/.axi/logs/`，路径相对于仓库根目录。下次启动不会恢复本次对话。

退出 Axi 后，可以在当前练习目录独立检查实际结果：

```sh
bun run stats.ts tasks.md
```

完成第 3 步后，检查三种状态仍为 3、1、2，新增总数为 6、完成率为 33.3%。以实际程序输出为准，不能仅看 Axi 的完成说明。若想重新开始，另建一个练习目录并复制两份原始输入；不要覆盖需要保留的试用产物。

## 记录反馈

不需要先定位代码。每个问题记录以下三项即可：

- 我当时想完成什么。
- Axi 实际做了什么。
- 我希望它怎样做。

优先记录一个具体卡点，例如“写文件的命令太长，我看不懂是否应该批准”。可以记录任务原话、发生顺序和屏幕上的现象。无需上传整个原始日志。

## 试用之后

先把反馈写入开发日报，并区分需要修复的错误和希望增加的能力。影响正确性的问题先补测试并修复。

之后选一次真实调用，按“用户输入 → API 请求 → 工具调用 → 人工确认 → 工具结果 → 最终回答”的顺序复盘。这样可以把产品体验与实现连起来。

最后讨论 v1 设计。当前候选方向是文件工具、修改预览和权限规则。例如，若主要卡点是长 shell 命令难以判断，就优先讨论专用文件工具与修改预览。权限规则涉及已有的逐次确认决定，需要单独确认。

这些方向仍是建议，尚未确认实现范围。
