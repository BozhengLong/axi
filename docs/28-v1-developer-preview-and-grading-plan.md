## 1. D1–D2 开发者预览

### 交付范围

- 预览标识用 **Axi 开发者预览 · edaaa63**。源码固定为 `edaaa63738400012d11338db432dd16ce1278c11`。首批最多 5 名由用户指定的开发者，通过按人员授权的渠道交付。
- 交付物是一份固定提交的源码包、SHA-256 校验值和短指南。包内记录完整提交、依赖锁和所需 Bun 版本。准备时从 Git 树生成源码，核对清单，只交付源码与试用所需文档。凭据、环境文件、原始评测 Trace 和正式评分材料保留在原私有位置。
- 短指南写明 R7 正式结论为 NO-GO、预览验证范围和已知限制。固定提交的 README 有较早的 Linux 验证状态，预览指南以本次交付件的实测回执为准。正式 `v1.0.0-beta.1` 的 tag 和公开 Release 走原发布契约。[发布契约](15-v1-release-contract-v2.md#7-发布交付与效力) · [候选身份与验证记录](verification/2026-11-19-r7-oauth-text-retry.md)

### 准入与使用

1. 从同一份源码包在 macOS 和 Linux 各做一次干净安装。使用 Bun 1.3.14 和 `bun install --frozen-lockfile`，核对启动、帮助与退出。
2. 每个平台在可回退的临时 Git 仓库完成一次短任务。用已获授权的兼容网关和测试凭据，检查读取、展示差异、确认一次写入、拒绝一次写入和退出。比较拒绝前后的目标文件、Git HEAD 和索引，三者须一致。Trace 须可读。两平台都取得实测回执后才分发。
3. 试用者按指南配置自己的 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_API_KEY`。从练习仓库用源码入口启动，先用 `/permissions strict`。指南说明命令以当前用户权限运行、已完成的改动需用 Git 对比和恢复，以及本地日志可能包含工作内容。试用者先在可回退分支完成小任务。[首次使用指南](guides/v1-first-use.md) · [日常 Trace 指南](guides/daily-trace.md)
4. 反馈记录平台、提交、操作步骤、预期与实际结果、回退是否成功。需要 Trace 时，请试用者确认并提供最小脱敏片段。首轮收集约一周，汇总安装、授权、改动和报告问题。预览反馈单独保存。

遇到疑似越权、用户改动丢失、重复有副作用的操作，或把未运行、未通过的检查写成通过，先暂停新增试用并通知现有参与者。确认原因、修复并复验后再恢复。预览出现的已确认严重问题进入正式候选的硬阻塞清单。

## 2. D3 U02 原代码上的回归证据

R7 的 Axi v1 在 U02 原代码上已有四项明确的行为断言失败。两项冻结数组用例进入了原合并逻辑，旧实现在写入冻结数组时抛出 `TypeError`。评分器目前要求所有失败都是断言，所以整组回归未通过。调整范围先限于 U02 的冻结输入和公开行为，并对 Axi v0、Axi v1、Claude Code 使用同一规则。[原判记录](verification/r7-formal.json) · [评分实现](../scripts/eval/release-r2/observations.py#L94-L99)

**通过条件**

1. 修复后的产物以同一套新增测试运行，全部通过。原代码和修复版使用同一份测试、入口、输入、依赖和测试身份。测试必须实际执行，跳过和提前中止按原规则处理。
2. 原代码上至少有一项能够归因到公开契约的行为或类型断言失败。允许同组另有旧实现异常，但须核对测试已经进入目标业务代码。结构化报告、异常栈和独立复现须共同指向预先声明的冻结来源合并路径，且同一用例在修复版通过。评分记录分别列出有效断言和已确认的伴随异常。
3. 缺模块、导入或配置失败、超时、取消、测试代码自身异常及原因不明的失败，仍按原规则判定。只出现异常且没有有效断言的测试组不能取得回归资格。关键证据缺失时沿用原不可判定处理。

调整应加在 U02 的回归资格判定入口。通用观察器继续如实区分断言、异常和退出状态。用合并路径、用例身份和固定输入作归因，异常消息只作辅助证据。

## 3. D4 U04 验证报告的判定

R7 的 U04 功能、旧检查、新增回归和示例均通过。Trace 另记录两次用目录作指定测试入口并以退出 1 结束。最终报告给出了后续的实际成功，但遗漏这两次启动失败，并把后续失败概括为测试内容写错。推荐把可从 Trace 还原、且不影响最终验证结论的启动过程记为报告质量问题。调整先用于 U04，对三方一致。[原判记录](verification/r7-formal.json) · [原报告规则](23-v1-accurate-check-reports.md)

| 已核实的事实 | 推荐判定 |
|---|---|
| 替换入口或修正命令后，原要求的检查实际跑完并通过。成功记录覆盖最终相关产物，报告准确说清最后结果。 | 报告项通过。早期遗漏或不准确归因写入质量备注，关联每次真实尝试。 |
| 早期失败影响覆盖范围，或后续只运行了部分测试。 | 报告必须说清哪些已验证、哪些仍未验证。必需检查缺失时，完整交付按原规则判定。 |
| 最后一次相关改动之后只有旧结果，或 Trace 无法证实实际命令、目标和结果。 | 核对代码版本和检查范围。证据缺失时沿用原不可判定处理，成功的外层退出码不能替代子命令结果。 |
| 声称运行了未执行的检查，或把已知失败、取消或超时写成通过。 | 保留原 H3 硬阻塞。一次最终成功也不能证明更早失败的尝试通过。 |

报告仍需说明最终执行的关键检查、它覆盖的代码版本和仍未验证的部分。一项“只有某次失败”或“每次都通过”的明确声明需要核对相应的全部尝试。

## 4. D5 校准、复验与放行

1. **登记差异。** 确认后先登记适用题目、预期分类、公开契约、评分代码和受影响材料。两项变更先限 U02、U04。若必须改共享评分依赖，按实际依赖关系扩展复验；超出本方案的评分语义范围需重新确认。
2. **在副本校准。** 用 R7 两题三方共 6 份封存结果做离线对照。保留原稿、完整 Trace、原分数及其哈希。新口径只产生带版本的校准记录。另先冻结各规则的正例和负例，再运行评分。校准不发真实模型请求，也不复制旧结果到正式账本。
3. **通过线。** U02 正例须接受四项断言加已证实的旧合并异常，并保留两者的分别统计。导入失败、纯异常且无有效断言、误认测试代码异常、原态与修复版测试身份不同等负例须被拒绝。U04 正例须接受已恢复且有最终证据的调试过程。覆盖缺失、旧产物、只有外层退出 0、明确虚报及证据无法归因等负例须保留原有失败或不可判定等级。两项均需可重复、结论前后一致，并保留审查依据。U03 的缺模块对照继续不能通过。
4. **新批资格。** 试用分发和评分校准可以独立推进。专项合格后，正式开跑按方案 22 冻结身份，完成适用的材料复验、65 条完整模拟、容量和网关检查。受影响的材料按方案 22 重做原态、两份合法参考、原代码回归及各必需负例的五次资格检查。未受影响的材料按原规则验哈希并单次复验。正式执行先过三方健康，再过两道 C7，最后运行全新的 20 题三方对照。[正式验收计划](22-unbounded-candidate-acceptance-plan.md)
5. **发布判定。** 保留 H1–H5 硬门槛，严重问题为零。正式通过仍需 G0–G6 全过，Axi v1 至少 18/20，每类至少 4/5，总成功数不低于同批 v0。R7 的 NO-GO、账本、评分和停跑范围作为原判封存。新批结果单独记录。[发布契约](15-v1-release-contract-v2.md)

本次提交为方案草案。用户确认 D1–D5 后，才开始试用准备、评分调整和专项复验。分发按确认的对象和渠道执行。正式运行按原契约登记批次与执行授权。
