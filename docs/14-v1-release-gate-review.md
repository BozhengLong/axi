# v1发布门槛复盘

2026-11-15。状态：讨论稿。用户询问怎样达到v1发布门槛、为什么多轮检查仍未达到，以及门槛的定义。本次核对已有设计、结果与产品差异；未修改现行门槛、历史成绩或产品代码，未新增模型运行。

## 1. 当前生效的门槛

原始[v1设计第9.4节](07-v1-design.md#94-评测适配与指标)已经要求：确定性场景通过，当前新Axi的C7两次及新任务六次全部完整交付，无未解决的保护或协议回退。不要求超过Claude Code。6/6不是最近才加的要求。

[方案13](13-v1-reentrancy-qualification-plan.md)增加并沿用了开发筛选。实际顺序是：

1. 产品确定性检查、参考及评分资格、真实接入前置通过。
2. 控制/候选各做E和D，选定版本须完整2/2；优先保留合格控制版。
3. 选定版本实际执行C7两题，完整2/2。
4. 冻结版本后选择两道新复杂题，三方各重复三次。新Axi须完整6/6。
5. 无未解决的保护、协议或已确认契约缺陷，完整可观察Trace与人工判定齐全。

完整交付包含公开行为契约、有效回归、类型和文档、报告真实性及用户文件保护。模型自己的测试通过，不能抵消已确认的契约缺陷。正式发布动作仍须另有明确授权。

当前卡在第2步。两版都是E失败、D通过，完整1/2；C7及新题不是本轮失败样本，而是未进入。最新四个共享范围场景在模型运行前已经冻结，这次失败不依赖事后新增的等待调用诊断。见[本轮结果](verification/2026-11-15-v1-reentry-results.md)。

## 2. 为什么多轮检查没有直接带来发布

### 评测进步和产品能力进步是两件事

前期实现了文件工具、权限、取消、协议兼容修复和一次有界复核。这些是产品改动。最近两轮的候选实验主要修改通用提示，另有大量参考与评分设施工作。

本次核对`git diff 0330626 HEAD -- src`，当前产品差异只有`src/agent/loop.ts`与`src/agent/review.ts`各新增一段提示。157条序列是外部检查任务产物的程序；修好它们不会自动使Axi学会对应推理。参考代码没有交给执行中的模型，每次任务也从独立初态开始。

因此，资格组数、测试数量和Trace数量增加，说明证据更完整，不代表完整交付率已经提高。最新两版仍为1/2，样本不足以证明通用提示整体有效或无效。

### 历次停止原因不同

- 环境和协议：早期运行出现Node/评分进程异常、上游限流或未知协议分类，不能算成普通代码失败。
- 评分设施：缓存恢复、测试文件超时和原生once计数产生过错误结果。参考实现也曾有真实缺陷，导致资格证据不足。
- 任务产物：评测修正后，仍发现回调接收者、Promise观察、重入登记、共享作用范围等实际错误。

这些都应分别处理。不能用“v1未达标”一个标签解释所有轮次；也不能因有过误判就忽略最新冻结检查检出的真实错误。依据见[风险归因轮结果](verification/2026-11-14-v1-review-results.md)、[可信评测轮结果](verification/2026-11-15-v1-trust-results.md)。

### 发布范围的论证不足

[最初目标](07-v1-design.md#1-目标与依据)是操作可控、结果可核查、已有任务能力不回退。后续把困难的新题转为必过开发题，不断深入异步状态机和运行时兼容边界。数值门槛保持，但实际需要证明的能力越来越专门。

已确认的既有契约缺陷必须如实记失败。与此同时，需要判断这些题是否足以代表v1承诺的日常工作。当前方案没有充分论证“这些高难题的全部成功”与“这个工具版本可以投入日常使用”之间的关系。这是助手提出方案时需要承担的设计责任。

6/6仅证明这六次满足既定判据；两道题的重复不能证明任意开发任务的可靠率。严格的全过要求和狭窄的任务覆盖可以同时存在。

### 对照尚不足以解释失败来源

最近两轮Claude只执行健康探针，未进入新的复杂任务正式对照。因此不能认定当前错误由Axi工具造成，也不能认定完全来自底层模型。生成错误仍影响Axi用户，不能以“模型问题”免除产品责任。

四次最新运行都实际复核，结束时尚剩7至8次复核请求。当前没有证据表明单纯增加预算或重复提醒能够解决问题。

## 3. 建议采用的发布定义

建议定义为：**在明确支持的任务和环境中，Axi能提供可控、可核查的真实开发能力，保护用户已有工作，验证证据可追溯，新增能力没有已确认的重大回退。**

这里仍需验证代码质量。用户逐次授权修改，不等于用户有能力发现代码缺陷；不能把自动测试和验收责任交回用户。

建议将证据分为三类：

| 类别 | 用途与要求 |
|---|---|
| 产品硬门槛 | 文件工具、权限、冲突处理、取消、用户文件保护、协议及状态报告；约定场景全部通过，已确认的严重缺陷阻止发布 |
| 日常开发可用性 | 从目标工作场景定义固定的代表性复杂任务，覆盖多文件修改、真实缺陷、兼容与错误路径、回归和文档；在运行前约定通过条件，与v0/Claude作可比对照 |
| 高难专项能力 | 重入、复杂并发、极端运行时行为等持续评测并披露限制；是否阻塞发布，取决于它是否属于声明的支持范围及风险，不能仅因某题失败就将它移出门槛 |

这还不是已批准的新量化验收方案。典型任务范围、可接受成功率和版本定位须在选新题及运行前确定。不能随手换一个百分比，也不能通过改名Beta就认定可发布。如果v1承诺复杂库任务在当前预算内自主完整交付，现行高难门槛就应保留。

## 4. 怎样推进到可发布

V1/GATE-REVIEW-001：建议先对齐发布承诺并做因果归因，再决定产品修改。提出人：助手；确认人：待用户；日期：2026-11-15；状态：建议，未实施。

1. 写成一份明确的发布契约：目标任务、硬性阻塞、验收材料和可接受限制。原研究结果全部保留；门槛变更单独确认、只对未来研究生效。
2. 用少量固定同题对照补足Claude证据，检查上下文、工具反馈、验证行为和结果差异。小样本只作归因线索，不作总体排名。
3. 每次产品改动必须回答：失败由哪一项可改变的机制造成；改动预计改变什么可观察行为；什么结果会否定这个假设。若线索指向模型/推理配置，就评估相应配置或承诺范围；若指向Axi流程，就修具体流程。不能默认继续加提示。
4. 有证据支持的新候选再冻结，执行事先定义的发布验收。保留普通失败，不重抽直到全绿；不把人工修好的库代码当作Axi能力提高。

若保持现行标准，必须实际取得开发2/2、当前C7 2/2和新题6/6。没有已验证的改进机制时，不能承诺再跑一轮就能达到。当前正确结论仍是：工具与评测基础已有较多通过证据，高难任务交付门槛未达到，最新日常可用性与三方比较证据还不完整。
