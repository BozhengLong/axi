## 1. 已确认的方向与待确认的范围

用户于 2026-11-10 确认：“先做 Axi 和 Claude Code 的同题对照”，并要求“先把自动测试和对比评测的设计方案写出来，我们确认后再开始”。这项确认只确定对照对象和先设计后执行的顺序，不表示下文所有方案已经获批。

自动测试由助手承担任务准备、操作、验收和报告。用户不需要逐条输入任务或批准测试中的每条命令。自动授权的适用环境和规则由 EVAL/D4 单独确认。手动试用保留为可选入口，见[首次试用指南](guides/v0-first-use.md)。

本设计是 v0 的测试基础设施，不是 v1 功能设计。Axi 继续使用手写协议和已有工具循环，不引入 agent SDK 或框架，也不增加自动授权产品模式。

## 2. 要回答的问题

1. Axi 能否独立完成已明确说明的任务？
2. 相同任务下，Axi 与 Claude Code 的完成质量、耗时、恢复能力有什么差异？
3. 差异来自可复现的程序问题、模型行为波动，还是环境与测量方式？

“通过”由预先写好的验收条件决定，不由工具自称完成决定。Claude Code 是对照对象，不是标准答案。

“同题”指初始文件、任务要求、追加输入、可用基础环境和验收条件相同。两个产品的系统提示、上下文管理和原生文件工具保留差异。比较对象是受控条件下的产品，不是纯模型能力。

不承诺消除所有不确定性。保证测试可信的办法是提前定义条件、记录实际配置、检查环境、保留失败证据，并在条件不满足时停止或标记不可比较。

## 4. 两类测试分开报告

| 类别 | 方法 | 能证明什么 |
|---|---|---|
| 确定性回归 | 本地模拟 API、固定响应、真实子进程与终端输入 | 拒绝、中断、断流、重试、历史配对等实现是否符合规则 |
| 真实任务对照 | 真实 Axi 和 Claude Code 分别调用真实模型 | 在本批任务和配置下，哪个工具完成了哪些要求 |

模拟 API 不用于替代真实任务对照。真实模型未触发某个异常分支，也不能代替该分支的回归测试。

确定性回归首先覆盖 R1 残留输入、R2 网络错误分类、R3 外部仓库日志，以及现有的空输入拒绝、多工具逐次确认、SSE 中断、执行中断和输出截断。macOS 特有的伪终端复现留在本机，以固定假响应和无副作用命令运行。未知模型命令不在本机自动执行。

## 5. 环境如何搭建

### 5.1 结构与职责

```text
宿主机：评测控制器、任务清单、验收规则、证据存储
  │ 输入任务、处理授权、监控超时
  ├─ Axi 任务容器：固定源码 + 初始文件副本 + 空白用户目录
  └─ Claude Code 任务容器：固定 CLI + 同样的文件副本 + 空白用户目录
             │ 仅允许访问本轮模型转发服务
             ▼
       独立 API 转发服务 → 同一个上游网关 / 模型

任务结束 → 冻结产物 → 新建无网络验收容器 → 输出验收结果
```

主评测按顺序运行两个工具，每次建立新的任务容器。图中两条分支表示不同环境，不表示默认并发执行。

### 5.2 文件与进程隔离

- 使用同一个固定基础镜像，安装相同版本的 Bun、bash、Git、基础文本工具和任务依赖。构建阶段下载依赖，执行阶段不安装包。
- 两边容器内工作目录统一为 `/task`，设置相同的区域、时区和资源上限。每次运行分配新的可写数据卷和新的用户目录。
- 任务容器使用非 root 用户。根文件系统只读，只有 `/task`、临时目录和该轮用户配置目录可写。移除不需要的 Linux capabilities，禁止新增权限。
- 不挂载真实仓库、用户主目录、SSH、钥匙串、云服务凭据或 Docker socket。Axi 源码从明确清单复制到只读位置，不复制 `.axi`、`.env` 或整份个人配置。
- 控制器通过容器接口投递初始文件和收取结果。清理只针对带本轮标签的容器、网络和卷，不运行全局清理命令。
- 容器是执行边界；临时目录只是文件归拢方式。不能因为目录名称含有 `test` 就自动批准宿主机上的命令。

### 5.3 网络与凭据

- 每个运行使用专用内部网络。任务容器不能直接访问互联网、宿主机服务、其他任务或上游网关。
- 独立转发服务连接内部网络和受限出口。只有它持有真实 API key；任务容器使用本轮临时凭据，结束后立即失效。
- 转发服务只允许固定上游、必要的 Messages API 路径和请求方法，不提供通用代理，不接受模型指定的新目标或任意重定向。Claude Code 如需 token 计数等附加路径，初始化时逐项核对后列入清单。
- 转发服务保留流式传输，不改写提示或工具结果，不额外重试。否则会影响对两个客户端的观察。它记录实际请求模型、effort、usage、时间和重试次数，认证头不进入日志。
- 不把“内部网络”标签当作已实现的隔离。正式执行前从任务容器实际尝试访问外网、宿主机与非本轮端点，确认失败；再确认允许的模型请求成功。若 Docker Desktop/VPN 的路由不符合预期，先修环境，不降低隔离条件继续跑。
- 只有虚构任务数据可进入这套测试。即使限制网络，也不把真实业务资料或个人秘密放入任务容器。

### 5.4 配置一致性与版本固定

- Axi 记录提交号、源文件清单及哈希；有未提交源码时记录实际快照哈希。仅记录提交号不足以标识实际运行的代码。
- Claude Code 候选版本为 `2.1.322`，安装到专用镜像并记录镜像摘要。每轮检查版本没有变化。宿主机的 Claude Code 配置和自动更新设置保持原样。
- 两边请求模型为 `claude-opus-5-5`、effort 为 `medium`，使用同一个上游网关。禁止自动降级模型。记录请求字段和响应中可见的模型标识；网关内部是否指向同一模型权重仍可能无法证明。
- Claude Code 使用空白配置目录和明确的测试设置，保留默认系统提示与原生文件工具。隔离个人记忆、插件、hooks、MCP、项目指令和历史会话；仅加载评测所需的权限通道。任务说明以两边相同的普通文件和用户消息提供。
- 主对照使用 Bash 与原生读写、编辑、搜索工具，不使用外部浏览器、联网搜索或 subagent。Axi 仍只有 bash。这是本轮限定的本地编码任务配置，不代表 Claude Code 的全部能力。
- 不默认使用 `--bare`：当前官方文档说明它还会改变系统提醒和后台任务等行为。若使用，应作为另一种明确标注的配置，不与主样本混在一起。
- 温度、输出上限、缓存和系统提示等无法完全对齐的因素，记录可见值并列为限制。不能为了表面一致，暗中改写任一产品的请求。

## 6. 如何自动操作两个产品

### 6.1 Axi 适配器

通过 Bun 的伪终端接口启动真实 `src/main.ts`，不绕过 `Terminal`、`confirmCommand` 或 `Agent`。控制器使用明确状态：启动、等待输入、等待响应、等待授权、等待理由、执行工具、任务结束、异常退出。

每次只在匹配状态下输入一行。不能将任务、`y` 和追加要求一次性灌入 stdin。确认必须关联当前完整工具调用、工作目录和命令文本。结合转发服务观察到的完整 `tool_use` 与终端状态校验；不能仅凭模型输出中出现 `[y/N]` 就发出授权。

终端解析遇到未知状态、重复提示或调用不匹配时，记录控制器错误并停止该轮。初始化测试必须覆盖模型文本伪装成提示、多行粘贴、光标移动和 Ctrl+C。

### 6.2 Claude Code 适配器

优先启动真实 CLI 的非交互模式，使用 `--input-format stream-json`、`--output-format stream-json` 和固定模型设置。多轮任务保留同一会话和同一工作目录，不把追加要求当成全新独立任务。

权限通过官方文档中的 `--permission-prompt-tool` 接入测试控制器，使用最小的外部权限服务。该机制只属于测试适配器，不给 Axi 增加 MCP 功能，也不导入 Claude Agent SDK。权限服务必须校验本轮身份、调用参数和决定，并将记录写到任务容器无法修改的位置。

**待验证点：** 本机 `--help` 没有列出 `--permission-prompt-tool`，但官方 CLI 文档列有该参数。先用固定假响应验证本机及容器版本是否支持、授权结果如何回传、用户问题如何输入。未通过时，不开始正式对照；可调整为 Claude Code 的伪终端适配器，并在文档和记录中说明变化。不能以静默跳过所有权限检查作为回退。

`-p` 与 Axi 交互入口的差异会影响界面层比较。因此主报告不评价两者的终端外观，也不把自动权限事件数直接称为真人点击次数。终端交互可另做小范围观察。

### 6.3 授权与补充信息规则

- 主任务允许在本轮可销毁环境中读取、创建、修改任务文件，并执行本地校验。禁止触达宿主机、联网安装、外部服务、改变测试控制配置或持久化后台服务。
- 规则不通过命令前缀判定来充当沙箱。复杂 shell 的最终执行范围由容器、挂载和网络限制约束。控制器只对已经关联到当前调用且处于允许场景的请求作出决定；无法识别时停止并留证。
- 拒绝专项使用固定目标文件和固定理由。首次请求修改该文件时拒绝；如果一个工具调用混合了多项操作，拒绝整个调用，不偷偷改写命令再执行。
- 模型询问缺失信息时，从任务预先定义的答复表中回复。没有预设答案就标记为需要额外信息，不由助手临场提供解题提示。
- 两边可有不同数量的工具调用。统一的是任务权限范围和答复规则，不强求完全相同的工具序列。
- 所有自动确认仅限评测环境。Axi 的日常运行仍遵守 v0/D3，逐次由用户确认。

## 7. 首批任务与验收

先写任务说明、输入文件和验收器，再启动任何候选工具。验收规则不根据某个工具的答案临时调整。隐藏测试只覆盖已在任务说明中表达的要求。

| 编号 | 任务 | 独立验收条件 |
|---|---|---|
| T1 | 只读检查一组虚构文件，报告文件数、内容字节数和指定文件摘要 | 数量和字节数与独立计算一致；摘要包含预设事实；输入文件内容、路径和权限不变 |
| T2 | 现有任务统计练习：读需求、实现并运行、追加总数和完成率 | 原始数据不变；输出 3、1、2；追加后总数 6、完成率 33.3%；额外空行、普通文字等公开规则边界通过 |
| T3 | 修复一个已有 TypeScript 解析器的已说明缺陷 | 公布失败样例；独立边界用例通过；保留既有输出接口；不得删除或弱化已有测试 |
| T4 | 读取多个虚构 JSON 数据文件，按明确规则去重、排序并生成汇总 | 输出与独立期望一致；输入保留；空输入、重复项和非法输入按题面约定处理；失败时不破坏已有输出 |

T3、T4 的精确题面、固定数据、允许修改文件与边界期望已在 [evals/tasks](../evals/tasks/) 和[验收器](../evals/oracles/grade.ts)中落盘并冻结。每项任务不新增业务依赖、不需外网，也不改 Axi 自身源码。

每个任务家族跑 3 次，每次从相同初始快照和空会话开始。T2 的三个步骤在同一次会话连续完成，并在各步骤后保留快照。主对照共 `4 × 3 × 2 = 24` 个运行，不等于 24 次模型请求。

另设不并入主成功率的专项：

- 拒绝后保持原文件并改用另存方案。若模型没有提出目标操作，记录“未触发”，不能算通过。
- 执行中断后继续。用可观察的启动标记确认命令已经开始，再中断；独立确认延迟写入没有发生，并检验后续对话。
- Axi 的 R1–R3 和协议异常用模拟响应保证触发。Claude Code 的内部历史不可完全观察，无法验证的细节标记为不可观测，不编造对等结果。

## 8. 验收与证据如何独立

验收器和标准答案保存在控制器侧，不放进任务容器。任务结束后先终止全部任务进程，再获取产物快照。不得让原 agent 在验收期间继续修改文件。

随后创建独立、无网络、无 API 凭据的验收容器。只带入规定的产物和测试输入，使用固定运行时执行生成程序。标准答案和比较程序仍留在控制器侧，不交给生成程序读取；由控制器检查实际输出与文件快照。生成的代码也是待测对象，不能直接在宿主机执行，也不能用它提供的“全部通过”日志代替验收。

验收包括：程序退出码、标准输出、生成文件、保留文件哈希、文件增删改和符号链接。收取产物时不跟随指向工作目录之外的链接，不把任意输出路径映射到宿主机。使用错误实现和故意篡改测试的样本，验证验收器确实能判失败。

控制器保存每轮的清单、事件、终端输出、脱敏 API 元数据、初始与最终文件哈希、差异、验收结果和终止原因。任务容器内的产品日志是补充证据，不能单独作为不可篡改的事实来源。

原始证据保存在宿主机专用的 `~/.local/share/axi-evals/<batch-id>/`，目录权限 `0700`、文件 `0600`。该目录不会挂载给任务容器。仓库只保存虚构任务、脚本和脱敏报告，不保存真实 key、网关地址或个人配置。

## 9. 运行顺序、限制与失败处理

### 9.1 启动检查与试跑

1. 检查 Docker 服务、可用空间、镜像与版本。
2. 验证文件、网络和配置隔离，包括无法读取宿主机标记文件、无法取得真实 key、无法访问非允许端点。
3. 用本地假 API 验证控制器、授权、拒绝、中断、崩溃回收和证据完整性。
4. 对两边各做一次最小真实请求，检查模型、effort、网关与流式协议。此步也必须在设计确认后执行。
5. 用独立的简单练习检查端到端路径，不计入正式成绩。锁定题面、验收器、控制器版本和配置后，才跑 24 个正式样本。

出现不一致就停止搭建或暂停批次。不能悄悄换模型、降档、扩大网络权限或取消确认来获取结果。

### 9.2 调度与外部限制

- 每对样本靠近运行，交替 Axi 先运行和 Claude Code 先运行。任务顺序由预先记录的随机种子决定。主批次串行，减少本机资源与网关并发竞争。
- 不共享会话、用户目录、任务输出或可写缓存。上游模型缓存可能无法清空，记录命中情况，不能据此声称首轮是完全冷启动。
- 初始建议：每个任务运行最多 15 分钟、50 次模型 HTTP 请求、2 个 CPU 核和 4 GiB 内存。限制作用于整个任务，包括多轮和重试。初始化检查如需调整，先修改整批配置，不对某个工具单独放宽。
- 控制器为证据和产物设置有界收集：初始建议每轮原始输出最多 200 MiB、产物最多 100 MiB 和 10000 个文件。达到上限停止该轮并记录原因，保留已收集部分，不把截断证据当作完整记录。
- 没有输出不等于进程卡死；先记录诊断状态，到外部限时才终止。控制器不依赖被测程序自己清理进程。
- 终止时先发送中断，等待 5 秒，再停止或强制销毁本轮任务容器。保存退出原因、可用证据和不完整产物。取消上游请求并撤销临时凭据。
- 断电或控制器崩溃后，按批次清单回收带标签的资源。恢复时不能继续使用半成品作为一轮新的初始状态。

### 9.3 失败分类

| 状态 | 示例 | 报告处理 |
|---|---|---|
| 通过 | 所有硬性验收条件满足 | 记成功 |
| 任务失败 | 输出错误、漏需求、误改文件、超出任务预算 | 记失败，保留完整样本 |
| 产品运行失败 | CLI 崩溃、未补齐工具结果、产品无法恢复 | 记失败，并与任务能力问题分列 |
| 环境失败 | 公共网关不可达、容器服务异常 | 报告为不可判定，保留原记录，不记成功 |
| 控制器失败 | 提示解析错误、自动授权通道失效 | 暂停批次修复，不用作产品质量结论 |
| 不支持或未触发 | 版本缺少控制接口，拒绝分支没有出现 | 单列，不记通过 |

报告同时展示计划数、实际启动数、有效样本数、各种失败和不可判定数。环境故障允许修复后额外补跑一次完整配对，必须保留原记录和补跑标记。产品失败不通过反复重跑挑选最好结果。

## 10. 如何比较与给出结论

| 指标 | 定义与限制 |
|---|---|
| 任务完成 | 每项硬性条件的通过数、整项任务是否通过，按任务家族列出 |
| 文件正确性 | 输入保留、约定外修改、测试是否被弱化，作为独立硬性结果 |
| 恢复能力 | 拒绝和中断专项是否触发、是否恢复、是否产生禁止的副作用 |
| 耗时 | 总耗时、模型等待、工具运行、控制器授权等待分别记录；镜像构建与启动检查不计入任务耗时 |
| 调用与交互 | 模型 HTTP 请求、工具调用、权限事件、额外澄清数分别列出；文件工具与 bash 调用的粒度不同，不能直接解释为效率高低 |
| token 与缓存 | 使用可观察到的实际 usage；看不到就记未知，不按估算填充；不因费用降低模型 |
| 可维护性 | 助手在隐藏工具名称后按同一准则检查产物；属于附加判断，不能覆盖执行结果 |

优先比较正确完成，再比较完成样本的耗时和交互负担。错误但快速的结果不算更好。失败样本的耗时仍保留，不从报表删除。

3 次重复用于发现明显波动。报告列出每次结果、成功次数、耗时中位数及范围，不把小样本描述为统计上证明的普遍优劣。一次通过也不表示整个产品已可靠。

结论分为事实、解释假设和改进建议。只有对齐条件得到验证，才使用“相同模型配置下”的表述；网关内部行为未知时明确保留限制。

## 12. 已确认决策

以下六项均于 2026-11-10 由用户确认采用推荐方案。此前草案的备选与理由保留，便于追溯。

| 编号 | 问题 | 推荐选择与理由 | 备选 |
|---|---|---|---|
| EVAL/D1 | 首批比较范围 | 4 类任务，各 3 次，共 24 个运行；另做确定性回归和恢复专项。覆盖实际工作与稳定性，规模可控 | 先做 2 类任务各 1 次，只能得到探索性观察 |
| EVAL/D2 | 自动执行环境 | Docker 独立任务容器 + 独立模型转发 + 无网络验收；实际验证隔离后运行 | 独立测试虚拟机，搭建更重；宿主机临时目录不作为无人值守方案 |
| EVAL/D3 | 对照条件 | 同模型、同网关、medium；Claude Code 保留原生文件工具和默认系统提示，使用干净配置 | 另加 Claude Code 仅 bash 的诊断组；不纳入首批 |
| EVAL/D4 | 谁回答授权和问题 | 测试控制器按已冻结的场景规则代答；只作用于可销毁环境；未知状态停止留证 | 用户逐条确认，无法满足本次全自动目标 |
| EVAL/D5 | 执行与统计方式 | 串行交替顺序，保存全部重复与失败；先验收正确性，再比较耗时 | 同时并发，速度快但更易互相影响 |
| EVAL/D6 | 是否边测边修 | 先报告当前版本基线，再单独确认修复与复测，保留原始结果 | 先修已知问题再测，报告只能描述修后版本 |

设计确认后的第一步是搭建与启动检查，不直接跳到 24 个正式运行。若关键接口不可用或需要扩大环境权限，先给出具体证据和修订方案。
