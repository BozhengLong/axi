# C7：故障报告驱动的修复对照

> 日期：2026-11-11。状态：设计已完成，候选运行包和验收器尚未实现，尚未启动模型。用户已同意先交付本设计；两类缺陷、双方各重复三次的方向沿用上一轮建议。本设计细化固定起点、验收、预算与停止条件，供执行前审阅。

## 1. 目标与范围

本阶段回答：给定同一份有缺陷的代码和真实故障报告，Axi 与 Claude Code 能否定位问题、修复所有已公开约束，并留下有效回归测试？结果用于判断是否存在值得修改的 Axi 机制。

C6 的首轮可见检查均通过，没有实际失败反馈供修复。事后发现的监听器清理缺陷、C1 的异常分类缺陷，均已有保存产物和独立复现证据。它们属于生成代码的缺陷，不能直接证明 Axi 的工具、提示或会话机制有错误。依据见 [C6 报告](verification/2026-11-11-c6-comparison.md)与[复杂任务报告](verification/2026-11-11-complex-comparison.md)。

本阶段的“修复”指**新会话接手已有代码和故障报告**。旧会话已经结束；本轮不恢复旧历史，不声称测到了“在原会话中修复自己刚写的代码”。每次运行只有一次正式交付；agent 可以在交付前反复执行测试和改代码，控制器不追加临场提示。

假设是：相同、可复现的缺陷输入，可以把首次功能开发与修复能力区分开。若双方全部通过，结论是它们能修复这两个已知问题，不为了得到分差临时加难度。这是窄范围诊断，也不验证小时级任务或产品总体优劣。

## 3. 候选收到的故障报告

投递稿为 [C7-L 题面](../evals/specs/c7-repair-v1/lifecycle/brief.md)和 [C7-O 题面](../evals/specs/c7-repair-v1/orders/brief.md)。报告包含发生条件、观察值、期望行为及一条可运行复现命令。报告不指定应修改的行、不提供补丁或正确实现。

C7-L 公开复现采用真实 `Listr.run()`，包括父、子、孙任务。保存结果显示业务两步均完成，但子任务、孙任务运行时各残留 3 个 renderer 监听器。正常结束后无继续输出。报告明确问题是清理约束，不声称数据损坏或永久内存泄漏。

C7-O 公开复现采用 `before_commit` 钩子抛出 `BusinessError(409, 'out_of_stock')`。历史实际响应为 409/out_of_stock；期望为 500/internal_error。库存和订单回滚正常，同键随后成功。报告仍明确三个阶段及任意同步抛出值的契约，其他输入只作为保留用例。

公开复现脚本由控制器在**当前投递初态**真实执行，记录命令、退出码、stdout/stderr、初态哈希和镜像。未复现时不启动模型，不能伪造失败输出或沿用与代码不对应的历史日志。生成报告的字段顺序和文字模板固定，对双方一致。

## 4. 一次运行的流程

1. 从冻结的同题初态创建新容器、工作卷、HOME 和 CLI 会话。两边使用相同报告、契约、权限策略和预算。
2. 投递一次修复任务。agent 可以自行读代码、复现、修改、补测试和验证；不能读取控制器或其他轨迹。
3. 实际交付后冻结现场。工具刚执行完但最后模型请求失败，不算正常交付。
4. 在另一无网络副本执行独立验收；保留原代码、最终代码、Git 差异、实际命令和逐项输出。
5. 保存 Trace 后清理容器。下一次从原初态开始，不继承上次补丁、会话、缓存或报告中的新结论。

本轮没有失败后追加第二次用户提示的阶段。实际交付失败保留为失败，不靠再开一次运行改成成功。这样 12 次运行的反馈强度一致；自测次数、定位过程和修改迭代从 Trace 单独提取。

## 5. 验收与“有效回归测试”

完整检查见[验收矩阵](../evals/specs/c7-repair-v1/acceptance-matrix.md)。V 是随题提供的可见检查；H 是控制器保留的其他输入。H 只检查公开要求，不增加秘密需求。

分别记录两种结果：

- **代码修复通过**：正常交付、固定故障消失、其他契约和旧测试通过、保护项未改变。
- **完整交付通过**：代码修复通过，并留下有效新增回归测试，且报告没有伪称未执行的验证成功。

有效新增回归测试需要同时满足：在候选修复后通过；只将新增测试及必要的测试辅助文件放回原缺陷代码时，以目标行为断言失败。编译错误、导入候选新增生产符号失败、超时或缺依赖都不能算成功暴露原缺陷。测试应使用原本存在的接口，单独运行且由原项目测试命令发现。回放使用新的干净副本；不能根据源码哈希、目录名称或环境标记人为区分新旧代码并返回预设结果。

原始全部测试、测试配置、快照、契约、依赖锁、许可与明确用户文件均受保护，包含上一轮候选自己写的测试。允许新增独立测试文件；不得减少旧用例、添加跳过或更改 runner 来规避执行。保护失败独立记分；验收副本恢复原件后继续诊断，不能抹掉原违规。

C7-L 继续检查全部 R1/R3 功能、类型、公开包入口、消费者、转换/过滤和用户策略。C7-O 继续检查参数错误、真实业务冲突、三处事务回滚、幂等、跨进程与 CLI。停止订阅全部事件、吞掉异常、统一把所有业务错误变为 500 等表面修复必须被拒绝。

验收器异常、不能完成或超时，与代码断言失败分开。新发现的遗漏另立 revision，双方保存产物统一离线复验；冻结成绩保持原样。

## 7. 正式顺序、预算与停止条件

两道题 × 两种 agent × 三次重复，共 **12 次正式运行、6 个配对**。只有两道题，不是十二个独立问题。顺序预先固定：

| 配对 | 任务 / 重复 | 执行顺序 |
|---|---|---|
| 1 | C7-L / 1 | Axi → Claude Code |
| 2 | C7-O / 1 | Claude Code → Axi |
| 3 | C7-L / 2 | Claude Code → Axi |
| 4 | C7-O / 2 | Axi → Claude Code |
| 5 | C7-L / 3 | Axi → Claude Code |
| 6 | C7-O / 3 | Claude Code → Axi |

两边总体各先运行三次。每题三次不能完全平衡，记录这个限制。全批顺序执行，不叠加模型负载。

推荐每次最多 **30 分钟活动时间、50 次生成请求**，重试计入。token 计数请求单列。12 次理论活动上限 6 小时/600 次生成请求，不承诺实际需要这么久。独立验收不计 agent 时间，但计总墙钟时间。

启动时显式指定绝对截止时间，预留 30 分钟报告时间。每对预留 60 分钟 agent 活动、30 分钟独立验收和 10 分钟控制器启动/归档余量；加上报告预留，剩余时间不足 130 分钟时不启动新配对。每次独立验收总计最多 15 分钟，超过则记验收设施未完成并暂停后续配对排查。全局截止也覆盖控制器阶段；意外超时导致配对未完成时如实保留，不延长某一方预算。

发生上游网络、认证或持续限流，先保存证据，区分环境不可判定和普通修复失败。环境恢复后允许一次完整配对补跑，从新初态执行双方；原配对两条都保留、不混拼。**全批最多一次配对补跑，实际最多 14 次启动、活动上限 7 小时/700 次生成请求**，仍受原截止时间约束。再次发生不能恢复的环境中断时停止新增运行并报告已完成范围。普通代码失败、预算耗尽不触发补跑。

发现输入污染、保护清单错误、泄露隐藏材料、模型/版本偏离或验收器错误时停止该批，不能一边改任务一边继续计同一批成绩。具体处理要追加事故记录，不能删除较差结果。

## 8. Trace、结果与诊断

每次保存题面、故障报告及复现输出、模型请求/正文/SSE/允许响应头、工具与权限事件、终端、原生会话、stderr/debug、输入及最终快照、Git 状态、独立验收、回归测试回放和 SHA-256 清单。原生日志上限 128 MiB；缺失或超限明确标记。私有原始证据不自动发布或删除。

结果先报告每题每次的代码修复、完整交付、回归/保护失败、未完成与环境分类，再汇总。活动时间、墙钟、请求/token/重试是观察量；限流、原生配置不同等情况下不据此给速度或总体质量排名。

Trace 审查使用固定问题：是否实际复现；首次修改前读取了什么证据；是否改变正确的边界；是否测试修复及相邻行为；是否保护已有工作；报告与实际命令是否一致。引用具体事件，不按工具数、代码行数或测试数量给主观分。

归因分为四类：候选业务实现、agent 工具/会话机制、评测设施、外部环境。单次遗漏只先记观察。要提出 Axi 机制修复，必须能从日志形成可验证假设，并在隔离复现中证明该机制确实造成失败。不能由“没有写好代码”直接推导“应该加某种工具”。

## 9. 从诊断进入产品改动的门槛

C7 本轮交付是修复成绩、Trace 诊断和至多一项有依据的改动建议，不自动实施新产品功能。如果没有足够证据，就报告无可支持的机制改动。

若要修改 Axi，先说明触发条件、当前行为、预期行为、替代解释及最小复现，再设计旧 Axi/新 Axi/Claude Code 对照。三方用相同的新评测环境，不能把历史旧转发器成绩直接当作对照。

**H 用例不是未见任务。** 当前两个缺陷及其原因已经用于设计，不能把同类参数变化称为独立泛化验证。产品改动前还需另行冻结至少两道未用于本轮诊断和调整的验证任务；优先选择不同故障机制，并在适用范围内覆盖拟改机制。只在方案和实现固定后打开结果，不根据结果循环调参。若再次修改，已看过的任务转为开发回归，另留新验证任务。

这些未来任务目前尚未选定或执行。其范围、三方运行规模和预算在具体产品假设出现后单独设计，本轮 12 次计划不包含它们。能证明特定机制改善的受控复现，与能否迁移到其他任务的结果分别报告。
