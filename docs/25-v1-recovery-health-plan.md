# 方案25：允许健康探针在限流后恢复

2026-11-18。状态为待用户确认。目标是在同一网关、模型和墙钟预算下，验证三套实际产品能否完成任务。网关可用性与产品交付结果均须报告。本次提案只涉及评测设施。

## 为什么 C4 停了

方案22/D3用一次没有临时上游错误的三方健康轮，作为网关已恢复稳定的见证。好处是弱化网关波动对下一组比较的干扰。局限是小样本中一次限流就足以终止本批，而连续三次无错也无法保证下一道长任务一路畅通。普通正式任务原本就允许在预算内重试成功后按产物评分。[方案22第3、4节](22-unbounded-candidate-acceptance-plan.md)

C4的v1恢复探针执行了46.2秒。代理序号1、2为流内限流，3取得完整响应；4、5为流内限流，6取得完整响应。原生日志也显示这是两个逻辑调用，各在第3次尝试成功。全部12次转发取得8份完整响应。产物精确匹配33字节，验证脚本和逐字节比对都返回0，复核前后两个评分视图通过。控制器收到了交付 `PASS` 和 `cleanUpstream=false`，按旧规停在v1。Claude尚未启动。[逐次审查](verification/2026-11-18-c4-formal.md) · [正式结论](verification/2026-11-18-c4-release-result.md)

## 待确认的决定

**如何认定恢复。** 对三方使用相同的上游事件定义和时间边界。以代理的请求序号、请求内容与响应结束记录对齐每段重试。原生记录可见逻辑调用编号时一并核对。两类通过都保留同一份产物分数，分别标注“无错完成”或“限流后完成”。若同一请求内容重复出现，须结合调用顺序、工具记录与终态区分；无法唯一归因的槽记未决。保留完整Trace，逐槽披露真实启动次数、生成请求数、完整响应数、限流次数、可核实的重试等待和总耗时。不得从墙钟成绩扣掉等待，也不按是否发生限流筛掉样本。

**设施如何验证。** 同一段合成事件分别绑定三种产品身份，判定须一致。实际CLI沿用各自原生重试策略；若某款在流内限流后直接退出，设施应如实判外部中断。旧规则的离线回放须重现C4在v1处停止，新规则回放只允许领取下一探针。改动涉及[上游事件审计](../scripts/eval/release-r3/execution-evidence.py)、[审查写入](../scripts/eval/release-r3/controller-gateway.py)及[控制器](../scripts/eval/release-r3/controller.py)。

**何时停止。** 持续限流直接导致探针中断或到期，按有凭据的外部中断记录，恢复轮停止。交付有普通错误仍判N，严重违规H立即停止。鉴权或模型身份错误、传输原因不明、观察或封存记录缺失均不能凭最终文字放行。本次豁免只覆盖可证实已恢复的限流，恢复探针中的其他临时上游故障继续按方案22处理。模拟验收还须覆盖证据无法配对、重试造成重复写入、过期到达的成功响应，以及只有两方通过时尝试领取下一阶段。零限流的失败产物也必须被拒。

**如何进入正式对照。** 新批先跑Axi v0、Axi v1、Claude Code三个健康槽。发生确证外部中断时才进入有界恢复。三方恢复检查均符合D1、D2才可完成该轮；初始健康槽只按现有逻辑槽规则补齐，额外恢复探针单列。满足初始健康3/3后，运行当前Axi v1的C7-L、C7-O。两题完整交付2/2才启动固定20题，三方每题各做一次，共60槽。正式任务每槽30分钟，按第一份有效尝试计分，并单列首次表现。发布仍要求v1至少18/20、每类至少4/5、总成功数不低于同批v0、严重问题为0，G0–G6全过。沿用预登记的提前停止条件。[发布契约](15-v1-release-contract-v2.md)

按此提案回看C4，v1这一次满足恢复探针的放行条件，下一步应是Claude恢复探针。Claude的结果、整个恢复轮能否通过以及C7和20题成绩，均须通过真实运行取得。
