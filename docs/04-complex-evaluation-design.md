# 复杂任务同题对照设计

> 日期：2026-11-11。状态：本轮已完成。COMPLEX/D1–D4 的确认见第 10 节，实际结果与验收修订见第 11 节。

## 1. 为什么需要另一组任务

上一轮是 4 类任务，各重复 3 次，所以每个工具有 12 个运行，不是 12 个不同任务。修复后两边均为 12/12 通过。

本次核对批次 `b20261110152552` 的最终产物：T1 不修改代码；T2、T3、T4 的 18 个编程运行均只新增或修改 1 个 TypeScript 文件，该文件总长为 14–118 行。原任务主要检验局部实现和明确边界，缺少存量系统中的多方约束。

这些结果证明基本任务能跑通，也验证了测试设施。它们没有提供足够证据区分复杂编码能力。本次不推翻原验收，也不把原任务的满分外推。

## 2. “复杂”具体指什么

优先增加以下需要协调的条件，不以文件数、代码行数或故意含糊作为难度标准：

- **关联行为**：修改一个入口，会影响持久化、命令行、HTTP 接口和旧调用者。
- **状态与时间**：同一请求重放、并发、重启、中途失败后，状态仍必须符合业务规则。
- **已有约束**：旧接口、测试和用户数据必须保留。
- **验证闭环**：agent 要运行测试，解释失败，再修正实现。
- **连续变化**：后续需求到达时，前一轮的成果和约束仍然成立。

不强制 agent 改动至少几个文件。若一个小补丁确实解决了跨模块问题，也应通过。也不把“最终两边必须出现不同分数”当成目标。

## 4. 独立验收如何区分“看起来做完”和实际完成

### C1：重复提交与并发扣减

**任务给 agent 的症状：** 客户端在超时后重试，有时生成两笔订单；并发下单偶尔使库存小于 0。普通顺序样例可以通过。

**公开契约：** 一次成功下单只产生一次业务效果。相同幂等键与相同业务参数重放，应返回同一订单和成功响应；相同键但不同业务参数应拒绝。幂等记录应随成功事务持久化。“幂等”指重复提交不会重复产生业务效果。

独立检查：

- 20 个并发请求使用同一键：只有一笔订单，库存只扣减一次。
- 库存为 5，12 个不同键各买 1 件：恰好 5 次成功，库存为 0，失败者没有订单残留。
- 提交已完成但响应丢失，再重试：返回原订单。进程重启后也成立。
- 同键不同数量或商品：返回约定冲突响应，不改变数据。
- 在事务提交前注入写入失败：库存、订单与幂等记录全部保持原状态。
- 原有读取接口、错误格式与旧客户端测试继续通过。

并发按屏障控制调度，不靠短暂 sleep 猜测竞争是否发生。不要求某一种锁或数据库写法。

### C2：迁移与向后兼容

**任务给 agent 的目标：** 将任务数据库从 v1 升级到 v2，但旧导出脚本与旧 HTTP 调用仍需工作。

公开数据契约：v1 状态 `todo / doing / done` 映射为 v2 的 `open / active / done`；增加可空的 `deleted_at`。旧接口继续输出旧状态，新接口使用新状态。保留 ID、标题和原时间戳。

独立检查：

- 空库、小库、含 Unicode 文本的库均可迁移，行数与业务字段保持一致。
- 重复迁移不产生额外变化；两个迁移进程同时启动时不会重复应用或损坏数据。
- 在事务中途注入失败，版本号与数据一起回滚，重跑仍可成功。
- 碰到题面声明的非法旧数据，明确失败，不自行丢弃或猜测映射。
- `--dry-run` 不改变逻辑数据和 schema 版本，不将辅助文件变化误判为业务变更。
- 旧 CLI、旧 API 与新增接口均执行验证，不只检查迁移函数本身。

SQLite 数据按逻辑记录和 schema 检查，不把页面布局或 JSON 字段顺序误判成错误。二进制数据库必须按原始字节传输。

### C3：并发、重试与取消

**任务给 agent 的症状：** 取消后仍有任务启动；某些重试超过并发限制；结果偶尔按完成顺序返回。

独立检查：

- 活跃任务数从不超过配置值；返回结果按输入顺序对应。
- 只有声明为可重试的错误进入重试，并符合最大尝试次数。
- 取消后，尚未开始和正在退避的任务不再启动；运行中的任务收到取消信号。
- 某个任务忽略取消信号时，调用者仍按公开契约取得“取消”状态，不能把晚到的成功结果改写为已完成。
- 每个任务只结算一次；定时器和事件监听被释放。
- 使用注入时钟与可控屏障复现竞争，不把机器调度抖动当成缺陷。

这里测试的是 agent 编写业务程序的能力。它不同于上一轮“中断 Axi 自身”的设施检查。

### C4：离线 Trace 校验与回放

**任务给 agent 的目标：** 给一份冻结的 Axi 副本增加 `--replay <trace.jsonl>`。没有 API 配置时也能读取合成的历史记录，展示会话并报告异常。

独立检查：

- 正常多轮、工具拒绝、多工具、失败重试和中断记录能按约定归并。
- 失败尝试的半截响应不能混入最终成功回答；按调用 ID 与 attempt 区分请求。
- 缺少工具结果、重复调用 ID、坏 JSON 或不完整记录能定位并报告，不能把异常历史修补成成功。
- 全程没有模型请求，也不执行 trace 中的历史命令。用本地请求计数器和带副作用的合成命令检查。
- trace 原文件保持不变，签名等原始字段不被改写。
- 原交互模式和原测试继续通过。

只给 agent 冻结源码和虚构 Trace。真实业务日志、认证配置和旧评测答案都不进入任务容器。这个功能在测试副本中实现，不自动合入真实 Axi。

### C5：有界内存的日志汇总

**任务给 agent 的症状：** 小文件正确，大文件内存增长，中文被任意分片时偶尔出错。

独立检查：

- 对相同输入，增量版与独立参考结果一致，包括排序、计数和无效记录策略。
- 覆盖 UTF-8 分片、CRLF、空行、末行没有换行及坏记录；这些规则全部提前写进题面。
- 在冻结的数据规模和内存限制下完成，不把全部内容一次读入内存。
- 中途失败不覆盖已有结果；可重复执行得到同样的业务输出。

数据量和内存阈值先用正确参考实现、明显全量读取的错误变体及实际 Bun 环境校准。目标数据约 30 MiB，具体阈值未确认前不计分。优先用内存上限检验，不用“必须在某个很短秒数内完成”作为主要门槛。

### C6：连续三轮完成发布

**任务给 agent 的起点：** 已有服务和部分未完成的软删除实现。用户写的说明文件及既有修改需要保留。

三轮固定要求：

1. 完成软删除，旧列表默认不包含已删除条目，旧客户端仍可运行。
2. 控制器提供冻结的可见验收反馈包，要求修复并重新验证。两边得到相同检查和反馈规则，不临场提示代码位置。
3. 新增恢复操作与显式查询已删除条目的选项，并保住前两轮的功能。

每轮都保存代码快照、测试结果和约束。第三轮新要求不能用于追溯判第一轮失败。原文件、旧接口和已完成行为是持续条件。初次交付失败与收到反馈后的修复效果分别报告。

## 5. 任务本身也要先验证

复杂任务更容易把测试作者的错误当成 agent 错误，因此在试跑前要满足：

1. 有正确参考实现，能通过全部公开和独立验收。
2. 至少准备两类“看似可用”的错误变体：例如顺序请求通过但并发失败；正常迁移通过但中断时损坏数据。验收器必须能拒绝它们。
3. 初始仓库可以启动和类型检查。除指定问题的复现检查外，旧行为测试应通过。
4. 隐藏测试只检查题面已声明的要求，不增加秘密业务规则。
5. 按结构比较 JSON 对象，忽略键顺序；有顺序含义的数组则按契约检查。
6. 同一份输入、同一事件序列和同一反馈规则用于两边，允许实现不同。

参考实现和标准答案在控制器侧保留，不进入任务容器。原有测试可见但受保护，agent 可以新增测试。最终验收使用控制器保留的原版测试，不以候选自己输出的“全部通过”作为结论。

试跑用于验证题目、验收器和流程，不追求预设的失败率。发现题面歧义后，先保留记录、修订版本，再对两边重跑；不能只修改不利于某一工具的用例。

## 6. 如何评分与复盘

不只给一个总成功率，也不按工具次数奖励。

| 维度 | 观察内容 | 结果表达 |
|---|---|---|
| 业务正确性 | 功能、并发、恢复和数据一致性 | 按验收组通过/失败 |
| 兼容与保留 | 旧接口、原测试、受保护文件、已有数据 | 单独列出回归；破坏硬条件则整题不通过 |
| 交付完整性 | 可运行入口、类型检查、实际验证、变更说明 | 完成、部分完成或缺失 |
| 自主修复 | 发现错误后是否自行修正；给反馈后是否恢复 | 首次提交与反馈后结果分开 |
| 执行负担 | 请求、工具、权限和耗时 | 描述性指标，不代表质量得分 |
| 可维护性 | 模块职责、重复逻辑、错误处理和测试意义 | 隐藏工具名后按统一准则做附加观察 |

整题通过要求所有预先声明的硬条件满足。分组结果解释“卡在哪里”，不能用多个容易通过的检查抵消一次数据破坏。

Trace 重点用于核对：是否真实执行验证、失败后具体改了什么、哪些旧要求丢失、工具输出是否被误读。不会根据思考摘要的文风或长度给分。

不在 agent 运行中临场救场。预设答复表之外的澄清问题记录为“需要额外信息”。如果问题暴露了题面确实缺信息，整个配对标记为题目问题，并在修订后同时重跑。

## 7. 现有测试设施需要的调整

这些是本次读代码确认的差距，不是已完成的功能：

| 当前实现 | 复杂任务需要 |
|---|---|
| 任务列表和 24 个运行数量写死 | 独立的 `complex-v1` 任务集、清单与重复次数配置；保留旧任务集 |
| 种子与验收导入主要按 UTF-8 文本处理 | 按原始字节处理 SQLite 等二进制文件，保存哈希 |
| 主要只验收几个脚本 | 仓库级构建、严格类型检查、原测试、模块测试与端到端验收 |
| 部分 JSON 比较依赖序列化后的键顺序 | 使用结构比较，并先做验收器自身的正反例 |
| 单条验收命令默认 10 秒 | 各任务明确配置验收超时；初始化时校准，不能看到失败后单独放宽 |
| 无业务故障注入与固定反馈包 | 增加受控存储故障、屏障、时钟及多轮反馈支持 |

预装锁定版本的 TypeScript 和 Bun 类型定义，用于严格类型检查，不让 agent 联网安装。SQLite 使用 Bun 自带能力。依赖变化只在测试镜像中完成，不给 Axi 增加运行依赖。

HTTP 服务由测试进程在同一容器的 loopback 上启动和关闭，不要求 agent 留下跨调用后台服务。不增加外网出口，也不扩大宿主机挂载。

沿用 Trace 版本 2、源码快照、独立验收容器与私有证据保留。复杂任务另建批次，不混入已有 T1–T4 成绩。

## 8. 推荐的执行顺序与资源

**推荐先实现 C1、C2、C4。** 它们分别覆盖跨层修 bug、带历史数据的升级、真实 Axi 副本中的功能开发。C3、C5、C6 的设计保留为后续扩展；其中性能和反馈型任务需要更多设施校准。

1. 准备这三份仓库、参考实现和验收器，验证环境可用。
2. 两边各做一次试跑，共 `3 × 1 × 2 = 6` 个运行，记录全部结果。
3. 修正题目或设施问题后冻结新版本，做 `3 × 3 × 2 = 18` 个正式运行。试跑成绩不混入正式统计；不只选择试跑中某个工具失败的题。

主配置继续使用同一网关、`claude-opus-5-5`、`medium`。先增加任务复杂度，不同时改 effort。后续若比较 high，应另开配置组。

建议每个完整任务最多 30 分钟、50 次模型 HTTP 请求。保留 Axi 当前的轮次上限，不为评测修改产品循环。两边相同的外部预算，达到上限记为预算耗尽，不能偷偷输入“继续”获取额外配额。

任务容器保留 2 CPU、4 GiB 的配置。性能专项的程序内存限制另行校准。30 分钟是上限，不是已测完成时间；实际耗时只有试跑后才能知道。

遇到控制器、Trace 归档或基础环境错误时暂停并留证。正常的任务失败继续记录，不为了满分修改 Axi、重写候选产物或不断重跑。
