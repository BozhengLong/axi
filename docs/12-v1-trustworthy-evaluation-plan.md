# v1可信评测与兼容行为复核方案

2026-11-15。状态：设计建议，D1–D5待用户确认。本次只核对证据并写方案，没有修改产品、评分器或启动新模型任务。上轮研究保持关闭。

依据：[上轮报告](verification/2026-11-14-v1-review-results.md)、[逐次数据](verification/2026-11-14-v1-review-results.json)及[原发布门槛](11-v1-delivery-review-plan.md#6-d4回到原发布门槛)。本方案建议先取得可信的判断，再验证交付行为的改进，最后进行新的发布验收。

## 1. 这次需要解决什么

| 已核对的事实 | 能支持的判断 | 下一步 |
|---|---|---|
| E三方都把cacheKey的普通调用变成对象方法调用，同参数可能算出另一把键 | 新包装破坏了原调用语义；不能直接归因到Axi文件工具 | 校准兼容行为检查，再验证agent能否主动发现这类回退 |
| E写入与D尝试的原生Promise诊断中，部分产物和两份参考也产生额外未处理拒绝 | 参考实现不是可靠性的充分证明；原库同输入对照有独立价值 | 修参考，并用不同实现路径和正反样本交叉检查 |
| D取消原因在instanceof检查中被替换 | 错误的分类顺序会破坏外部原值 | 验证身份、传播路径和清理，而不只检查“抛了一个错误” |
| 评分器把17.4秒内正常结束的原库回放在10秒截断 | 一项有效回归被设施误判，不能算agent失败 | 统一评分预算，记录超时来源，正确保留不可判定 |
| tsimp的进程缓存包含Unix socket，原模拟未暴露该问题 | 只写入参考文件的CLI模拟没有完整覆盖真实构建和测试副作用 | 模拟中实际执行项目命令，再封存和重建 |
| 题面写attemptTimeout?: number，同时规定运行时接受null | 类型契约与保留检查存在歧义 | 在新版本中先明确类型要求，再固定断言 |
| 两份新Axi复核均执行了工具，但文件未变，缺陷仍在 | 不能声称一次通用复核已经提高完整交付成功率 | 对更具体的兼容行为复核做小规模对照，不增加复核轮数 |

这里的“可信评测”指：明确的公开契约、能分清设施问题的评分器、经过反例校准的检查，以及可复查的执行证据。“兼容行为”指原接口的可观察表现，包括调用上下文、参数、返回值、错误身份、取消和清理。

发布验收是预先声明的有限检查，不是任意程序都正确的证明。但已经确认违反声明契约的缺陷，仍然阻止发布。不能为取得通过率删去已确认的要求，也不能把声明外的偏好临时变成扣分项。

## 3. D1：先让评分器通过资格检查

### 3.1 时间限制与结果分类

移除未写入题面的文件级10秒上限。每次任务的最终产物与复核检查点仍共用15分钟独立评分预算，不为检查点重新计时。

- 命令、子进程和清理都受同一绝对截止约束。任何额外运行器限制必须公开、登记来源，并计入总预算；不得随意叠加更短上限。
- 契约场景可以有明确的有界等待。只有它对应公开要求，且健康对照和断言证据足够时，才能据此判行为失败。
- 整个测试文件、评分进程或设施命令被监督器终止，不能自动转成候选失败。无法完成判断就标为indeterminate（不可判定）。
- 同时记录命令退出码、内层测试结果、取消项、信号、超时来源和剩余预算。外层退出0不能覆盖内层testTimeoutFailure；管道尾部成功不能代表测试成功。
- 保持执行状态与评分状态分离。评分未完成时，代码和回归分数为null，不得填成false或沿用旧的成功分数。

不取消无限等待保护。没有足够证据区分代码问题和资源问题时，允许停止并保留不可判定；不会为了凑齐分数强行归因。

### 3.2 重建、缓存和保护

保留原封存。只在独立评分副本中处理明确登记的工具缓存。缓存目录的来源、路径和处理理由进入清单；不以“特殊文件”为由跳过任意候选内容。用户原有文件和受保护内容先核对，再做允许的工作副本规范化。

初始化、构建、评分、清理的失败路径都要覆盖。每个工作卷和容器有唯一所有者；初始化失败也能收回自己创建的资源。输出缺失、异常进程信号、源码或Git身份变化均不能误报成功。

### 3.3 必须通过的离线资格矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 原库回放超过10秒、仍在15分钟预算内 | 完成全部测试；本轮D旧Axi的23项应得到18项目标断言失败、5项通过、0取消 |
| 契约断言失败、语法失败和明确保护违规 | 正确记录候选不通过，不混作上游恢复 |
| 测试运行器自身超时、监督器截止、异常信号或空报告 | 来源清楚；证据不足时不可判定，不能把截断伪装成完整失败报告 |
| 真实构建与测试生成tsimp缓存、socket | 执行可完整封存；评分从源码安全重建；原始缓存证据保留 |
| 未登记的特殊文件、目录逃逸或符号链接 | 拒绝或不可判定，不能静默忽略 |
| 评分初始化失败、进程失败，且目录里已有成功分数 | 不采用旧分数；计时器、进程、卷均可收回 |
| 最终与检查点共用预算，前一个耗时较长 | 后一个只能使用剩余额度，不能重置；不够则明确未评分 |
| 停止新增模型时仍有任务运行 | 正常风险下让已启动任务完成封存；关闭和评分状态分别记录 |

回放上轮全部6份最终产物及2份新Axi检查点，共8份封存快照。不向模型重新提问。结果写入新研究的离线资格命名空间，记录旧执行哈希、新评分版本和对应条款。不得覆盖旧机判，不得把离线回放变成上轮新增正式成绩。

所有将使用的CLI/版本模拟都必须实际执行原构建、测试和类型命令。开发准入覆盖三种运行适配器及两份v1版本，再走“交付—封存—重建—评分”。只把参考文件写进容器再输出完成，不再足以证明链路可用。模拟仍不算模型能力。

资格阶段的发现可以修复后重新验证，但须保留失败记录，并重跑受影响的整组检查。它不消耗真实模型启动额度，仍消耗18小时总时间。进入真实开发对照后，不再用准备阶段名义无限修设施。

## 4. D2：先明确规则，再校准参考和断言

### 4.1 公开契约必须能逐条映射

每项保留检查注明：公开条款、可观察结果、适用输入范围、正例、反例及失败分类。文档示例、类型检查和运行时检查使用同一套规则。没有公开依据的断言先不用于候选判失败。

对已转为开发材料的E/D，建议在新版本中明确：

- 键计算使用原回调的调用方式；接收者、参数副本和计算次数都属于契约。
- 支持的普通值、原生Promise和Promise-like对象分别是什么。新包装须保持适用原行为；不能引入额外未处理拒绝。新增属性访问本身可能影响行为，需要实际对照，不能仅凭外观相似推断等价。
- 新取消模式中，外部reason先按取消路径原值传播，不能在决定取消前对它做不必要的类型检查。旧模式的行为另行明确。
- 新版D的attemptTimeout在类型与运行时都接受null。另明确name是否要求字面量类型，以及元数据只读是类型约束还是同时要求运行时只读。建议新开发契约明确要求字面量name、类型及运行时只读元数据。
- 命令、保护路径、允许的生成缓存、回归有效性和全部评分时间边界都写入材料。

这些是待确认的新开发契约，不是对旧题面作追溯解释。旧null类型争议继续单列，不能回写成历史候选缺陷。

### 4.2 参考实现也必须被检验

修正E/D参考的原生Promise问题，并补齐本轮三个语义缺陷族：调用上下文、Promise传播、取消原值。用原库验证应保持的行为；原库不存在的新API，按新契约检验，不能把原库缺少导出误当作正例。

每题至少有一个完整参考和一个不同结构的正确实现用于校准。后者可以是明确修复后的历史产物副本，但必须另存、标明人为修复，不算agent成功。检查不能导入参考的业务helper，也不能要求实现结构或源码字符串相同。

同时纳入已知失败产物、去掉关键逻辑的错误变体、恒真测试、错误基线及缺失报告。至少为每个已确认缺陷族固定一个会失败的负例。错误不能靠吞掉消费者异常、安装全局兜底或跳过检查来变绿。

默认Node进程退出检查与带观察器的定位诊断分开。前者判断是否有额外进程失败，后者帮助定位来源；不以观察器抑制默认行为后的成功代替前者。

资格通过前确定案例清单和预期，再运行校准。新题原测试及正例在固定隔离环境下各完成5次预定重复；发生不稳定就停止准入，不选取其中的成功轮次。重复通过只说明已检查范围，不声称穷尽全部边界。当前助手的审查不称独立盲审。

## 5. D3：试验兼容行为复核，而不是增加次数

### 5.1 改动假设与产品范围

假设：在实现前说明需要保持的可观察行为，复核时针对最高风险变化取得可失败的行为证据，可能比只核对diff、Git和一般资源清理更容易发现兼容回退。这仍需实验，不能先宣布有效。

建议只试验通用工作提示与一次复核提示的调整。保留现有auto/off、40次工作加10次复核、30分钟任务上限、权限、取消、日志和追加式历史。不新增第二次复核、另一个agent、自动批准或任务专用工具。

建议的工作过程：

1. 实现前读原接口和实际接手代码，区分有意改变的行为与必须保持的行为。对于有脏改的源码，不能把HEAD当作真实接手版本。
2. 对本次改变的调用、返回、错误、取消或资源边界，选择风险最高的一项，明确“怎样的输入会让错误实现暴露”。这是可失败案例，不是写一句“已检查”。
3. 保持型要求用同输入的可信原态与新态对照。新能力用公开契约及有效行为断言检验，不能要求旧库通过尚不存在的新API。
4. 复核先看已有证据是否覆盖该变化。已有证据仍适用就复用；存在缺口再补。修复后重跑受影响检查，保留检查本身退出码。
5. 无法验证时明确未验证；确认违约而来不及修复时明确未完成。流程结束标记不等于独立验收通过。

通用提示不写具体库名、隐藏输入、三个最小复现或修复代码。不要求对每个任务机械新增测试，不强制使用全部10次复核请求。是否形成有效兼容证据由评测和人工复核判断，不用一段自述自动放行。

### 5.2 固定四次开发对照

| 版本 | 内容 | 运行 |
|---|---|---|
| 当前v1 | 0330626，原auto流程 | E、D各一次 |
| 候选v1 | 同工具、模型和预算；仅通用工作/复核提示调整 | E、D各一次 |

这里的“当前v1”不是正式三方中的v0。开发顺序固定为E当前→候选、D候选→当前。公开开发材料和新验收相同；开始四次运行前固定两版产品。中途不看结果改提示，不重抽普通失败，也不向候选反馈保留结果。

合格的开发版本必须两题完整交付2/2，且有与改动直接相关的有效行为证据、实际复核记录和无保护/协议回退。证据可以在工作阶段已经取得，不要求复核一定改文件。GC次数、测试数量和“发现几个问题”不单独充当成功指标。

选择规则提前固定：当前v1合格就保留0330626；当前不合格而候选合格，才选择候选；两版均不合格则停止，不进入C7或正式新题。两版都合格时没有必要仅凭更长提示选新版。这是小样本的候选筛选，不是统计意义上的优劣证明。

开发题已暴露给实施者，只能用于修复验证，不能充当新的正式迁移证据。

## 6. D4：通过前置后才进入发布对照

选定版本后固定产品、提示和auto配置，commit、push并核对远端。随后实际执行C7两题，各一次；完整2/2才选择新的正式题。即使选回0330626，也不拿上轮C7执行代替本轮要求的检查。

新题不能继续使用E/D或其改名版本。选两道复杂真实仓库任务，固定上游提交和依赖。建议分别覆盖多模块状态/资源行为、数据或CLI的兼容改动，避免两题都只是给Promise工具库扩API。两题都必须包含实际实现、多文件影响、兼容/异常边界、类型或数据契约、文档及有效回归。这里只确定选择标准，当前不挑题或接触新保留答案。

对新题重新完成D1/D2资格检查，固定公开条款、参考、保留检查、输入、环境和评分版本。三方分别为v0 `963704b`、选定v1、固定版本Claude Code；每题每方三次，共18次。顺序轮换、隔离工作卷、模型档位和总预算相同。

模型任务、容器评分和补充诊断串行使用评测资源。人工读取已封存日志可以在当前组三方的其他运行期间进行；不把隐藏结果反馈给候选。耗时是过程观测，不据小样本宣称性能优势。

每组三份完成后，控制器必须等待本组机判和人工判定。助手完成对应源代码、回归有效性、文档及报告复核，写出与产物哈希绑定的组决定，才能启动下一组。这样不会在人工已经发现候选不达标时又自动启动下一题。

发布门槛保持：选定版本确定性检查通过；当前C7完整2/2；新题中新v1完整6/6；没有未解决的保护、协议或已确认契约缺陷；完整可观察Trace齐全。不能靠降低门槛、修改正式题答案或重复抽样取得6/6。达到门槛后再处理明确的合并和版本发布，本方案不包含发布授权。

| 总时间 | 确认后开始实施时固定18小时，包含修设施、资格、改产品、准备新题、模型、恢复及报告；最后30分钟留报告 |

每次启动仍检查45分钟执行/评分窗口。每个三方组预留150分钟：135分钟执行/评分，加15分钟组级人工判定、准备和封存。恢复需至少156分钟，包含3个两分钟探针及整组窗口。人工判定到时仍不能确定则记录不可判定，不以赶时间代替审查。

新题准备前必须估算准备时间和后续组窗口；每个准入点重新检查原截止。18小时是上限，不保证所有样本都能跑满；不足就停止新增运行，不能从资格通过或正式开始重新计时。预算未确认前，本设计不创建新研究时钟或启动台账。

### 7.2 停止与恢复

- 开发无合格版本，或当前C7未完整2/2，就停止进入下一阶段。
- 正式新v1出现明确的普通契约失败，完成当前三方组及其判定后停止，不再启动下一组。这是本轮新增的组级止损规则；v0或Claude的普通失败单独保留，不因此重抽。
- 保护、隔离、鉴权、未知协议或证据完整性问题立即停止新增运行；若继续执行会扩大风险，则中止在途并保留实际可取得的Trace，不伪装完整。
- 已验证的临时上游错误仍最多一次整组恢复，不单独补失败一方。原组保留，探针和补跑都计入34次总额。
- 进入真实开发运行后，评分设施最多一次批次级离线修复，只能修实现，不能改变执行身份、冻结断言或评分语义。先重新校准，再统一重评当前研究全部已封存可评分产物；保留旧分数。再次发生无法可信判定的评分设施问题则结束研究。
- 正式中发现条款歧义或断言超出公开要求，不归为候选失败。暂停后续准入并单列；需要改契约或断言则终止本轮正式统计，下一设计重新确认，不借“设施修复”改规则。
- 新发现且明确属于已有契约的缺陷，可作统一补充诊断；原机判保持。对所有可比产物使用相同程序，必要时影响完整交付。声明之外的新要求只作为后续建议，不临时扣分。

控制器区分“停止新增模型”“在途完成封存”“评分可用/被阻断”“研究关闭”。一旦停止，启动台账立即拒绝新模型；无执行风险时，已启动任务在原预算内结束。评分器仍可信时可以处理在途产物；评分器已被判不可信时明确未评分，不以通用关闭异常掩盖具体原因。最终关闭不允许恢复启动额度。

### 7.3 完整证据与交付

继续保存API/CLI原始事件、工具和权限、原生日志、Claude stderr/debug、初态/检查点/最终文件与Git、执行及评分版本、失败和恢复记录。校验执行封存及新旧分数的哈希。Trace完整指可观察渠道，不包括服务端未返回的内部推理，工具自身截断仍注明。

每个阶段commit、push并核对远端。报告分别列采用组、诊断材料、未评分和未启动；不把缺分当失败。原始Trace和可能含凭据的配置保持私有，公开方法、脱敏摘要和最小诊断。

本方案不能保证下一轮一定6/6。它要先消除已有误判，再检验一个范围明确的交付改进假设，使“通过”或“未达到门槛”都有可复查的依据。
