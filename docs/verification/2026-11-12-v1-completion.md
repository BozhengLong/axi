## 3. 异常定位

Claude Code 的独立验收先通过交付、保护、Git、文档存在性、原上游30项测试、原类型测试和7项保留契约。随后外部类型检查无输出，持续60,013毫秒，评测器终止命令，记录 `exitCode=137`、`timedOut=true`。整体验收15分钟截止没有触发。

正式时没有采集容器内的原生调用栈。因此不能直接声称原进程卡在某个C++函数，也不能倒推上一轮缺少timedOut字段的137一定同因。

停止后用独立副本诊断，未追加模型调用：

1. 同一产物、镜像、未修改的验收器完整离线复验通过。外部类型检查354毫秒退出0；新增14项通过，原实现14项断言失败。
2. 原类型命令单独重复12次，全部通过。随后80次静默Docker命令通过，紧接的一次原类型命令再次60秒超时。容器内Node进程仍存在，外部控制器和观察命令正常运行。
3. 在同一产物上加入仅记录退出事件的诊断标记，交替执行50次原命令和50次关闭V8并发编译的命令，每次诊断上限5秒。原命令4次卡住，均已输出 `EXIT_MARKER:0`；主线程和V8工作线程等待futex。缓解组50次全部退出0。

这证明本地复现的失败发生在Node报告成功之后的退出阶段。其现象与Node官方记录的退出死锁一致；上游修复讨论说明后台编译可能等待主线程垃圾回收，而主线程正在等待后台线程退出。[Node问题64274](https://github.com/nodejs/node/issues/64274)、[修复讨论66171](https://github.com/nodejs/node/pull/66171)。本地未取原生栈，精确内部路径仍属于有证据支持的判断，不冒充直接观察。

## 4. 停止后的离线缓解

只修改V1新题的独立验收器中TYPES命令：tsc的Node启动参数增加 `--no-concurrent-sparkplug --no-concurrent-recompilation`。检查内容、严格类型选项、退出码判断、测试数量要求、超时和不可判定规则保持。候选CLI、模型、产品源码、候选命令、旧正式镜像和原评分都没有替换。

新增离线稳定性门槛：两道参考类型检查各重复25次，两个故意类型错误各重复25次，共100次；成功必须退出0，错误必须退出2并报告TS2322。任何超时或结果不符立即失败，不自动重试。正式启动器要求这份记录与当前完整源码、固定镜像和输入一致。

首次离线尝试将参数用于全部Node验收命令，AVA把参数传给Worker后报ERR_WORKER_INVALID_EXEC_ARGV。校准正确拒绝该方案，失败记录保留。最终只用于独立tsc，AVA、TSD、node:test和C7入口保持原样。

最终限定范围后的同一源码已通过：类型检查、92项本机测试/601个断言、100次正反类型重复检查、14项完整评分校准及8项公开命令/入口检查。原基线和六个错误变体按预期失败，参考通过，恒真测试被拒绝。当前离线修复源码指纹为 `fb5b180cc5419694605f18db594a676269bf88ca06fa78a9dcd40cd6208bc0ce`；它不同于正式批次指纹，不倒填到原运行。

这是一项限定范围的缓解措施，不是Node上游修复。候选自己执行的原始Node命令仍可能遇到同类问题；50次或100次通过也不能证明故障概率为零。下一轮真实模型比较前，应先确定统一的候选运行环境并完成重复验证。本次没有重新运行真实接入探针，也没有启动第四个正式样本。
