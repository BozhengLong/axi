# Axi / Claude Code 复杂任务同题对照

> 日期：2026-11-11。状态：已完成。冻结验收双方均 9/9；事后补充边界后的离线复验均为 7/9。两种口径分开报告。

## 1. 本次要回答的问题

本次检验两个工具能否在已有项目中处理并发、持久化、失败回滚、旧接口兼容和日志状态归并。原第一轮只有四类短任务，各重复三次；它们不足以支持复杂仓库能力判断。

本次方案与用户确认见[设计](../04-complex-evaluation-design.md)和[日报](../devlog/2026-11-11.md)。首批执行 C1、C2、C4。C3、C5、C6 仍是后续候选，未运行。

## 2. 题目规模与验收范围

| 任务 | 起点 | 主要独立检查 |
|---|---|---|
| C1 订单服务 | 虚构项目；15 个源文件，约 5.9 KB 源码 | 同键重放、库存竞争、三个写入故障点、跨进程共享库、提交后丢响应与重启 |
| C2 数据迁移 | 虚构项目；13 个源文件，约 4.9 KB 源码，真实 SQLite 原件 | 保留数据、状态映射、唯一约束、dry-run、回滚、非法数据、并发迁移、新旧 API/CLI |
| C4 离线回放 | 冻结的真实 Axi 副本；11 个源文件，797 行、约 37.9 KB | 原有 39 项测试、日志诊断、重试隔离、重复工具、离线检查、无历史命令副作用 |

这些题增加了相互关联的行为约束，但仍是小项目，题面也给出了明确契约。C1、C2 不是生产仓库的历史问题。不能把源文件数量当成难度证明；本次没有建立人工完成时间基准。

类型检查和旧测试是硬条件。数据损坏、兼容回归、改写受保护文件，任一发生都会使整题不通过。每题的验收组数不同，不把检查总数当成加权能力分数。

## 3. 运行条件

- 同一固定 Linux arm64 镜像、Bun 1.3.14、Claude Code 2.1.322；每个任务容器 2 CPU、4 GiB。
- 同一网关与模型 `claude-opus-5-5`、medium；每次任务最多 30 分钟、50 次模型 HTTP 请求。
- Axi 使用原有 bash 工具；Claude Code 使用原生 Bash/Read/Write/Edit/Glob/Grep。两边保留各自系统提示和执行循环。本次比较产品流程，不是仅比较工具接口或模型本身。
- 固定随机顺序，逐对交替先后次序。每次重新创建任务目录和 HOME，不继承上次候选结果。
- 正式阶段使用固定身份、日期的相同 Git 起点。候选与验收环境隔离；参考实现及独立探针不进入候选目录。
- 验收器在独立无网络容器运行，恢复控制器保留的原测试和配置。JSON 按结构比较，SQLite 按原始字节转移、按逻辑内容验收。
- 固定测试工具链为 TypeScript 5.9.3、@types/bun 1.4.2。依赖锁文件另行归档；未给 Axi 添加运行依赖。

## 4. 前置检查与验收器校准

正式前置检查 42 项通过。本地类型检查及 43 项测试通过，共 255 个断言。镜像内的 11 份 Axi 源文件哈希与本机冻结产品一致。

三份参考实现均通过当时冻结的验收。后续复查确认 C1 参考实现和验收器都遗漏了一个错误类型边界，见第 7 节。每题另有两份错误变体，均能正常编译并通过旧测试，但被相关行为验收拒绝：

- C1：去掉事务；忽略已有幂等记录。
- C2：去掉事务；升级后仍直接返回新状态给旧客户端。

这证明验收器可以识别上述错误，不代表已经证明任务足以区分两种工具。

## 7. 匿名复查与事后补充验收

固定抽取每题第 1 次运行，双方共六份产物。先隐藏工具名称，记录观察与待验证假设，再揭示映射。这是同一助手的辅助审阅，不是独立外部审查，不按代码行数或测试数量评分。

复查发现 C1 的一个具体边界：[公开契约](../../evals/complex-v1/C1/seed/contracts.md.fixture)要求故障钩子抛错时返回 `500/internal_error`。若钩子抛出已有的 `BusinessError(400/409)`，部分实现会被外层业务错误处理捕获，误返回 400/409。库存和订单仍正确回滚，问题属于错误分类，不是数据损坏。

在工具映射仍隐藏时，固定了“三个故障阶段 × 普通 Error / BusinessError(400) / BusinessError(409) / 字符串异常”的 12 个检查，并对全部六份 C1 产物统一验证。没有重新调用模型，也没有给某一方反馈后重做。

| C1 样本 | 原冻结验收 | 补充边界 | 说明 |
|---|---|---|---|
| Axi r1 | 通过 | 通过 | 已将故障钩子异常包装为内部错误，并自行写了对应回归 |
| Axi r2、r3 | 通过 | 未通过 | 六个 BusinessError 组合返回 400/409；数据回滚正确 |
| Claude Code r3（补跑） | 通过 | 通过 | 错误分类符合契约 |
| Claude Code r1、r2 | 通过 | 未通过 | 同样的错误分类遗漏；数据回滚正确 |

原参考实现也失败 6/12，说明最初的验收覆盖不足。修正参考实现后 12/12 通过。该检查已纳入当前 revision 3 验收器，参考实现和两个错误变体重新校准通过；六份保存产物也在完整的 revision 3 验收中复验，只有上述边界组失败。

|---|---:|---:|

| 事后加入同一公开契约边界，C1 离线复验；C2/C4 沿用原结果 | 7/9 | 7/9 |

第二行是事后扩展口径，不能伪装成预先冻结的成绩，也不覆盖原数据。[补充检查明细](2026-11-11-complex-supplemental.json)保留了每个错误类型、状态码、回滚和重试结果。

其他附加观察：两边 C2 都在写锁内读取版本并做状态映射，使用 `IS NULL` 过滤软删除；两边 C4 都把回放从 API 配置初始化前分流。Axi 的 C4 r1 还增加了真实日志生产者的合成往返测试。部分新增测试使用固定等待时间，尚不能据此证明所有调度条件下都稳定。未发现足够证据给可维护性建立总体排名。

### 评测设施的后续修复

- 传输摘要最初只收集 SSE 错误，漏掉普通 HTTP 429；原始 Trace 没有丢失。现已从原始 HTTP 响应补齐摘要，并增加两项回归。上文限流数据按原始记录重新统计。
- 复现并修复 Axi 测试适配器的完成识别：工具执行后 API 失败也会回到输入提示，旧适配器可能误报完成。修复前模拟场景返回 completed，修复后返回 product_error；正常场景仍完成。使用真实 CLI 和模拟 API，未调用真实模型。
- 核对本批 9 个 Axi 有效样本，最后一个完整 API 响应均为 end_turn，因此这项适配器缺陷未影响本批原成绩。它属于测试设施，不是被测 Axi 吞掉了错误。

最终本地类型检查及 48 项自动化测试通过；完成识别另有两个真实 CLI 模拟场景通过。真实 Axi 产品源码保持不变。

## 9. 结论与下一步

这组三题仍未拉开双方的通过率差距，但复查暴露了共同的错误分类遗漏，也暴露了验收器自身的覆盖缺口。不能用最初的满分断言产物完全满足契约。

本轮完成了 6 次试跑、19 次正式启动（18 个有效样本、1 次环境不可判定），并对保存产物做了事后离线复验。候选代码未自动合入真实 Axi，发现的问题与原始记录均保留。

任务比首轮多了并发、事务、兼容和真实项目功能开发，但仍是规格完整的小项目，实际任务只持续数分钟。下一阶段建议优先 C6 的连续需求与用户已有修改，并扩大真实项目上下文；本次发现的错误类型边界应作为固定回归。新阶段仍需先确认设计。
