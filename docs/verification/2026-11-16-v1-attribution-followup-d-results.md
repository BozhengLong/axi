## 2. 统一补充诊断：业务值多读then

D2人工审查发现，Axi用`(async () => await input(...))()`包装调用。内部async函数返回业务值时，Promise又解析该值一次。D1-Axi采用相同路径。先前D1审查只确认了原生Promise拒绝路径，漏掉了普通返回值的再次解析。

D公开题面已要求“原接口已经能处理的普通值、原生Promise和Promise-like返回值应保持可观察行为”。以下输入是普通对象：它的`then`前两次读取均返回undefined，第三次读取才抛错。它没有可调用的then，也没有同步阻塞或等待环。

```js
let reads = 0;
const marker = new Error('extra then access');
const value = Object.defineProperty({}, 'then', {
  get() {
    reads++;
    if (reads === 3) throw marker;
    return undefined;
  },
});
const actual = await pRetry(() => value, {
  attemptTimeout: Infinity, retries: 0, minTimeout: 0,
});
```

同一脚本在固定镜像、隔离副本上检查原库、两套参考和全部四份D最终产物。另一个正交输入只计数、不抛错。没有改变任一被测代码，没有新模型调用。

| 对象 | 只计数 | 第三次抛错的公开结果 |
|---|---|---|
| 原库、两套参考 | 2次 | 返回原对象 |
| D1-Claude、D2-Claude | 2次 | 返回原对象 |
| D1-Axi、D2-Axi | 3次 | 拒绝为marker |

这是现有兼容要求下的具体反例。预期先由普通值与原库的行为确定，再用参考校验；没有用参考投票定义新要求，也没有依赖固定微任务数。七个进程均正常退出，诊断容器和卷已清理。

因此D1-Axi先前“完整通过”的人工结论撤回，改为N类兼容失败。原机判、原审查及原配对文件留档；[日报第13节](../devlog/2026-11-16.md#13d1两边完整通过继续反向d2)保留当时结论，第14节追加更正。评分器未改，唯一评分修复没有再使用。两套参考通过该反例，无新评分争议，后续E继续。
