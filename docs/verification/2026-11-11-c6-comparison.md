# C6：真实仓库连续任务对照结果

> 日期：2026-11-11。状态：已完成。冻结正式验收为 revision 2；事后补充边界为 revision 3。两种口径分别保留。数据见[逐次结果](2026-11-11-c6-results.json)和[补充复验](2026-11-11-c6-supplemental.json)。

## 1. 这次工作本质上是什么

这是 coding agent 的端到端工程评测。目标是把“能否可靠完成任务”转成可重复执行、可独立验收、可追溯的证据，再据此决定 Axi 下一步值得改什么。

两种 agent 接收同一份真实仓库和逐轮需求。控制器负责隔离、投递、授权、保存现场和反馈。独立验收器判断代码是否满足契约。Trace 用来解释过程。参考实现与错误变体用于检查验收器自身是否可靠。

本阶段主要修改评测设施。被测 Axi 的 11 份源码与正式冻结哈希一致；候选 Listr2 改动没有合入 Axi 或发布到上游。本轮没有训练模型。后续产品改动需要基于具体问题，再用同一类回归验证效果。

## 3. 任务和环境

目标是公共项目 Listr2，固定提交 [`d4e97973e06a38f5c61d34c4182f72cb8c83566b`](https://github.com/listr2/listr2/commit/d4e97973e06a38f5c61d34c4182f72cb8c83566b)。提供完整的 414 文件仓库；主包包含 87 个非测试 TypeScript 源文件。不是大型企业项目。三轮分别为：

1. 新增公开 JSONL renderer，贯通别名、包导出、类型、文档、测试和消费者示例。
2. 根据真实可见验收结果复查和修正。
3. 增加输出过滤和文本转换，并接入用户新修改的策略文件，保留旧行为。

每条轨迹保持同一 CLI 进程、会话和工作目录。每轮暂停候选容器，保存稳定快照，在独立无网络副本验收，再恢复并投递下一轮材料。动态反馈没有包含隐藏用例或隐藏成绩。

环境为 Node 24.22.2、pnpm 10.34.9、Bun 1.3.14、Claude Code 2.1.322。候选每次使用独立工作卷和 HOME；依赖只读，运行时不能安装包或访问公网。资源上限为 2 CPU、4 GiB 内存；工作卷采用 2 GiB 监测限制，每 10 秒检查，属于监测型限制而非文件系统硬配额。

两次上游基线均完成构建、类型检查和原测试：285 项通过、4 项上游原有 skipped、625 个快照通过。正式前校准了参考产物与错误变体。三轮模拟还检查了进程/历史延续、暂停计时、文件权限、符号链接、用户补丁和真实反馈。

## 5. 事后发现的订阅清理边界

先对原批次首个环境可判定配对（编号 2）隐藏工具名，阅读 R1/R3 产物，再保存假设。匿名仅隐藏了工具元数据，不宣称独立双盲。之后执行统一探针，最后核对工具映射。

具体触发条件：一个先注册的监听器在 SUBTASK 事件分发中调用 renderer.end()。当前事件分发随后继续调用 renderer 已登记的回调。如果该回调没有检查 ended，就会在结束之后再次订阅子任务，并继续订阅孙任务。

探针首先检查参考实现和故意移除结束检查的错误变体。参考通过、变体失败。随后验证全部 9 份完成的最终产物，并用真实 Listr.run() 集成流程复现；改变监听器注册顺序、或在分发前结束的两个对照条件均正常。

正式采用样本中，Axi 第 2 次与 Claude Code 第 3 次失败。两者在结束后仍为子任务和孙任务各安装 3 个监听器。业务任务仍完成，记录也没有继续写出；缺陷是没有满足结束后的订阅清理约束，不将它描述为数据损坏或已经量化的永久内存泄漏。

新增检查为 H-END-DURING-SUBTASK。它覆盖 R1 已公开的生命周期要求，属于事后补充验收。原冻结成绩、原代码和旧验收文件均保留。没有把新反馈交给模型重做，也没有修补候选代码后重新计分。

试跑 Claude Code 和原首对 Claude Code 的最终产物也命中该边界，单列在补充数据中。原首对替换为整对补跑的决定早于这个问题的发现，未因事后分数改变选择规则。

## 7. 转发器修复和比较边界

双方都请求 claude-opus-5-5、adaptive thinking、medium。保留各自原生配置：Axi 的 max_tokens 为 64,000、thinking display 为 summarized；Claude Code 的 display 为 updates，max_tokens 通常为 128,000，但正式第 2 次的 57 个生成请求中有 1 次为 64,000。系统提示、工具和上下文策略也不同。本次比较的是完整系统，不能把差异单独归因于某一种工具。

评测后复查发现，旧转发器没有记录或透传 Retry-After。Axi 客户端本来支持该字段。官方接口将它用于指示重试等待时间，但并非每个 429 都提供该头。参见 [Claude API 限流说明](https://platform.claude.com/docs/en/api/rate-limits)。

修复后保留重试、限流和请求 ID 等允许的响应头，并按请求序号、轮次留证；认证、Cookie、压缩长度和逐跳响应头不透传。真实本地 HTTP 回归使用冻结 Axi APIClient、转发器和合成服务：上游给出 7 秒时，旧版客户端采用默认 1 秒参数，新版采用 7 秒参数；测试注入 sleep 记录参数，没有真的等待 7 秒。SSE 正文字节完全一致。没有真实模型请求。

修复发生在全部 C6 模型运行之后。新源码通过 52 项自动化测试、304 个断言；新镜像再次通过 44 项前置检查，包含真实模型连通性。这些后续修复不能追溯说成已经用于本批。历史上游响应头未保存，所以无法确认该缺口对当时限流恢复的具体影响；本批不支持原生恢复能力或速度排名。

## 9. 对下一步的意义

这次建立了可以自动跑完三轮、保留已有修改、独立判定并复查的测试基线。最具体的发现是一个双方都可能遗漏的事件清理边界，以及测试转发器的响应头缺口；两者都已转成固定回归。

下一步应把实际使用中遇到的失败加入这套基线，再验证针对性的 Axi 改动。若要专门评估收到缺陷反馈后的修复能力，需要预先设计独立的反馈输入集；当前这批首轮全过的数据不能回答那个问题。
