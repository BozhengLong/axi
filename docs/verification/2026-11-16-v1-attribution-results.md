## 2. E09为何使研究停止

公开[任务说明](../../evals/specs/v1-attribution-dev-v1/E/brief.md)同时要求：同键删除顺序执行，后一次不因前一次失败省略；新计算等待尚未完成的同键删除；后端删除失败时，删除调用和正在等待它的调用按原错误拒绝。

[冻结E09](../../evals/v1-attribution-dev-v1/oracle/E-test.mjs.fixture)运行这个序列：

1. 第一次删除D1开始，尚未完成。
2. 第二次删除D2排队。
3. 新的缓存调用P进入。
4. D1失败，D2随后成功。
5. E09要求P成功，结果为1。

这里缺少公开定义：P是只受进入时最新删除D2的结果约束，还是已经等待D1和D2，因D1失败而拒绝？后续删除自身仍会执行，并不能单独决定P的错误传播规则。

P3两份实现均采用后者。P3-Claude还有14项不依赖E09的明确错误，因此仍可确定为普通失败。P3-Axi的其他21条契约、157条重入序列、W01等待调用检查、原90项运行测试及类型检查全部通过；E09成为决定性判据。这使措辞分歧从限制说明变成不能公正判分的前提问题。

两套参考都通过E09，只能证明它们遵循同一种解释。此前正反校准、重复和全链路检查没有证明公开文字排除了另一种解释。**增加测试数量不能补上未定义的预期。**

按[方案第8节](../16-v1-axi-claude-attribution-plan.md#8-归因研究的完成条件与止损)，更改任务含义或预期不属于“同契约评分实现修复”。因此本轮没有用那一次修复额度来重写E09，没有重评成通过，也没有继续启动P4/Q。这次停止由评测契约触发，不由普通代码失败、请求额度或时间不足触发。

## 3. 目前能归因到哪里

### 3.1 Axi的D样本：验证选择和文档收尾有明确缺口

P2-Axi代码通过原132项运行测试、原类型和22条冻结契约；新增回归在当前实现通过，在原态取得真实行为断言失败。没有证据表明文件工具或协议错误造成这份产物缺口。

[D交付要求](../../evals/specs/v1-attribution-dev-v1/D/brief.md)明确要求实际运行相关示例。最终报告披露没有运行README/d.ts示例，理由是不能联网。相同环境中的Claude使用本地fetch替身执行了示例。Axi新增的`#attempttimeouterror`链接也没有对应标题或HTML锚点。

示例未执行是明确的交付缺口；如实披露不等于完成，也不构成伪造执行。报告总述“没有必需未完成项”过宽，但详细未运行项已披露，本轮按N处理。新增内部链接检查统一适用于全部六份README，只有P2-Axi发现该缺口；原机判不改，人工文档准确性审查不是新增产品要求。

Axi用了40次工作请求和2次复核请求，仍余8次复核请求。检查点代码已经通过，复核没有改生产文件，也没有补上示例或链接。因此支持的解释是本样本验证选择、文档收尾不足。不能由此断定预算不足、某条提示无效或工具存在确定性缺陷。

### 3.2 Claude的第二份E样本：明确遗漏同步重入的登记边界

实际工具返回已包含公开[重入登记条款](../../evals/specs/v1-attribution-dev-v1/reentrancy-contract.md)；相应返回没有截断标记。不是仅凭“文件存在”推定模型拿到要求。

产物在异步函数返回后，仅检查`!hasSettled`就把旧Promise重新登记。当`cache.has`或其属性读取同步重入delete/clear时，失效发生在登记之前。旧调用随后又登记自己，新调用便错误复用已失效工作。源码与运行前冻结的S122、S128、P143–P154共14项失败相互对应。

模型新增19项回归确实执行并通过。它们覆盖set、delete后端、cacheKey等重入路径，但没有覆盖这条“先失效、后重新登记”路径。报告所列原测试、类型、示例及回归都有执行证据；独立检查发现错误不等于报告伪造。

这里可以确认**产物的缺陷机制与验证覆盖缺口**。它还不能确认Claude内部为何漏掉该边界。相同Claude第一次E通过、第二次失败，也不能用于推断固定的模型能力上限。Q修复种子针对另一项共享作用范围问题，即使Q完成，也不能直接解释这份不同缺陷。

### 3.3 Axi的第二份E样本：无法作能力失败归因

P3-Axi用本函数`registrations`集合控制去重登记，用调用捕获的epoch/generation控制写资格，并在等待后单独刷新读取资格。冻结的登记、共享范围和等待调用场景通过。其`waitForDeletes`等待当时全部未完成删除，因其中D1失败而拒绝P；后续D2自身仍能执行成功。这是E09争议的具体代码路径。

本次37次工作请求后由草稿触发复核，复核用了4次请求。复核实际比较原库与新实现的clear重入行为，并重跑基线及必需检查。不能说复核完全没有做事，也不能把这些检查推断成E09已经有唯一明确答案。源码审查未确认另一项能独立决定失败的缺陷，最终保留不可判定。
