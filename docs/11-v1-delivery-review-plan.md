# v1风险归因与有界交付复核方案

2026-11-14。状态：D1–D5已由用户确认，开始实施。设计提出时未修改产品或验收器，也未启动模型任务；实际实施见[当日日报](devlog/2026-11-14.md)。依据是用户询问“针对这次发现的问题，下一轮应该怎么做，才能让v1达到发布门槛”。

## 1. 先确定这次失败意味着什么

[上轮报告](verification/2026-11-14-v1-rc-development.md)说明：协议兼容修复和确定性前置通过；两个开发产物都通过冻结自动验收，但完整交付只有1/2。Emittery新增的溢出路径丢弃内部Promise，导致未处理拒绝和进程退出。相同程序在原库及参考实现中正常退出。完整记录和旧机判保持原样。

| 层次 | 已有证据 | 判断 |
|---|---|---|
| Axi运行工具及协议 | 本轮110项测试、27项真实前置通过；没有API错误；实际工具结果留档 | 尚无证据表明这次生成代码缺陷由文件工具造成 |
| agent的交付判断 | 已报告Promise风险，却将其笼统归为旧行为，没有用同输入对照证明 | 据实报告测试结果，还不足以保证风险归因正确 |
| 验收器 | 原测试、新增回归和已补的`then` getter检查都通过；新诊断仍发现进程退出 | 原验收对异常传播的覆盖不足，必须补齐 |
| 产品流程 | 当前`Agent.run()`在正常`end_turn`后结束，没有单独的收尾复核阶段 | 可以试验一次有界复核，但不能先声称它必然有效 |

本方案中的“完整交付”指公开契约、保护项、有效新增回归、文档及报告都满足要求。写出代码、测试全绿或主动列出风险，都不能单独代替完整交付。一个已经证实影响契约的缺陷，不会因为列进“未完成项”就变成通过。

假设：把“旧问题”“不影响本次改动”等风险判断转成需要证据支持的判断，并在结束前安排一次有上限的复核，可能减少过早结束。这个假设尚未验证。同一个模型也可能重复原判断，因此仍需独立验收和人工复核。

## 3. D1：先让验收器能够发现这一类错误

“异常传播”不仅包括函数是否抛错，也包括内部异步对象在无人消费后是否把错误传到进程级。

实施时先固定测试矩阵与预期，再运行候选。矩阵从公开契约推导，不将未约定的新行为暗中设为扣分项：

| 维度 | 重点覆盖 |
|---|---|
| 值的类型 | 普通值、成功Promise、调用者已处理拒绝的Promise、拒绝的thenable、读取`then`时抛错的对象 |
| 生命周期 | 正常消费、等待消费、两种丢弃、溢出报错、取消、return、clear后排空 |
| 消费者状态 | 无等待者、多个等待者、相邻迭代器及普通监听者 |
| 观察结果 | 返回值及原始错误、顺序、订阅清理、晚到事件、全局拒绝及进程退出 |

不是机械穷举全部组合。选择能够区分合理实现和已知错误的组合，并写清每项对应的公开条款。不能要求参考实现也没有实现的行为，却仍把参考当作正确答案。

新增检查至少同时证明：

- 输入Promise已经由调用者处理时，库新建并丢弃的内部Promise不会造成额外的全局拒绝。
- 正常消费者仍能收到应传播的错误和原始reason。不能通过吞掉所有错误来通过检查。
- 原有`then` getter异常隔离、取消、return、clear和相邻监听清理继续符合契约。
- 一份带观察器的诊断用于定位错误来源；另一份无全局兜底处理器的独立子进程验证默认退出行为。不能用全局catch掩盖问题。
- 已知错误产物失败，参考通过；去掉关键清理或拒绝处理的变体失败，恒真回归不能通过有效性检查。原上游实现只作为适用行为的对照，不要求它通过尚不存在的新功能。

本次54次事后诊断保留原身份。下一版验收发布后，再将相应程序纳入新版本；不回写旧分数。文档示例语法检查和报告命令核对继续保留。

报告评分继续区分“执行结果准确”与“风险归因有证据”。涉及契约的重大风险若仍无法判定，不能仅凭报告文字获得完整交付通过。

## 4. D2：一次同会话的收尾复核

### 4.1 备选方案

| 方案 | 判断 |
|---|---|
| 继续只增加通用提示，再跑同样两题 | 改动最小，但上轮已有这类提示；难以确认模型是否执行了独立的收尾动作 |
| 一次有界收尾复核 | 推荐试验。可记录初稿、复核动作和最终产物，检查新增阶段是否实际改善交付 |
| 引入多agent审查、自动批准或复杂自主流程 | 当前不推荐。会扩大v1范围，还没有证据证明需要这些机制 |

复核仍由当前agent、当前模型和同一会话执行。它不是独立审稿人，也不称盲审。外部验收器的答案和结果不会反馈给复核阶段。

### 4.2 触发、预算与用户体验

建议增加本进程的`/review auto|off`控制，由本地用户设置，模型不能修改。候选默认使用`auto`，`off`用于明确退出和开发对照。普通问答不触发；本轮实际发生文件修改或获准执行bash后，属于可复核任务。bash可能有副作用，因此不只依据文件工具的修改清单判断。

流程只允许一次：

`正常工作 → 收尾复核 → 最终交付或未完成`

- 首次正常`end_turn`视为待复核初稿，不立即把它作为任务完成。
- 开启模式将正常阶段限制在最多40次实际生成请求，复核阶段最多10次；总计仍不超过50次，HTTP重试也计入。提前进入复核时，复核仍最多10次，不能吃掉全部剩余额度。
- 达到正常阶段上限时，只在完整响应和工具结果配对结束后的安全点切换。若请求失败、被截断或协议异常，按原失败规则停止，不把错误包装成正常复核。
- 一次模型请求可以产生多个工具调用。已有工具的审批、拒绝、取消和结果配对仍完整执行；切换阶段不能跳过配对，也不能重做已执行的副作用。
- 若40次边界遇到未完成的请求，或剩余时间不足，输出明确的未完成状态。整个任务仍受30分钟评测上限约束，不额外加10分钟或重新启动任务。
- 界面明确显示“待复核”和“收尾复核”。初稿保留为过程输出；最终报告完成后才回到输入提示符。预算不足或中止也返回控制，但不能标为成功交付。
- `off`使用同一全任务50次实际请求上限，无自动复核。两种模式均使用相同的模型、基础提示、工具和权限；实验差异为复核及其预算分配。

这是本轮新确认的产品行为。当前产品只有模型调用循环上限，重试与实际请求还须用统一计数器对齐；不能把10次高层调用误称为10次实际请求。计数应在API客户端每次发出生成请求前消费额度，并与转发器记录交叉核对。

### 4.3 复核要求

复核重点是补证据，不要求机械增加测试数量。已经在最后相关修改之后执行、且仍适用的检查可以复用；新增风险缺少证据时才补对应验证。不能靠重复无关测试制造已复核的印象：

1. 对照公开契约、实际diff和当前验证结果，检查是否有漏项。优先处理正确性和保护要求，再考虑可选风格检查。
2. 检查新增对象、资源或异步工作的所有者，以及它们在完成、拒绝、取消、丢弃和清理后由谁负责。只选择与当前改动有关的路径。
3. 对报告中的重大风险判断做核查。声称“旧问题”“与本次无关”“不会影响调用方”时，提供同输入、同环境下的可信基线与当前实现对照。证据不足则写未验证，不当成结论。
4. 基线指接手时实际代码。用户有脏改时，不能把Git HEAD冒充接手版本，更不能reset或覆盖用户文件。可信基线无法取得时如实说明；在隔离副本中复现，原工作区继续受保护。
5. 若已确认违反当前契约，在剩余预算内修复并复验。来不及修复则报告未完成。披露缺陷是必要记录，但不替代交付条件。
6. 最后一次相关修改后重跑受影响检查。记录检查自身的退出码，分别报告通过、失败、未执行及尚未验证的风险。

指令中不出现Emittery专用实现、隐藏测试名或`Promise.resolve(...).catch(...)`答案。不增加隐藏自动批准，不绕过用户拒绝，不允许为做对照而污染用户工作区。基础系统指令可补上通用的证据要求；开发开/关两种模式使用完全相同的基础指令。

### 4.4 Trace和确定性验收

历史仍只追加。自动插入的复核请求在API正文及原生日志中标明由Axi生成，不伪装成用户的新指令，也不覆盖用户约束。

增加阶段开始/结束、原因、请求计数及最终状态记录。评测侧分别封存复核前和最终产物，评分在最终执行结束后进行；初稿评分不得在运行中反馈给agent。无初稿交付而因40次边界进入复核时，将快照标为“工作中检查点”，不能和自然完成初稿混为一谈。

先做完整CLI模拟，覆盖触发一次、不触发、开关、工具配对、API重试计数、预算边界、拒绝、取消、日志失败、复核失败与下一用户回合。终端适配器须用原生阶段/结束状态核验完成，不能仅凭模型写了“完成”或出现一次`end_turn`就提前封存。已有权限、保护、协议及Trace检查继续运行。

## 5. D3：四次开发对照，先验证流程是否有用

使用已知p-limit、Emittery题，各做一次关闭模式和一次开启模式。顺序提前固定为p-limit关闭→开启，Emittery开启→关闭。四次独立工作卷，同一新产品/基础提示快照、同一输入/依赖/模型和50次请求上限，中间不调产品或验收器。旧两次试跑单列，不算本轮控制组。

冻结前完成D1的验收校准；四次运行期间，不返回保留测试或外部人工发现给agent。每次正常完成的产物仍进行代码、文档和报告复核。

主要比较：

- 完整交付及保护项，而非仅自动测试通过率。
- 开启模式有没有核查初稿的重大风险、取得有效对照证据、发现并修复问题。
- 初稿/工作中检查点与最终产物的变化；复核是否新增回退。
- 实际请求数、时间、确认次数以及未完成原因。二阶段不能通过超出总预算取得优势。

进入下一阶段的必要条件：开启模式两题均完整交付，无新的权限、协议或完成识别回退，且Trace证明复核实际执行。关闭模式的普通代码失败作为实验结果保留，不因此重抽或阻止完整记录另一模式；任一模式出现隔离、权限、未知协议或证据损坏则停止新增运行。

两对样本不能证明统计意义上的改善。若两种模式都通过，只能说候选满足开发门槛，不能说已证明复核提高成功率。若复核只是重复“检查通过”而没有实际核查，或开启模式未完整通过，则先分析，不进入正式轮、不重置四次额度。

## 6. D4：回到原发布门槛

开发门槛通过后，冻结开启模式的产品、提示和配置，commit并push。随后：

1. 新候选实际运行两道C7，各一次。两题完整通过才继续。历史产物离线重评不替代当前版本执行。
2. 再选择两道新的复杂真实仓库任务，固定提交、依赖、公开契约、参考实现和保留验收。要求多文件修改、兼容性、错误或状态边界、类型/文档及有效回归。
3. 旧Axi`963704b`、新候选、Claude Code各做两题×三次，共18次。同一执行环境和总预算，三方顺序预先轮换。复核属于新Axi产品行为，其全部请求、时间和确认次数计入新Axi，不给额外预算。
4. 新题结果不得反向用于调整本轮候选。若必须改产品，新题转为开发材料，停止按这份正式计划继续计分。

复用固定Node22、隔离、执行封存及独立评分。产品变化后派生新镜像，并验证源码和二进制指纹。新增的复核、完成识别和预算边界须用当前版本重验；旧环境证据只用于说明未变部分，不冒充新产品已通过。新题需要自己的参考、基线、错误变体和恒真回归校准。

发布条件不变：当前版本确定性检查通过，C7完整交付2/2，新题中新Axi完整交付6/6，代码/回归/文档/报告均通过，无未解决的保护、协议或已确认契约缺陷，完整可观察Trace齐全。不要求胜过Claude的速度或token，也不要求没有任何无关的旧缺陷。

## 7. D5：新预算与停止规则

本轮已确认预算如下：

| 用途 | 计划及上限 |
|---|---|
| 开发开/关对照 | 2题×2模式×1次，共4次；普通失败不补跑 |
| 当前候选C7 | 2次 |
| 正式三方新题 | 18次 |
| 正式上游恢复 | 至多1个完整三方组，增加3次；C7与正式总上限23次 |
| 真实探针 | 初始3次；合法正式上游恢复前最多再3次，总上限6次 |
| 真实CLI总上限 | 4 + 23 + 6 = 33次；基本计划为27次，恢复相关最多增加6次 |
| 单任务与评分 | 任务30分钟、50次实际生成请求含重试/复核；独立评分15分钟 |
| 单探针 | 2分钟、12次实际生成请求 |
| 绝对截止 | 确认后开始实施时固定18小时，含实现、前置、开发、正式和恢复；最后30分钟留报告 |

模型任务串行。每次启动检查能否容纳45分钟执行/评分窗口；完整三方组至少需要135分钟；恢复的三方探针及完整组至少141分钟，另核对准备/封存所需余量。开始新题准备前也估算准备时间和后续组窗口。上述是最低预算核查，不是“总上限内一定能全部跑完”的承诺；不足就停止新增运行，不延长时钟。

鉴权、未知协议、权限/隔离或证据异常直接停止。已知且已验证的临时上游错误才可在正式阶段使用一次整组三方恢复，保留原组。开发及C7的环境中断不单独重抽。

评分设施故障最多一次批次级离线修复。它只能改变评分实现，不能改已冻结的执行身份、断言或评分语义；先校准，再对全部已完成产物统一重评。新发现的契约边界不能冒充评分设施修复；应单列补充诊断，并统一核查可比产物。

旧研究继续关闭，旧额度不结转。新控制器须显式拒绝已写入关闭决定的研究；既有claim和只读封存继续保留。每个阶段commit、push并核对远端。完整Trace私有保留，公开报告只发脱敏摘要、方法和可复现诊断。

通过发布门槛后再办理明确的合并/版本发布事项。本次设计不包含发布授权。
