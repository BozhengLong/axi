# v0 设计：最小 agent 循环

> 状态：**D1–D5 已确认，v0 已实现并完成本轮验收**。确认依据见 [开发日报](devlog/2026-10-12.md)，实际结果与限制见 [验收记录](verification/2026-10-12-v0.md)。

## 目标

在终端里运行 `bun run axi`，进入多轮对话。每轮任务结束后，继续等待用户输入，并沿用本次运行中的会话历史。退出后恢复会话属于 v2 的范围。

模型可以调用 `bash` 工具。每次调用前展示工作目录和完整命令。用户输入 `y` 后才执行；输入 `n` 或直接回车则拒绝。

验收任务：

1. "这个目录里有什么，总共多大？"（单次工具调用）
2. "写一个 hello.py 并运行它"（多次工具调用、多轮循环）
3. 拒绝一条命令，看模型能不能换个办法继续（错误恢复）

## 整体结构

```
src/
  main.ts            入口：REPL，读用户输入、渲染输出
  api/
    sse.ts           字节流 → SSE 事件（纯函数，可单测）
    stream.ts        SSE 事件 → 拼装好的 assistant 消息
    client.ts        发 HTTP 请求、重试、错误分类
  agent/
    loop.ts          agent 主循环
  tools/
    bash.ts          bash 工具：schema + 执行 + 截断
  ui/
    permission.ts    命令确认
  log.ts             原始请求/响应写入 .axi/logs/
```

数据流：

```
用户输入 → loop → client.fetch(stream:true)
                     ↓ ReadableStream<Uint8Array>
                  sse.ts（切事件）
                     ↓ {event, data}
                  stream.ts（拼 content block，同时回调 UI 实时显示）
                     ↓ 完整 assistant 消息
          loop：stop_reason == tool_use ? → 确认 → 执行 → tool_result → 再请求
                                        : → 回到用户输入
```

## 一、协议层：手写 SSE 解析

### 已经实测到的事实（2026-10-12，经公司网关）

```
event: message_start
data: {"type":"message_start","message":{...}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""} }

event: ping
data: {"type": "ping"}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"1"}              }
...
event: message_delta        ← stop_reason 和最终 usage 在这里
event: message_stop
```

注意 `data` 末尾有**一串空格填充**，还会穿插 `ping` 事件。解析器必须容忍这两点。

### 解析器要处理的坑

| 坑 | 处理 |
|---|---|
| 网络分片是任意切的：一个事件可能分在两个 chunk 里，一个 chunk 也可能包含好几个事件 | 按行缓冲，兼容 LF、CRLF、CR。空行结束事件；未用空行结束的尾部事件不派发 |
| 一个中文字符（3 字节）可能被切成两半 | `TextDecoder` 开 `{stream: true}` |
| `ping` | 直接忽略 |
| `event: error`，HTTP 状态码却是 200 | 按错误类型分类。限流和服务端临时错误可重试，参数和认证错误不重试 |
| 流中途断开（没收到 `message_stop`） | 视为失败，**不把半截消息写进历史** |

### 拼装 content block

按 `index` 维护数组，按 delta 类型处理：

| delta 类型 | 处理 |
|---|---|
| `text_delta` | 追加文本，同时实时打印 |
| `thinking_delta` | 追加 API 返回的思考摘要，并按 D2 的展示规则实时打印 |
| `signature_delta` | 思考块的签名，**原样保存** |
| `input_json_delta` | 追加 `partial_json` 字符串，到 `content_block_stop` 时才 `JSON.parse` |

`input_json_delta` 是个学习点：工具参数是一截一截流过来的 JSON 碎片，中途不能解析。参数不是完整 JSON 对象时，本次响应失败，不执行工具，也不追加该 assistant 消息。日志保留原始响应，用户可以重新发起任务。

实现修订：原方案要求把半截参数作为工具错误回传。原始碎片不能直接成为合法的 `tool_use.input` 对象。v0 不伪造参数来修补历史。如果响应以 `max_tokens` 结束，但参数已经是完整对象，则追加对应的错误结果，要求模型缩短输出后重试。

### 项目规则：thinking 块原样回传

请求启用 adaptive thinking。响应包含 `thinking` 块时，Axi 将原文和 `signature` 一起保留在历史中。摘要不保证每次请求都返回。

从 v0 起采用项目规则：**历史只追加，不修改**（append-only）。v2 做上下文压缩时，需单独设计变更方式。

实测修订（2026-10-12）：E5 的完整历史对照和删除 thinking 块的请求均成功。当前网关没有返回预期的签名错误。因此，不能将“删除就一定报错”作为事实，也不能据此推断其他接口都允许删除。Axi 的保留规则不变。原设计判断保留在 Git 历史中，实测差异见开发日报。

## 二、Agent 循环

```ts
while (true) {
  const msg = await callModel(history)      // 流式
  history.push({ role: "assistant", content: msg.content })  // 整块追加，含 thinking

  switch (msg.stop_reason) {
    case "end_turn":   return               // 回到用户输入
    case "tool_use":   break                // 执行工具，继续循环
    case "max_tokens": 提示用户；如果最后一块是 tool_use，回 is_error 让模型重来
    case "refusal":    提示用户，结束本轮
  }

  const results = await runTools(msg.tool_uses)  // 可能有多个（并行调用）
  history.push({ role: "user", content: results })  // 所有结果放进同一条 user 消息
}
```

两个容易写错的地方：

- **并行工具调用**：一条 assistant 消息里可能有多个 `tool_use`，所有 `tool_result` 放在**同一条** user 消息里返回，以保留调用与结果的对应关系。v0 按顺序确认并执行这些调用。
- **每个 tool_use 都必须有对应的 tool_result**，被拒绝或报错也一样（用 `is_error: true`），否则下一次请求直接 400。

循环上限：单轮用户输入最多 50 次模型调用，防止死循环。

## 三、bash 工具

```jsonc
{
  "name": "bash",
  "description": "在用户的 macOS 终端执行一条 shell 命令……",
  "input_schema": {
    "type": "object",
    "properties": {
      "command": { "type": "string" },
      "timeout_ms": { "type": "number" }
    },
    "required": ["command"]
  }
}
```

执行方式：

- 每次调用都 `Bun.spawn(["bash", "-c", command], { cwd })`。**无状态**：上一条命令里的 `cd`、`export` 不会带到下一条。v1 再考虑持久 shell。
- stdout 和 stderr 合并，结果里附上退出码。
- 默认超时 120 秒，可指定 1 至 600000 毫秒。超时或中断时终止同一进程组，并返回错误结果。已发生的文件修改不会自动撤销。
- stdin 关闭。v0 不支持交互程序或后台任务，shell 结束时回收同一进程组的残留进程。
- **输出截断**：超过 30,000 字符时保留头尾各一半，中间写 `[省略 N 字符]`。不截断的话，一条 `cat` 大文件的命令就能撑爆上下文。

### 安全

- 每次 bash 调用前展示工作目录和完整命令。输入 `y` 才执行；输入 `n` 或直接回车则拒绝。只读命令也遵守该规则。
- 一次确认只授权当前调用。一个调用可以包含多行命令，必须完整展示后一起确认。
- v0 不提供沙箱隔离。人工确认不能将命令限制在项目目录内。进程隔离留到 v4。

## 四、请求参数

| 参数 | 值 | 说明 |
|---|---|---|
| `model` | `claude-opus-5-5` | |
| `max_tokens` | 64000 | 输出上限。每次 HTTP 请求仍设 5 分钟超时 |
| `stream` | `true` | |
| `output_config.effort` | `medium` | D4 已确认：默认 medium，支持 `/effort` 切换 |
| `thinking` | `{type: "adaptive", display: "summarized"}` | D2 已确认：默认显示 API 返回的思考摘要 |
| 工具上的 `eager_input_streaming` | `true` | 参数一生成就流过来，不等服务端缓冲完。代价是服务端不再校验 JSON，客户端要自己校验 |
| system prompt | 简短：身份、工作目录、操作系统 | **不放当前时间**，否则每次请求前缀都变，v2 做缓存时会失效 |

## 五、可观测性（v0 就做）

- 每次模型调用结束打印一行：`↑ 输入 1,234（缓存读 0 / 写 0） ↓ 输出 567  ⏱ 3.2s`
- 每个请求体和每条原始 SSE 行都写入 `.axi/logs/<session>.jsonl`，后面做实验和排查问题都靠它。

## 六、错误处理

| 情况 | 处理 |
|---|---|
| 429 / 5xx / 网络错误 / 流中临时错误 | 最多重试 3 次（1s、2s、4s），优先使用有效的 `retry-after` |
| 400 / 401 / 404 | 不重试，打印错误体。400 多半是我们的历史拼错了，这时正好看日志 |
| Ctrl+C | 中止当前输入、请求或命令。未完成的 assistant 消息不入历史；已收到的工具调用补齐结果，再回到输入框 |

## 七、v0 不做的事

文件读写工具、edit、权限规则、持久 shell、会话保存、prompt caching、上下文压缩、TUI、subagent、MCP。

## 决策点与确认状态

**D1 交互形式（已确认：A，2026-10-12）**

- A. REPL 多轮对话（已选）：启动一次，可以持续追问。程序需要管理会话历史和输入状态。
- B. 一次性命令 `axi "做某事"`：任务完成后退出，适合脚本。后续补充需要重新发起。一次任务仍可包含多次模型请求和工具调用。

决定与范围：

- 用户运行 `bun run axi` 后进入对话。每轮任务结束后，程序继续等待输入。
- 连续对话使用当前进程中的历史，包括用户输入、模型消息和工具结果。
- v0 不支持退出后恢复会话。运行日志仍按可观测性方案记录，日志不提供会话恢复功能。
- 选择理由：便于通过连续追问，验证模型能否承接前文和工具结果。
- 确认依据：用户对“连续对话，历史仅保留在本次运行中”的方案回复“好的，我觉得可以”。见 [2026-10-12 开发日报](devlog/2026-10-12.md)。

验收补充：先要求创建 `hello.py`，完成后再要求“把刚才的输出改成中文”。第二轮应承接第一轮的文件信息。

**D2 思考摘要展示（已确认：A，2026-10-12）**

- A. 显示摘要（已选）：便于观察模型报告的处理思路，有助于学习和排查问题。终端文本会增加。
- B. 隐藏摘要：只显示等待状态，界面更简洁。等待期间可见的信息较少。

决定与范围：

- 请求使用 `thinking: {type: "adaptive", display: "summarized"}`，默认展示 API 返回的思考摘要。
- 使用灰色文字和“思考摘要”标签，与正文和工具输出区分。即使终端不显示颜色，标签仍能区分内容。
- 摘要随流式响应显示。等待期间没有摘要内容时，显示“正在处理”。
- 展示层的格式不改变原始 thinking 块。块内容及签名仍按协议要求保存和回传。
- 选择理由：v0 兼顾学习和实际使用，需要让用户观察模型报告的处理思路。任务完成情况仍由工具结果和验收证明。
- 确认依据：用户对“D2 采用 A，默认显示思考摘要”的方案回复“可以的”。见 [2026-10-12 开发日报](devlog/2026-10-12.md)。

验收补充：有摘要时，摘要与正文、工具输出可以区分；没有摘要内容时，等待状态仍可见。公司网关对相关参数和返回块的支持需在实现时验证。

**D3 执行确认（已确认：A，2026-10-12）**

- A. 每次 bash 调用都确认（已选）：执行前可以检查完整命令，便于观察过程。多次调用会频繁打断用户。
- B. 只读命令自动执行：查看和搜索时更顺畅。需要可靠判断整段命令的效果，不能只根据命令名称判断。

决定与范围：

- 每次调用前展示工作目录和完整命令。多行命令必须完整展示。
- 输入 `y` 才执行。输入 `n` 或直接回车则拒绝，不启动当前调用的进程。
- 一次确认只授权当前调用。若模型返回多个工具调用，每个调用都需要单独确认。
- 只读命令也需要确认。v0 不提供自动放行规则。
- 被拒绝的调用仍需返回对应的工具结果。是否附加拒绝理由由 D5 决定。
- 选择理由：v0 先采用明确的授权规则，让用户观察每次执行。只读效果判断留待后续工具和权限设计。
- 确认依据：用户明确回复“D3 就按 A 来，每次调用都确认，回车默认拒绝”。见 [2026-10-12 开发日报](devlog/2026-10-12.md)。

验收补充：连续两次调用应分别请求确认。输入 `n` 或空输入后，对应命令不得执行。输入 `y` 只执行当前调用。

**D4 effort 默认档位（已确认：B，2026-10-12）**

`effort` 是模型处理请求的投入档位，会影响思考、回答和工具调用。它不是固定的 token 配额。Opus 5.5 的 API 默认值为 `medium`。依据：[官方 Effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)，2026-10-12 查阅。

- A. `high`：提高模型的处理投入，适合比较复杂任务的效果。对 Axi 的质量收益和耗时影响尚未实测。
- B. `medium`（已选）：先为 v0 的短任务建立基线，再用实际结果判断是否需要提高默认档位。
- 修订说明：原设计推荐 `high`。评审改为推荐 `medium`，主要考虑当前任务范围和交互反馈速度。用户已确认此方案；原推荐和修订依据保存在 [开发日报](devlog/2026-10-12.md)。

决定与范围：

- 默认使用 `medium`。
- 提供 `/effort medium` 和 `/effort high`。用户在等待输入时切换，从下一轮用户任务开始生效。
- 同一轮任务及其工具循环使用同一档位。每次模型请求的日志记录实际档位。
- 选择理由：先建立完成质量和等待时间的基线，并保留手动提高档位的能力。Axi 中的实际效果仍待实验验证。
- 确认依据：用户明确回复“D4 就按 B 来，默认 medium，保留 /effort 切换”。见 [2026-10-12 开发日报](devlog/2026-10-12.md)。

验收补充：新会话请求默认使用 `medium`。切换到 `high` 后，下一轮任务的全部模型请求使用 `high`。再切回 `medium` 后，下一轮请求恢复该档位。

对比实验：使用相同任务和相同初始文件比较两档。记录结果和处理耗时，扣除用户确认期间的等待。首轮已比较 120 行文件的命令生成；两档生成内容均通过校验，但没有执行生成命令。样本量和时间波动不足以判断普遍的质量或速度收益。详见开发日报。

**D5 拒绝命令后的反馈（已确认：A，2026-10-12）**

- A. 拒绝后可以附理由（已选）：模型能获得调整依据。用户多处理一个可跳过的输入步骤。
- B. 直接返回“用户拒绝执行”：操作较快，但模型缺少调整方案的依据。

决定与范围：

- 输入 `n` 或直接回车后，当前命令保持未执行状态。
- 显示“拒绝理由（选填，回车跳过）”。理由允许留空。
- 有理由时，将“用户拒绝执行，命令未执行”和用户理由一并传给模型；没有理由时，只返回拒绝事实。
- 要求模型遵守理由中的约束。模型可以询问、解释或提出符合约束的新方案，不能通过改写命令绕过用户拒绝的操作。
- 后续每次 bash 调用仍遵守 D3，均需用户确认。
- 选择理由：保留用户的限制条件，同时允许快速跳过理由输入。
- 确认依据：用户于 2026-10-12 回复“D5 就按 A 来，理由可选，回车跳过。这样 D1–D5 都定了，我们开始实现 v0。”

例子：用户拒绝覆盖文件，理由为“保留原文件，另存为 hello_new.py”。模型应根据这项约束提出新方案，再请求执行确认。
