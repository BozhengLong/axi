本方案使用以下术语：

| 术语 | 含义 |
|---|---|
| 执行环境 | agent实际看到的镜像、运行时、依赖、题目、工具、权限和资源限制 |
| 执行产物 | CLI结束后收齐的代码、Git状态、报告、请求与原生日志等不可变证据 |
| 评分版本 | 在独立容器中检查既有产物的代码、镜像、依赖和规则指纹 |
| 评分重放 | 不调用模型、不修改候选产物，用指定评分版本重新检查全部指定产物 |
| 三方组 | 同题、同重复编号、同执行环境下的旧Axi/新Axi/Claude三个样本 |
| 不可判定 | 环境或证据不足，无法可靠归因到候选能力；不当作代码失败或成功 |

设计时的假设：使用兼容的固定Node 22版本，可避开本轮观察到的退出异常。当时该假设尚未在新镜像验证。重复通过只提供限定条件下的稳定性证据，不保证故障概率为零。

截至本次核查，官方将Node 22列为维护中的LTS系列，归档版本为22.23.5。[版本状态](https://nodejs.org/en/about/previous-releases)、[22.23.5发布归档](https://nodejs.org/en/download/archive/v22.23.5)。冻结输入声明p-limit要求Node>=20，Emittery要求Node>=14.16；这只能说明库的声明允许该版本，不能替代对完整依赖、测试工具和Claude启动路径的实际验证。上游[退出挂起问题64274](https://github.com/nodejs/node/issues/64274)只作定位参考，不作为本机已经修复的证明。

## 3. 执行环境与冻结

### 3.1 新镜像的范围

- Axi产品源码、Bun 1.3.14、Claude Code 2.1.322、pnpm 10.34.9、TypeScript 5.9.3、任务依赖锁与库提交保持。单独核对Claude可执行文件及其实际解释器，不能从安装方式推断其运行时。
- 目标Node固定为22.23.5。实现时核对官方发布校验和、平台/架构和实际二进制；记录新镜像完整digest。设计阶段未预填镜像ID；实际构建结果写入执行记录。
- 使用同一基础镜像派生，不重新拉取可变latest标签。优先只替换Node二进制，保留现有其他工具。若npm或原生依赖与该Node不兼容，记录具体依赖关系并停止重新设计，不静默更新锁文件。
- 新环境的Node命令不使用全局V8参数或退出码替换。独立tsc也在这个新profile下重新校准；旧Node 24的局部缓解保留在其旧评分版本，不直接套用到新profile。
- 保持2 CPU/4 GiB、2 GiB工作卷预算、4 GiB宿主归档余量、依赖只读、候选网络隔离和假token。真实凭据仍只进入转发器。
- 两题功能、原测试、参考实现和保留契约不改。环境说明更新Node版本及实际命令后，生成新输入hash；记录相对上一输入的差异。

### 3.2 冻结记录

分别记录executionProfileHash与graderRevision。执行profile覆盖产品与CLI源码/二进制、镜像、Node/Bun等版本、依赖清单、题面、模型/effort、权限、预算和顺序。评分版本覆盖评分代码、镜像、原测试/契约/类型检查和回归有效性规则。

模型仍为claude-opus-5-5、effort=medium。每次生成请求核对实际配置；计数请求与实际转发的生成请求分开。正式运行后执行profile不得改变。

## 4. 样本复用与评分恢复

### 4.1 本次旧样本如何处理

D1改变了agent实际使用的Node环境，因此旧9次正式运行均不进入新环境的胜率或时间比较。本次新题重新运行完整18次。旧3份首题产物可用于验证评分重放机制，但标注为诊断材料。

旧两道C7仍是历史模型执行，产品源码没有改变。将两份原交付产物在新环境离线复验，连同原语义审查，作为已知回归证据；必须明确标注“历史执行 + 本轮离线检查”。它们不计本轮18次，也不冒称本轮又完成两次模型任务。

### 4.2 执行与评分分离

执行结束后先冻结候选容器，结束后台残留，保存交付/最终文件和Git状态，收齐原生日志与API事件。逐文件校验后写入不可变的执行清单；保存前后产物变化要显式记录。证据不全或无法判明交付状态时停止，不进入自动重放。

评分结果以`运行ID + graderRevision`另存。汇总视图引用执行清单、评分文件和人工审查，不回写原result。正常执行但评分异常时，分别记录`execution=completed`和`grade=indeterminate`；不再用一组false同时表示代码失败和评分失败。

新鲜独立评分容器只接收冻结产物，不接收候选仍运行的进程。所有原始评分、失败命令和缺口保留。重新评分不会重新调用模型、重新给agent反馈或改变报告。

### 4.3 恢复判定

| 事件 | 本轮处理 |
|---|---|
| 候选功能/类型断言失败、测试不足、报告不实、正常预算耗尽 | 按实际失败记录，继续原计划；不重抽 |
| CLI结束后评分执行器、评分运行时或输出收集故障，执行证据完整 | 停止新增模型启动；保留原机判。可用一次批次级恢复额度，离线修复并校准后重放全部已完成产物 |
| 恢复涉及测试期望、公开契约、保护规则或评分语义变化 | 不属于自动评分恢复；停止并提交设计变更 |
| 恢复涉及候选镜像、CLI、题面、资源、模型、权限或执行控制器语义变化 | 执行条件变化，停止本轮，不将旧执行与新环境拼接 |
| 明确的上游连接/限流故障导致执行不可判定 | 不干预产品既有重试。自然结束后，按额度对同组三方全部补跑一次 |
| 真实凭据暴露、隔离失效、权限配对异常、证据损坏、未知协议故障 | 立即停止并留证，不用评分恢复或补跑额度掩盖 |

评分恢复只允许一次，适用于整个新批次，不按样本分别重置。修复前必须证明问题位于评分层；保持原断言与输入不变，通过正反校准和故障注入后，按固定顺序重评全部已完成产物，包括此前成功和失败的产物。每份产物在新评分版本只评一次。仍有不可判定，或后续再次发生评分设施异常，则停止本轮。

恢复成功后，后续样本使用同一新评分版本。原评分仍可查。普通断言失败即使在重放中存在，也保持失败，不再单独重跑直到成功。该规则只在新方案确认后生效，不改变已结束批次的约定。

| G5 恢复规则 | 注入交付后评分挂起、评分普通断言失败、证据缺失、执行profile改变、第二次评分异常、截止不足 | 只有第一种可走一次评分恢复；普通失败无模型补跑；其余按规则拒绝；模型调用数可核对 |
| G6 真实接入 | 旧Axi、新Axi、Claude各1个固定短探针 | 配置、读取/写入/执行、正常结束、Trace全部通过；不计能力成绩 |

G2按冻结顺序交错正反类型，并在每个正式三方组前做短离线参考健康检查。短检查失败即停止，不单独重抽健康检查。不得在正式期间修改Node参数或延长类型检查上限来通过。

同一完整源码指纹下收齐门槛后，提交、推送、核对远端，再建立新的正式claim。普通自动化测试仍只使用模拟API；真实接入和正式模型执行需要显式入口。

## 6. 样本顺序、预算与结束条件

两题仍为p-limit取消/空闲通知、Emittery有界迭代器。固定题已参与设施诊断，因此称固定题复验，不称盲测。完整顺序沿用v1：

| 组 | 题目/重复 | 执行顺序 |
|---|---|---|
| 1 | A/1 | 旧Axi → 新Axi → Claude |
| 2 | B/1 | Claude → 旧Axi → 新Axi |
| 3 | A/2 | 新Axi → Claude → 旧Axi |

| 5 | A/3 | Claude → 旧Axi → 新Axi |

推荐预算：

- 正式18次；至多一组完整三方上游恢复，最多21次新正式启动。原9次不改变，不把额度理解为允许其他重抽。
- 每次30分钟、最多50次实际转发生成请求，包含产品重试。每份独立验收最多15分钟。
- 正常真实探针3次；上游恢复前允许额外三方健康探针各一次，合计最多6次。每次最多2分钟、12次生成请求，单独列账。任一探针失败则停止，不自动重试探针。
- 新方案确认并开始实施时固定18小时绝对截止，包含准备、探针、正式执行、离线评分恢复和报告。最后30分钟预留报告。开始每组前检查可容纳三方最坏执行/验收窗口；上游恢复还须容纳健康探针。剩余时间不足即停止，不延长截止。
- 评分恢复最多一次，不增加模型启动额度；所需校准与全部产物重评也必须在原截止内完成。

正式比较只采用同执行profile、同最终评分版本的完整三方组。分别报告执行正常率、功能通过、有效回归、报告准确性、完整交付、权限次数和时间/用量。中断的组、原恢复组和历史C7另列。

阶段完成条件：确定性门槛通过，新Axi6次新题均完整交付，历史C7两份产物在新环境回归通过，无未解决的保护或协议回退。旧Axi和Claude无需低于新Axi；普通能力失败要如实报告，不能通过后加样本取得6/6。
