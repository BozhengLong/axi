# 方案 27　上游 OAuth 过期后的重试和验收

2026-11-19。用户确认按 D1–D5 执行。目标是让 Axi v1 在网关偶发上游 OAuth 过期时，能在原时限内重试同一次模型调用，并据实报告是否恢复。产品候选和正式评测规则均需要变更。

## 冻结候选的实际行为

在产品提交 `280d1f3` 上，通过 `APIClient.call` 离线回放封存响应。每个样本的第二次请求都可取得同一份完整响应，以区分客户端是否真的发出了重试。共使用两条 R6b HTTP 401、一条 R6c 流内 401 和两条对照。未向网关发起新调用。

| 首次响应 | 样本数 | 每个样本实际发送次数 | 结果 |
| --- | --- | --- | --- |
| R6b HTTP 401，网关转述上游 OAuth 过期 | 2 | 1 | 客户端记录不重试 |
| R6c HTTP 200，流内错误携带上游 401 | 1 | 1 | 客户端报“事件缺少 type”并退出 |
| HTTP 429 | 1 | 2 | 客户端重发同一请求，取得完整响应 |
| HTTP 401，客户端 API key 无效 | 1 | 1 | 客户端立即退出 |

R6c 随后的四次成功各有独立随机标记。它们能证明路由间歇可用。原失败请求的恢复能力仍需用同一逻辑调用验证。[五次原始实测](verification/2026-11-19-r6c-gateway-stability.md) · [R6b 两次 HTTP 401 的归因](verification/2026-11-19-r6b-oauth-attribution.md)

## 建议的产品和评测决定

1. **D1　只重试已识别的上游过期错误。** 对配置的同一网关，识别两种已留证的错误封装。HTTP 401 需要解析网关转述的上游鉴权错误及过期原因。HTTP 200 的事件流需要检查事件名 `error`、内层状态 401、结构化 `authentication_error` 和明确的令牌过期原因。仅在错误通道判定。裸 401、客户端 key 无效、403、归属不明的鉴权错误按原行为停止，并报告可核对的脱敏原因。
2. **D2　重发同一次模型请求。** 仅在失败尝试尚未交付模型内容或工具提案、没有工具副作用时适用。沿用同一网关、客户端身份、模型、请求体和逻辑调用 ID，使用既有退避、取消及故障时间预算。产品默认故障窗口为 10 分钟；正式健康执行窗口为 3 分钟，先到的截止生效。成功前的每次错误、等待和尝试均写入 Trace。持续过期、取消或超时即结束。Axi 只持有客户端 key，服务端凭据的刷新和选择由网关运行方负责。
3. **D3　把连续实测的单位定为逻辑调用。** 冻结新候选后，在同一网关、冻结模型和 medium 档发出 5 个带不同随机标记的逻辑探针。每个探针的所有内部尝试共用一个标记、请求体和 3 分钟预算，相邻探针至少间隔 20 秒。每个探针都需在预算内得到正确模型、正确标记、闭合的内容块、`end_turn` 和 `message_stop`。可采纳 D1、D2 规定且证据完整的本次恢复，并延续既有限流恢复机制。报告同时列出首次成功数、重试后成功数、物理尝试和未恢复错误。5/5 才开批。
4. **D4　对三方应用同一证据标准。** Axi v0、Axi v1、Claude Code 各自运行原生 CLI。代理逐次记录，由各产品自行决定是否重试。恢复要求在同一 CLI、同一逻辑调用中，以相同请求体获得完整响应。核对原生记录、代理顺序、工具执行次数与产物。响应归属不明、重复执行、未解决的流中断或迟到响应均不能放行。各产品的首次表现和恢复表现分别报告。原有整槽重跑预算、环境事件数和截止时间继续适用。[原恢复规则](25-v1-recovery-health-plan.md)
5. **D5　先验证，再冻结和计分。** 用实际封存的两种错误格式回放“过期后成功”和“持续过期”。覆盖无效 key、403、普通文本伪装成错误、半截响应、工具已开始、换调用或换模型、超时和取消。用三套 CLI 的已知输入验证设施能分别认出首次通过、确证恢复和未恢复。复核受产品和评分设施改动影响的工程门槛及模拟证据，生成新的候选、设施身份和账本。通过容量等原准入后，三方正式健康 3/3 才进 C7，当前 v1 的 C7-L、C7-O 通过 2/2 才进 20 题三方对照。旧成绩封存，正式分数从零开始。[发布门槛](22-unbounded-candidate-acceptance-plan.md)

该方案验证调用能否恢复并继续交付。对具体过期凭据及刷新原因，仍沿用此前的未决归因。
